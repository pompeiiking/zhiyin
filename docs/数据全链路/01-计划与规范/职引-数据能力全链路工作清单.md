## 一、职责总览

数据能力全链路如下：

```text
外部数据源 / 用户授权数据
        ↓
采集 Fetch（公开页面、授权 API、文件上传、人工导入）
        ↓
解析 Parse → 清洗 Normalize → 去重 Dedup → 审核 Review
        ↓
数据分流
  ├─ 公共知识：专业、职业、岗位、政策、理论
  ├─ 临时缓存：原始响应、短期岗位快照
  └─ 个人数据：画像、行为、会话记忆、资产版本
        ↓
MySQL / Redis / 对象存储 / pgvector
        ↓
关键词检索 / 向量检索 / 混合检索 / RAG
        ↓
业务服务：资产、记忆、工作台、影响面传播
```

### 1.1 数据域红线

1. 描述“世界”的公共知识不得写入个人画像。
2. 描述“这个用户”的简历、测评、目标和对话抽取不得进入公共知识库。
3. 原始 HTML、JSON 和临时岗位列表只进入短期缓存，不进入长期业务库。
4. 个人抽取数据必须带 `source`、`confidence`、`evidence`，需要用户确认的不得直接成为确定事实。
5. 外部采集必须先确认 robots、站点协议、授权与使用范围；禁止绕过登录、验证码、访问控制或反爬机制。
6. Repository 只负责保存与查询；版本为什么增长、哪些资产受影响、何时发布事件属于业务服务或 Policy。

## 四、M2：业务主干端到端（本期核心）

M2 目标是在本地实现和第一期 Redis 上跑通真实业务数据闭环，不追求生产级关系数据库和向量检索。Redis 在第一期直接接入，用逻辑库隔离不同用途；画像、资产、行为和会话记忆等权威数据仍不得只存在 Redis 中。

### 4.1 会话记忆能力

| 工作项 | 代码位置 | 交付要求 |
| --- | --- | --- |
| 会话记忆服务 | `zhiyin-business/zhiyin_business/services/memory.py` | 创建、读取、更新、追加摘要、维护当前环节/主理/最后活跃时间 |
| 会话记忆存储 | `repositories/memory.py` + 本地实现 | 按 `user_id + task_id` 隔离，支持列出用户全部任务会话 |
| 可拆可续验收 | `tests/e2e/test_main_path.py` | 用户重新进入后不重复提问，能恢复环节、主理和摘要 |

业务口径：会话记忆保存“聊到哪里、已经确认了什么”，不是完整聊天记录的无边界复制。

### 4.2 资产与版本能力

| 工作项 | 代码位置 | 交付要求 |
| --- | --- | --- |
| 资产服务 | `zhiyin-business/zhiyin_business/services/asset.py` | 读取报告/方案/计划，保存资产版本，发布资产变更事件 |
| 版本规则 | `AssetVersion` + `AssetRepository` | 首版为 1，后续严格递增；记录依赖画像字段和版本差异 |
| 影响面传播 | `policies/impact.py` + `AssetService.propagate` | 只处理依赖命中字段的资产，未命中资产不得升版本 |
| 影响面 Worker | `zhiyin-business/zhiyin_business/workers/impact.py` | 消费画像字段更新事件，幂等调用资产传播 |
| E2E 验收 | `tests/e2e/test_main_path.py` | 画像变化只更新受影响资产，版本单调，diff 可解释 |

业务编排负责人负责确定“哪些字段影响哪些业务结论”；数据能力负责人负责依赖表达、版本一致性、落库、事件和可追溯性。

### 4.3 工作台与功能块的数据能力

| 工作项 | 代码位置 | 交付要求 |
| --- | --- | --- |
| 工作台聚合 | `zhiyin-business/zhiyin_business/services/workspace.py` | 聚合画像、报告版本、方向方案、行动计划、行为和会话记忆；只读、不触发重算 |
| 报告全文 | `zhiyin-business/zhiyin_business/services/function.py` | 只读已有资产版本，不重新生成 |
| 日历 | `FunctionService` + `ObjectStoreGateway` | 支持关键节点登记和查询，使用 ETag 条件写避免并发覆盖；规划师写、教练读 |
| 成就 | `FunctionService` + 行为数据 | 只允许行为日志驱动解锁，不因登录或浏览解锁 |
| 跟踪时间线 | `FunctionService` + 行为/事件数据 | 返回提醒、预警、节点完成、复盘等时间线数据 |

### 4.4 第一期 Redis 基础能力

第一期 Redis 采用“单 Redis 实例 + 逻辑分库 + 强制 Key 前缀”。逻辑分库用于降低不同用途的键冲突和误操作范围，但不是权限隔离，也不能代替 Key 命名规范。

完整实施口径见[《职引 · 第一期 Redis 分库策略》](../02-架构与设计/职引-第一期Redis分库策略.md)；本节只保留排期摘要。

| 逻辑库 | 用途 | Key 前缀示例 | 默认 TTL 原则 |
| ---: | --- | --- | --- |
| DB 0 | 通用应用缓存 | `zhiyin:{env}:cache:*` | 5–60 分钟，必须可重建 |
| DB 1 | 游客/登录临时会话 | `zhiyin:{env}:session:*` | 30 分钟–7 天，按会话类型配置 |
| DB 2 | 调度、延迟任务、冷却期 | `zhiyin:{env}:schedule:*` | 执行时间 + 安全缓冲 |
| DB 3 | 限流、幂等、短期去重 | `zhiyin:{env}:guard:*` | 限流窗口或幂等保留期 + 缓冲 |
| DB 4 | 采集任务状态与原始快照缓存 | `zhiyin:{env}:crawl:*` | 原始内容 1–24 小时，任务状态按批次保留 |
| DB 5 | 知识检索/RAG结果缓存 | `zhiyin:{env}:knowledge:*` | 10 分钟–24 小时，知识版本变化时失效 |
| DB 6 | 向量同步检查点与短锁 | `zhiyin:{env}:vector-sync:*` | 锁 5–30 分钟，检查点按同步策略配置 |
| DB 15 | 本地自动化测试专用 | `zhiyin:test:*` | 用例结束清理；不得连接共享或生产实例 |

第一期交付：

- 使用异步 Redis 客户端，通过 `CacheGateway` 等既有契约访问。
- 连接信息进入 `Settings`/环境变量，业务 Service 不持有 Redis Client。
- 每个适配器固定使用自己的逻辑库，业务代码不得运行 `SELECT` 切库。
- Key 格式统一为 `zhiyin:{env}:{domain}:{entity}:{id}`；不同逻辑库即使允许同名键，也不得依赖同名覆盖或省略前缀。
- 所有缓存键明确 TTL；禁止创建无期限且无人治理的临时键。
- Redis 故障时，可重建缓存允许降级；涉及限流、幂等和调度的失败策略必须显式测试。
- 当前 Redis Cluster 仅支持 DB 0；未来迁移 Cluster 时，逻辑分库改为独立实例或命名空间，业务调用接口不变。

### 4.5 第一期公共知识与采集最小链路

| 工作项 | 交付要求 |
| --- | --- |
| 数据源登记 | 为每个来源记录名称、授权/公开性、用途、更新频率、责任人和下架方式 |
| 采集实现 | 优先使用公开 API、开放数据或明确允许采集的页面；每个来源独立适配 |
| 数据解析 | HTML/JSON/文件转换为专业、职业、岗位、政策等标准结构 |
| 标准化 | 统一专业代码、职业编码、城市、学历、经验、技能等字段 |
| 去重更新 | 以来源唯一键或稳定指纹去重；内容变化才生成新版本 |

| 下架能力 | 能按来源、唯一键和版本停用或删除采集结果 |

第一期不得为了演示绕过登录、验证码或站点限制。遇到禁止采集、风控或授权不明确时停止该来源，并切换到官方开放数据、授权接口或人工导入。

## 五、M3：真实存储、采集管线与知识库

M3 将本地/内存实现替换为真实数据基础设施，不改变业务调用接口。

### 5.1 M3 启动前必须确定的事项

下列十项已于 2026-09-16 在《职引-M3启动依赖与决策登记表》中完成决策，M3 基础设施选型
冻结已经解除；仍未完成的业务表清单、迁移与 Repository 契约评审继续作为各自工作的开工门槛，
不得为了联调把尚未实现的真实 Repository 标记为 `wired`。

1. 业务权威库：复用 PAMI MySQL，使用独立库 `zhiyin_service` 与独立最小权限账号。
2. 向量库：独立 PostgreSQL 16+ + pgvector 0.7+，数据库 `zhiyin_vector`。
3. Embedding：调用 PAMI 模型服务，统一 1024 维，并保存模型版本。
4. 模型切换：新旧版本隔离，验证后重建/切换，不跨空间检索。
5. 混合检索：采用 RRF。
6. 向量同步：实时事件 + 补偿扫描；具体 Worker 待实现。
7. HNSW：`m=16`、`ef_construction=64`。
8. 备份恢复：按登记表中的 RPO/RTO 分级执行。
9. 检索日志：按登记表保留并脱敏。
10. RLS：M3 不启用，M4 再评估；应用层仍必须做用户隔离。

### 5.2 真实数据库

| 工作项 | 代码位置/交付 |
| --- | --- |
| ORM 模型 | 补齐 `zhiyin-infrastructure/.../persistence/models.py` 中的核心表模型、约束和索引 |
| 事务管理 | 实现 `SqlAlchemyTransactionManager.begin()`，明确提交、回滚和异常语义 |
| Repository 实现 | 为七类 Repository 提供真实数据库适配，方法签名与本地实现完全一致 |
| 数据库迁移 | 建立可重复执行、可回滚的 schema migration 和版本记录 |

### 5.3 Redis 生产升级、对象与生命周期

- 在第一期逻辑分库基础上补 Redis 高可用、连接池、认证/TLS、监控、容量、持久化与故障切换。
- Redis 缓存只承载可重建数据，继续落实 key、TTL、失效和穿透保护。
- 若采用 Redis Cluster，统一迁移到 DB 0，并以独立实例/命名空间 + Key 前缀替代逻辑分库。
- 原始采集响应设置短生命周期，到期可自动清理。
- 用户上传原件进入对象存储，数据库只保存对象键、哈希、归属和元数据。
- 明确公共知识、个人数据、日志、缓存和向量的保留周期。

## 九、统一完成定义（Definition of Done）

每项数据能力合并前至少满足：

1. 契约、实现、装配和测试四处完整，不以“文件存在”代替完成。
2. 正常、空数据、重复调用、用户隔离、异常回滚均有测试。
3. 所有写操作明确幂等键、事务边界和事件语义。
4. 数据带来源、版本、时间和必要的 trace id。
5. 不引入跨层依赖，不把业务规则写进 Repository。
6. 不使用未经授权的真实个人数据或外部受限内容。
7. 相关阶段门禁与自动化测试通过。

常用验证命令：

```bash
cd zhiyin-src/template
python -m pytest -q
python -m ruff check .
python scripts/export_openapi.py --check
python -m zhiyin_boot --check --phase=2
python -m zhiyin_boot --check --phase=3
python -m zhiyin_boot --check --phase=4
```

执行时只运行当前目标阶段对应的门禁；后续阶段未开始时失败属于预期，不得通过伪装 `wired` 或保留 skeleton 绕过。
