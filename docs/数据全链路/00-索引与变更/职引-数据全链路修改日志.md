## 十六、2026-09-19 15 维呈现口径定案：只给证据等级，不给分值（本轮追加）

本节记录一个**冻结契约变更**及其依据。触发问题是"为什么那批可视化 CSS 会被删掉"，查到底后发现根因不是"没有预留接口"，而是**契约里没有分数字段、当年前端只好自己编**。拍板结果见《业务口径决策记录》**决策 17**。

### 16.1 事实核对（先摆证据，再定口径）

| 问题 | 核对结果 |
| --- | --- |
| 15 维有没有契约？ | **有**。`zhiyin_kernel/assets.py::ReportDimensionGroup`（`SELF-PORTRAIT`/`JOB-MARKET`/`DECISION-RISK`）与 `ReportDimensionItem`；`Report.dimensions` 是其列表 |
| 运行期真的产出吗？ | **真的**。查容器内 MySQL `report.payload`：1 份报告、3 组、**6 + 5 + 4 = 15 条**，每条带 conclusion 与 evidence |
| PRD 要求什么？ | `FR-DIAG-001`（P0）："输出自我画像 6 维 / 职业环境 5 维 / 决策与风险 4 维，**每维有结论与证据引用**"——**没有分值要求** |
| 契约里有分值吗？ | **没有**。`ReportDimensionItem` 只有 `index/name/tag/conclusion/evidence`；`Verdict` 只有 `title/summary` |
| 那被删的样式在渲染什么？ | **编造的分数**。旧模板 `radarTarget = [82, 82, 78, 80, 75, 76]`、`matchScore` 取自 `agents.analysis?.matchScore`（前端 store 臆造）、`.ov-ring` 用 `--score: matchScore * 3.6deg` |
| 设计要求呢？ | 《前端改版需求说明》§2「**15 维热力图或雷达图**」；该文件 §1 自己也写了"若实现新界面需要新数据，按 §9.3 提出"——即规定了正确走法：**先提数据需求、定契约，再实现**，而不是前端编数字 |

**结论**：缺的不是"接口"，是**一个数值轴**；而 PRD 从未要求该数值轴。所以正确解法不是补分数字段，而是换一个**报告能自证**的轴。

### 16.2 定案内容

1. **新增内核枚举** `zhiyin_kernel/enums.py::DimensionEvidenceLevel`（英文值 + 中文注释，沿用 `PlanRole` 范式）：
   `confirmed`（字段或检索证据直接支撑、可溯源）/ `partial`（有支撑但证据链不完整）/ `pending`（有线索未确认）/ `missing`（无任何证据）。
2. **收紧冻结字段**：`ReportDimensionItem.tag` 由自由字符串改为该枚举。实测模型原本产出 **11 种措辞**（已确认/待验证/未定义/缺失/待确认/部分匹配/无依据/严重不足/未知/低/未建立），既无法上色，又把"证据够不够"和"这一维好不好"混在一句里。
3. **模型受强制约束**：`output_contracts.json` 的 `json_schema` 为空，`loop.py::_output_schema` 回落到 `model_json_schema()`，因此枚举自动进到发给模型的 Schema（实测 `$defs.DimensionEvidenceLevel.enum` 已生效）。
4. **提示词补四档语义**：`services/loop.py::_STAGE_DUTIES[DIAGNOSE]` 明确写出四档判据，并强调"tag 只表示证据够不够，好坏写在 conclusion 里"。
5. **前端**：报告页新增「15 维证据覆盖」热力图（等级色块 + 悬停出结论与证据 + 四档计数）；四档中文名按既有 `ROLE_LABELS` 范式在前端映射；明细列表的 tag 也改走等级中文名。
6. **不做雷达图**：需求写的是"热力图**或**雷达图"，选热力图即在授权内；雷达半径必须是数值，用四级等级硬撑会制造假精确。

### 17.5 D2 报告加「个人画像」——而且是**冻结快照**（原记的 B 不成立）

**定案**：`Report` 增加 `profile_snapshot: list[ProfileField]`——`ProfileField` 已是内核形状，**不需要新造**。②诊断生成报告时把**当次所用画像**冻结进去（构造点 `orchestrator.py` 里 `profile` 变量本来就在手边，正是本次诊断用的那一份）；`mappers.report_full_text_view` 在快照非空时追加 `profile` 章节；前端渲染为「本版本生成时的画像快照」并显示生成日期。旧报告该字段为空 → 不生成章节，**向后兼容、无需数据迁移**。

**顺序**：画像章节放在**最后**，与 §4.4 的枚举顺序（"15 维全景、方案、行动计划、个人画像"）一致；目录与正文由同一个 mapper 产出，天然同步。

**为什么"快照"是这件事的关键**：报告是版本化只读资产、画像是活状态。实时读会让用户在 v1 报告里看到今天的画像，与工作台对不上——这正是原记里识别出的风险，只是原记的结论（不做画像）选错了方向。

**改动面**：`zhiyin-kernel/zhiyin_kernel/assets.py`（加字段 + 文档串；顺手确认 `blackboard.py` 只依赖 `enums`，不成环）、`business/services/orchestrator.py`（填快照）、`api/dto/mappers.py`（追加章节）、前端 `ReportPage.vue`（`profileSnapshot` / `profileSnapshotAt` / 字段名译自 `copyBundle` / 值格式化沿用 `ProfileFields` 口径 / 加入 `RENDERED_IDS`）。

**新增守卫**：`test_report_carries_a_frozen_profile_snapshot` —— 生成报告后断言快照非空；**随后给画像新增一个字段，再读已存的那一版报告，快照必须不变**；并断言报告正文里有 `profile` 章节且字段来自快照。这条测试锁的正是"冻结"这个语义，而不只是"有个字段"。

**契约影响**：`Report` 加了字段（`extra="forbid"` 下属契约变更，但纯增量、有默认值）；`ReportFullTextView.sections` 是 `list[dict[str, Any]]`，所以 **OpenAPI 快照与前端生成类型都没有变化**（实测 `export_openapi.py --check` 一致）。

**门禁**：`pytest` **451 passed / 1 skipped**；Ruff 通过；OpenAPI 一致；前端 `typecheck` / `check:api` / `build` 通过；新 CSS 守卫无需新样式（复用既有 `.rp-block`/`.rp-item` 等类，故 0 新增）。

### 17.6 D9 能力池改由 bootstrap 下发（原记认为的两个形状难点，有一个不存在）
