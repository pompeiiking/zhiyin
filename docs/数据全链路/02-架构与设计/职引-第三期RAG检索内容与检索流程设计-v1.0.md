## 一、设计结论

第三期检索采用“业务检索计划 + 多路召回 + 证据包”的方式，而不是把用户原话直接扔给一个 RAG 应用：

```text
用户输入 + 当前环节 + 黑板活状态 + 已有资产
  → 判断本轮是否需要检索
  → 生成结构化检索计划
  → 权限、时效和知识域预过滤
  → 关键词召回 + API Embedding 向量召回
  → RRF 融合
  → 业务过滤、去重、必要时 API Rerank
  → 回 MySQL 补全权威详情
  → 形成带来源、版本和有效期的证据包
  → 注入对应环节的结构化产出
  → 保存引用与检索元数据
```

核心规则：

1. **先判断任务，再检索**：检索服务必须知道当前是采集、诊断、决策、行动还是复盘，不能把五个环节用同一套查询处理。
2. **事实与用户状态分开**：公共知识回答“外部世界是什么”，个人数据回答“用户现在是什么状态”，二者在证据包中分区，不能互相覆盖。
3. **MySQL 是权威事实源**：ES 和 pgvector 只负责召回；命中后必须回 MySQL 补齐当前版本、状态和权威字段。
4. **引用必须可追溯**：进入模型上下文的公共事实必须带 `source_id`、来源地址、更新时间、版本和片段定位。
5. **模型不得补事实**：没有检索证据时，生成模型只能说明缺少依据、提出澄清或给方法性建议，不能编造岗位要求、政策、时间节点或行情数字。
6. **降级必须显式**：Embedding API、关键词通道或 Rerank API 故障时记录降级通道；两路召回均不可用时返回“无可用证据”，不能伪装为检索成功。
7. **不新增向量命名空间**：沿用已冻结的 `theory`、`occupation`、`jd`、`report`、`memory`、`resume` 六个空间；专业、行业、政策和时间窗口用 `content_type` 在既有公共空间内区分。

## 二、范围与协作边界

### 2.1 本文负责

- 知识库应该包含哪些内容；
- 每类内容的结构、切片单位、元数据、版本和时效；
- 五环节分别何时检索、检索哪些知识域、如何构造查询；
- 候选结果如何过滤、融合、补全和形成证据包；
- 检索失败、无结果、过期结果和冲突结果的业务处理；
- 检索质量评测集、指标和验收口径；
- 与 RAG 技术方案负责人的输入输出边界。

### 2.2 本文不负责

- 选择 LangChain、LlamaIndex 或其他 RAG 框架；
- 决定模型供应商、模型价格和 API 配额；
- PAMI RAG Engine 内部的部署、扩缩容和进程结构；
- ES、pgvector、Kafka、Redis 的容量计算和运维方案；
- 修改冻结的 Port、DTO、公开 API 或数据库语义；
- 设计新的前端页面或流式接口。

如技术方案需要修改 `KnowledgeGateway`、`SearchGateway`、`VectorGateway`、公共 DTO 或六个命名空间，必须先做契约评审，不能由实现方在代码中临时扩签名。

### 2.3 与 RAG 技术方案负责人的交付关系

| 本文提供 | 技术方案需要给出 |
| --- | --- |
| 六个内容域和字段要求 | 这些内容如何映射到 PAMI 知识库、ES 索引和 pgvector 表 |
| 五环节检索计划 | 查询编排由哪个组件执行、如何并发和超时 |
| 权限、版本、时效过滤规则 | 平台侧如何实现过滤与权限回查 |
| RRF、去重和证据包规则 | 具体组件、调用顺序、错误码和可观测性 |
| API-only 模型约束 | Chat、Embedding、Rerank API 的接入、熔断、配额和密钥管理 |
| 评测集与指标 | 自动评测流水线、基准报告和回归门禁 |

## 三、已冻结基础口径

以下结论来自现有架构与 M3 决策，本设计直接继承，不重新拍板：

| 项目 | 冻结口径 |
| --- | --- |
| 业务权威库 | PAMI MySQL 实例中的职引独立库 `zhiyin_service` |
| 向量库 | 独立 PostgreSQL 16 + pgvector，数据库 `zhiyin_vector` |
| 全文检索 | 复用 PAMI Elasticsearch |
| 向量维度 | 1024 |
| 向量索引 | HNSW，`m=16`、`ef_construction=64` |
| 融合算法 | RRF，当前决策常量 `k=60` |
| Embedding | 经 PAMI 模型服务/API 调用，不自建、不直连本地模型 |
| 模型切换 | 以 `model_version` 隔离；换模型后全量重建索引，不跨向量空间检索 |
| 向量命名空间 | `theory` / `occupation` / `jd` / `report` / `memory` / `resume` |
| 检索回源 | 命中 ES/pgvector 后必须回 MySQL 补全权威详情 |
| 检索日志 | 只存元数据和 `query_hash`，不保存查询原文，保留 180 天 |
| 租户隔离 | M3 不启用 RLS；SDK 强制注入 `org_id`，禁止无组织过滤的私有数据检索 |
| 流式接口 | 职引第三期不因此新增 SSE/WS；如调用 PAMI 流式接口，由适配器收敛为现有业务契约 |

### 3.1 API-only 模型约束

第三期运行环境中：

- Chat 模型通过 PAMI Agent/Model API 调用；
- Embedding 通过 PAMI 模型回调 API 调用；
- Rerank 若启用，也必须通过平台模型 API 调用；
- 模型密钥、组织 ID、模型 ID、应用 API Key 只从运行配置注入，不进入代码、知识数据、日志和 Git；
- 本地哈希向量、固定结构化结果和 Demo 知识只允许出现在测试环境，运行报告必须标记为 Mock；
- 没有真实模型凭据时，Embedding 与 VectorSync 继续保持未装配，不得用 Mock 向量冒充第三期完成。

## 四、检索内容总设计

### 4.1 内容域总表

| 向量命名空间 | 内容类别 | 公共/私有 | 权威来源 | 主要使用环节 |
| --- | --- | --- | --- | --- |
| `theory` | 职业咨询理论、方法卡、使用边界、解释模板 | 公共 | 理论卡与人工评审知识 | ①②③④⑤ |
| `occupation` | 专业、职业、行业、能力要求、发展路径、一般政策 | 公共 | 学职平台、公开权威目录、人工审核资料 | ①②③ |
| `jd` | 招聘岗位、招聘公告、报名/网申时间窗、岗位实时要求 | 公共或组织私有 | 获准招聘来源、组织内部岗位 | ②③④⑤ |
| `report` | 用户诊断报告、方向方案、行动计划的可检索片段 | 私有 | MySQL 资产当前版本 | ②③④⑤ |
| `memory` | 会话摘要、阶段结论、用户确认和未决问题 | 私有 | MySQL 会话记忆 | ①②③④⑤ |
| `resume` | 简历、项目、作品、教育与经历片段 | 私有 | 用户上传与解析结果 | ①②③④ |

现有第一期本地 `profession` 内容在第三期归入 `occupation`，并设置 `content_type=major`；不新建 `profession` 向量空间。政策按用途归类：一般职业/就业政策进入 `occupation` 且 `content_type=policy`，具体招聘公告和报名窗口进入 `jd` 且 `content_type=announcement` 或 `timeline`。

### 4.2 所有可检索内容的共同字段

下表是内容治理所需的逻辑字段。具体落到现有 MySQL 模型、ES document 或 pgvector `metadata` 的方式由技术方案确定；它不是新增公共 DTO 的授权。

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `document_id` | 是 | 权威文档 ID，跨索引稳定 |
| `chunk_id` | 是 | 分片 ID，建议由 `document_id + section_key + chunk_index` 稳定生成 |
| `namespace` | 是 | 六个冻结命名空间之一 |
| `content_type` | 是 | `theory_card`、`major`、`occupation`、`industry`、`policy`、`jd`、`timeline`、`report_section` 等 |
| `title` | 是 | 人可读标题 |
| `content` | 是 | 供召回和模型引用的片段正文 |
| `source_id` | 是 | 数据源台账 ID 或私有资产 ID |
| `source_url` | 公共内容必填 | 可追溯来源；无公开 URL 时记录内部来源标识 |
| `source_level` | 是 | 来源可信等级，见 §4.4 |
| `version` | 是 | 权威内容版本 |
| `content_hash` | 是 | 幂等同步与变更识别 |
| `status` | 是 | `reviewing` / `enabled` / `disabled` / `expired` |
| `effective_at` | 时效内容必填 | 生效时间 |
| `expires_at` | 时效内容按需 | 失效时间 |
| `fetched_at` | 外部内容必填 | 最近采集时间 |
| `reviewed_at` | 公共内容必填 | 最近人工/规则审核时间 |
| `org_id` | 私有内容必填 | 组织隔离；公共内容为空 |
| `user_id` | 用户私有内容必填 | 用户隔离，不作为公共检索条件 |
| `model_version` | 向量记录必填 | Embedding 模型版本 |
| `language` | 是 | 当前为 `zh-CN`，为后续多语预留 |
| `tags` | 建议 | 同义词、技能、地区、行业等检索增强标签 |
| `section_key` | 建议 | 片段在原文中的结构位置 |

### 4.3 六个内容域的具体内容

#### 4.3.1 `theory`：理论与方法知识

应收录：

- 帕森斯、霍兰德 RIASEC、能力三核、舒伯、职业锚；
- CD 发展状态、三叶草；
- CASVE、决策平衡单、Vroom；
- SMART、执行意图、计划性偶发；
- 班杜拉自我效能等复盘理论；
- 每个理论的适用环节、适用问题、输入条件、推理步骤、输出含义和禁止误用边界。

每张理论卡至少拆成以下逻辑小节：

1. 理论定义；
2. 职引中的使用场景；
3. 所需输入；
4. 推理步骤；
5. 允许形成的结论；
6. 不允许形成的结论；
7. 示例与反例；
8. 来源和版本。

不能只存“理论名称 + 一句话摘要”。诊断和决策需要的是可执行的方法骨架和边界，否则模型仍会自由发挥。

#### 4.3.2 `occupation`：职业世界公共知识

应收录：

- 专业代码、专业名称、核心课程、培养能力、常见去向；
- 职业编码、职业名称、工作任务、知识/技能/能力要求；
- 行业分类、行业链条、典型岗位族和发展路径；
- 学历、证书、地域、工作方式等常见进入条件；
- 经审核的一般就业政策、行业规范和公共指导信息；
- 职业人物案例中的事实性路径，不把个案包装成普遍结论。

推荐 `content_type`：

```text
major | occupation | industry | skill_requirement | career_path | policy | case
```

涉及薪资、需求量、增长率等行情数字时，必须同时保存地区、统计口径、样本时间和有效期；缺少任一项时只能作为背景线索，不能作为确定性结论。

#### 4.3.3 `jd`：岗位与时间窗口

应收录：

- 岗位标题、岗位族、公司/组织、地区和工作方式；
- 职责、硬性要求、技能要求、经验要求、加分项；
- 招聘批次、报名/网申开始与截止时间；
- 来源、发布时间、更新时间和失效时间；
- 经审核的组织内部岗位或导师提供岗位。

推荐 `content_type`：

```text
jd | announcement | timeline | internship | campus_recruitment | internal_role
```

JD 默认是高时效内容。已过截止时间、来源下架、连续复核失败的记录必须标记 `expired`，不得作为“现在可以申请”的证据；历史 JD 可保留用于要求分析，但要明确标记为历史样本。

#### 4.3.4 `report`：用户资产片段

可检索资产包括：

- 15 维诊断中的单一维度结论与证据；
- SWOT 的单项；
- 用户已认领的差距；
- 主攻/平行/保底方案及取舍依据；
- 行动计划的阶段、里程碑和任务；
- 历史版本中发生变化的片段。

切片必须保留 `asset_type`、`asset_id`、`asset_version`、`section_key` 和依赖的画像字段。默认只召回当前有效版本；做变化解释时才允许显式检索历史版本。

#### 4.3.5 `memory`：跨会话记忆

应收录：

- 用户亲自确认的事实和偏好；
- 每个环节已达成的结论；
- 尚未解决的问题和待确认假设；
- 用户作出的可撤回选择；
- 最近行动与复盘结论；
- 会话结束后的结构化摘要。

不得把模型猜测直接写成用户事实。记忆项需要区分：

```text
confirmed_fact | user_preference | decision | open_question | hypothesis | stage_summary
```

`hypothesis` 只能帮助生成下一次澄清问题，不能参与确定性匹配结论。

#### 4.3.6 `resume`：简历与作品证据

按原子经历切片：

- 教育经历；
- 工作/实习经历；
- 项目经历；
- 作品与成果；
- 技能与证书；
- 自我描述。

每个片段要保留时间范围、角色、行动、结果、技能标签和原文定位。解析模型通过 API 调用，但解析结果只有经 schema 校验并保留原文定位后才能进入检索；模型推断出的技能要标记 `inferred=true`，不能与用户原文混为一谈。

### 4.4 来源可信等级

| 等级 | 来源 | 使用规则 |
| --- | --- | --- |
| A | 政府、官方目录、组织正式公告、用户本人确认的数据 | 可作为主要事实证据 |
| B | 平台公开结构化数据、经审核的机构资料 | 可作为主要证据，需保留采集时间 |
| C | 企业招聘页、职业人物案例、公开课程材料 | 可作辅助证据，涉及普遍性结论时需交叉验证 |
| D | 未审核转载、论坛、自媒体、模型生成内容 | 不进入生产知识库；只能进入待审区 |

同一事实存在冲突时优先级为：用户当前确认值或组织内部事实 > A > B > C。时间敏感事实还要优先使用更新时间更近且未过期的版本。

## 五、内容切片与索引规则

### 5.1 切片原则

1. 一个片段只表达一个可独立引用的事实或方法步骤。
2. 标题、章节路径和关键实体必须随片段一起索引，不能只嵌入孤立正文。
3. 表格按行或同一语义组转成“字段名：字段值”，避免列头丢失。
4. 时间窗口、适用地区、主体和例外条件必须与结论在同一片段中。
5. 私有资产按业务结构切片，不按固定字符数粗切。
6. 内容更新后使用 `content_hash` 幂等覆盖；旧版本保留策略由资产规则决定，不能和当前版本混检。

### 5.2 各内容域的推荐切片单位

| 内容域 | 首选切片单位 | 建议长度 | 重叠 |
| --- | --- | --- | --- |
| 理论卡 | 一个方法步骤/边界/示例 | 300～600 中文字符 | 同一小节 50～100 字 |
| 专业/职业 | 一组要求或一个发展阶段 | 300～700 字 | 共享标题与实体标签，不机械重叠 |
| JD | 职责、硬性要求、加分项、时间窗分别成片 | 150～500 字 | 不跨字段混切 |
| 报告 | 一个维度/一条差距/一个方案依据 | 150～500 字 | 不重叠 |
| 会话记忆 | 一个确认事实或一次阶段摘要 | 100～400 字 | 不重叠 |
| 简历 | 一段教育/项目/工作经历 | 150～600 字 | 保留经历标题和时间 |

长度是内容治理初值，不是代码常量。正式阈值应放入配置，并由固定评测集校准。

### 5.3 索引文本组成

Embedding 输入不直接使用裸 `content`，建议组合为：

```text
[内容类型] {content_type}
[标题] {title}
[实体/标签] {normalized_entities + tags}
[章节] {section_path}
[正文] {content}
[适用范围] {region / effective_at / expires_at / stage}
```

不得把 `user_id`、手机号、身份证等标识拼入 Embedding 文本。私有内容隔离通过过滤字段完成，不通过把身份信息嵌入向量完成。

## 六、五环节检索内容设计

### 6.1 总体矩阵

| 环节 | 检索目的 | 主要知识域 | 输出给业务的证据 |
| --- | --- | --- | --- |
| ① 采集建模 | 理解用户表述、解析简历、选择下一条追问 | `resume`、`memory`、`theory`、必要时 `occupation` | 已知事实、冲突信息、画像缺口、追问依据 |
| ② 诊断匹配 | 比较用户现状与目标要求 | `occupation`、`jd`、`resume`、`report`、`theory`、`memory` | 目标要求、用户证据、差距、理论解释 |
| ③ 决策 | 比较多个方向的适配性、代价和可达性 | `occupation`、`jd`、`report`、`resume`、`memory`、`theory` | 选项事实、用户偏好、约束、取舍依据 |
| ④ 行动 | 找到当前可执行机会和时间窗口 | `jd`、`report`、`memory`、必要时 `occupation`、`theory` | 截止时间、任务前置、最小动作、风险提醒 |
| ⑤ 复盘校准 | 判断停滞来自执行、动机还是方向 | `memory`、`report`、必要时 `jd`、`resume`、`theory` | 历史承诺、实际进展、外部变化、归因线索 |

### 6.2 ① 采集建模

默认不做大范围公共检索。流程是：

1. 读取画像活状态和缺口；
2. 检索 `memory`，避免重复询问用户已确认的信息；
3. 用户上传简历时检索 `resume` 的原子经历，提取可支持画像字段的证据；
4. 只在需要解释测评/理论或识别专业、职业实体时检索 `theory` / `occupation`；
5. 输出“已知、冲突、未知”三类信息，下一问只针对最高优先级缺口。

禁止行为：不能因为职业库出现某岗位，就在采集阶段直接替用户确定方向。

### 6.3 ② 诊断匹配

诊断需要“双证据对齐”：

```text
用户侧证据：画像 + resume + memory + 历史 report
目标侧证据：occupation + jd
解释侧证据：theory
```

每条差距必须包含：

- `requirement_evidence`：目标要求来自哪条职业/JD；
- `current_evidence`：用户现状来自画像、简历或行为中的哪条证据；
- `gap_statement`：要求与现状的差值；
- `confidence`：证据是否充分；
- `theory_basis`：使用了哪个理论框架；
- `next_action`：让用户认领、补证或行动。

目标不明确时先检索职业族而不是具体 JD；目标明确后才检索具体岗位。不得用一条 JD 代表整个职业。

### 6.4 ③ 决策

对每个候选方向分别生成检索子任务，保证证据对称：

```text
选项 A：要求 / 机会 / 路径 / 风险 / 时间窗口
选项 B：要求 / 机会 / 路径 / 风险 / 时间窗口
选项 C：要求 / 机会 / 路径 / 风险 / 时间窗口
```

每个选项至少要有：

- 一条职业/行业事实；
- 一条岗位或进入要求事实；
- 一条用户适配证据；
- 一条现实约束或风险；
- 来源与更新时间。

若某选项证据明显少于其他选项，应标记“证据不足”，不能把检索量差异解释成该选项一定更差。

### 6.5 ④ 行动

行动阶段优先检索强时效数据：

- 当前仍有效的招聘公告和 JD；
- 报名、网申、考试、申请节点；
- 用户行动计划中的未完成任务；
- 与任务有关的前置条件和材料要求。

流程：

1. 从 `report` / `memory` 读取已选择方向和当前里程碑；
2. 用地区、时间窗、岗位族、学历/经验等硬约束过滤 `jd`；
3. 只把未过期且来源可核验的机会放入证据包；
4. 将证据转成今天/本周能完成的小任务；
5. 如果搜不到合适机会，返回“扩大条件/补齐材料/人工核验”的动作，不生成虚构岗位。

### 6.6 ⑤ 复盘校准

复盘先检索个人历史，不先检索外部知识：

1. 读取上次计划、承诺和截止时间；
2. 检索近期会话摘要、行为日志关联资产和历史差异；
3. 判断“任务太大、动机不足、外部条件变化、方向不匹配”中的候选原因；
4. 只有怀疑外部条件变化时才检索 `jd` / `occupation`；
5. 用 `theory` 提供归因和干预方法，但不让理论覆盖真实行为证据。

方向动摇时，复盘只输出“需要回到诊断/决策复核”的证据，不直接替代 ②③ 产出新方向。

## 七、检索查询构造

### 7.1 检索请求的逻辑输入

检索计划至少需要以下上下文：

| 输入 | 用途 |
| --- | --- |
| `stage` | 决定允许检索的知识域和证据要求 |
| `intent` | 区分了解、比较、验证、找机会、复盘等目的 |
| `user_input` | 当前问题原文，只用于本次处理，不写检索日志原文 |
| `profile_summary` | 只取与本轮相关的画像字段 |
| `path_focus` | 就业、考研、留学等路径焦点 |
| `target_options` | 目标职业、岗位、专业或方案候选 |
| `constraints` | 地区、时间、学历、经验、单位性质、截止日期 |
| `current_assets` | 当前报告、方案、计划的 ID 和版本 |
| `org_id/user_id` | 私有域权限过滤 |
| `trace_id` | 链路追踪 |

### 7.2 查询生成策略

采用“确定性模板优先，API 模型增强”的方式：

1. 先从结构化上下文生成基础查询；
2. 识别职业、技能、地区、学历、时间等实体；
3. 为多个目标生成独立子查询；
4. 可调用 Chat API 生成同义词和查询改写，但必须输出结构化结果；
5. API 改写失败时使用基础查询，不阻断检索；
6. 改写模型只能扩展表达，不能新增用户没有提供的硬约束。

查询示例：

```text
用户原话：我会 Python，想找后端实习，但不确定差什么

诊断查询：
- occupation：后端开发 实习 核心知识 技能 能力要求
- jd：Python 后端 实习生 要求 {地区} {当前时间}
- resume：Python 项目 后端 数据库 API
- theory：能力三核 差距诊断
```

```text
用户原话：产品和开发我到底选哪个

决策查询：
- occupation：产品经理 工作任务 能力要求 发展路径
- occupation：软件工程师 工作任务 能力要求 发展路径
- jd：产品经理 校招 {地区}
- jd：软件开发 校招 {地区}
- report/resume：用户兴趣 能力 价值观 现实约束
- theory：CASVE 决策平衡单 职业锚
```

### 7.3 过滤顺序

过滤必须在尽可能早的阶段执行：

1. `status=enabled`；
2. `namespace` 与 `model_version`；
3. 公共/私有权限、`org_id` 和 `user_id`；
4. 生效时间、失效时间；
5. 地区、岗位族、学历、经验等硬条件；
6. 当前资产版本；
7. 来源可信等级；
8. 召回和排序。

权限条件不得在召回后靠应用层“删一下”作为唯一保护，底层查询必须带过滤。

## 八、完整检索流程

### 8.1 流程总览

```text
① 接收业务上下文
  ↓
② Need-Retrieval 判断
  ├─ 不需要：只读黑板/权威资产
  └─ 需要：进入检索计划
  ↓
③ Query Plan
  ├─ 选择知识域
  ├─ 生成一个或多个子查询
  ├─ 生成权限/时效/业务过滤
  └─ 指定每域候选数与最终证据数
  ↓
④ 并行召回
  ├─ ES/BM25 关键词候选
  └─ Embedding API → pgvector 语义候选
  ↓
⑤ RRF 融合（k=60）
  ↓
⑥ 后处理
  ├─ 权限复核
  ├─ 过期/禁用过滤
  ├─ 文档级去重与片段多样性
  ├─ 来源可信度与时效校正
  └─ 可选 API Rerank
  ↓
⑦ MySQL 回源补全
  ↓
⑧ 证据包构建与上下文预算裁剪
  ↓
⑨ 业务产出模型 API 调用
  ↓
⑩ 结构化校验、引用核对、资产落库、日志记录
```

### 8.2 Need-Retrieval 判断

以下情况需要检索：

- 用户询问职业、专业、岗位、政策、行情、时间节点等外部事实；
- 诊断需要目标要求；
- 决策需要比较多个方向；
- 行动需要当前机会或截止时间；
- 需要引用理论依据；
- 需要从长简历、历史报告或跨会话记忆中找相关片段。

以下情况通常不需要外部检索：

- 只确认用户刚刚提供的信息；
- 只读取黑板中的结构化状态；
- 只记录用户选择或行为；
- 只询问一个画像缺口；
- 只执行确定性的环节路由和业务规则。

### 8.3 多路召回

每个子查询并行执行：

```text
关键词通道：规范化 query → ES/BM25 → 候选列表
向量通道：规范化 query → PAMI Embedding API → pgvector → 候选列表
```

初始建议每路候选数为最终 `top_k` 的 3 倍，最多 100 条，与当前实现保持一致。该参数必须配置化，并通过评测集校准。

### 8.4 RRF 融合

同一 `chunk_id` 在两路中的名次通过 RRF 合并：

```text
score(d) = Σ 1 / (60 + rank_channel(d))
```

RRF 分数只用于排序，不能解释为“匹配百分比”。向用户展示的匹配度仍按 PRD 定义为解释性分值，不直接暴露向量分数或 RRF 分数。

### 8.5 后处理

按以下顺序处理：

1. 去掉权限不符、过期、禁用、模型版本不符的命中；
2. 以 `document_id` 聚合，避免同一文档多个相邻片段占满结果；
3. 每个文档默认保留最相关片段，并按需要带一个相邻片段；
4. 保证候选来源多样性，避免一条来源垄断所有证据；
5. 对时效问题优先新版本，对理论问题优先已审核版本；
6. 如平台提供 Rerank API，对融合后的少量候选重排；
7. Rerank 不可用时直接使用 RRF 结果，并标记降级，不启用本地 Rerank 模型。

### 8.6 MySQL 回源

ES/pgvector 命中只表示“可能相关”。返回业务层前必须：

- 按 `source_id/document_id` 查询 MySQL 权威记录；
- 确认当前状态、版本、权限和失效时间；
- 用权威字段覆盖索引副本中的旧字段；
- 权威记录不存在或已禁用时丢弃该命中；
- 记录索引版本落后的观测事件，交同步任务修复。

### 8.7 上下文预算与证据包

证据包按“任务说明 → 用户事实 → 外部事实 → 理论依据 → 引用清单”组织，避免把未经区分的片段直接拼成大段 Prompt。

逻辑结构示例：

```json
{
  "stage": "diagnose",
  "question": "用户本轮要解决的问题",
  "user_evidence": [
    {
      "evidence_id": "resume:project-2",
      "fact": "完成过 Python API 项目",
      "source_type": "resume",
      "confidence": 0.9
    }
  ],
  "external_evidence": [
    {
      "evidence_id": "jd:backend-python#requirements",
      "fact": "岗位要求数据库与接口开发经验",
      "source_id": "jd:backend-python",
      "source_url": "https://example.invalid/job/1",
      "version": 3,
      "updated_at": "2026-09-18T00:00:00Z"
    }
  ],
  "theory_evidence": [
    {
      "evidence_id": "theory:ability-trinity#gap",
      "fact": "按知识、技能、才干区分差距",
      "version": 2
    }
  ],
  "retrieval": {
    "channels": ["keyword", "vector"],
    "degraded_channels": [],
    "model_version": "由平台配置提供"
  }
}
```

这是内部逻辑形状，不表示可以直接新增同名公共 DTO。实现时应优先复用现有 `KnowledgeHit` / `SearchHit.metadata`；若字段不足，先按冻结接口规则发起契约评审。

## 九、PAMI 接入下的两种检索路径

现有 PAMI 接口有两个重要约束：RAG API 的知识范围由 API Key 绑定的应用决定；当前 OpenAPI 不接受调用方裸向量，也不支持任意 metadata filters。因此技术方案可以在以下路径中选择，但必须满足本文的内容与隔离规则。

### 9.1 路径 A：职引自管检索，PAMI 提供模型 API

```text
职引 Query Plan
  → PAMI Embedding API
  → 职引 pgvector + PAMI ES
  → RRF/过滤/回 MySQL
  → 证据包
  → PAMI Chat/Agent API
```

优点：可实现六命名空间、`org_id`、版本、时效和复杂过滤，符合现有技术架构。

### 9.2 路径 B：按知识域发布 PAMI RAG 应用

```text
职引按 stage/namespace 选择 RAG 应用
  → 使用该应用绑定的 API Key 调 PAMI RAG
  → 接收上下文与来源
  → 职引侧做权限复核和权威回源
```

要求：

- 公共知识与用户私有知识不能绑定到同一个无隔离应用；
- 每个 API Key 的知识范围必须可审计；
- PAMI 返回必须包含足够的来源标识用于 MySQL 回源；
- 如果 PAMI 不能表达用户级权限、版本和时效过滤，则私有域不能直接走此路径；
- 不能把 `namespace` 文本拼进用户 query 冒充服务端隔离。

### 9.3 当前建议

第三期优先采用路径 A 作为主检索路径：它与现有 MySQL + ES + pgvector 架构、六命名空间和权限过滤一致；PAMI 负责模型 API 和平台能力纳管。路径 B 可用于公共知识问答试验，但只有在来源、权限和过滤能力验证通过后才能替代路径 A 的某一知识域。

该建议不替代技术方案评审；如果技术负责人选择其他路径，必须逐项说明如何满足本文的隔离、回源、时效、引用和降级要求。

## 十、降级与异常流程

| 异常 | 处理方式 | 用户侧口径 |
| --- | --- | --- |
| Embedding API 超时/限流 | 只用关键词通道；记录 `vector` 降级 | 可以继续，但不声称完成语义检索 |
| ES 不可用 | 只用向量通道 | 可以继续，精确关键词命中可能下降 |
| Rerank API 不可用 | 使用 RRF 顺序 | 不影响基本检索，不启本地模型兜底 |
| ES 与 pgvector 均不可用 | 返回无可用证据，停止事实型生成 | 明确提示暂时无法核验外部信息 |
| MySQL 回源失败 | 丢弃无法核验的命中；全部失败则按无结果处理 | 不展示未核验事实 |
| 结果全部过期 | 可作为历史样本，但不能作为当前机会 | 提示信息已过期并建议重新查询 |
| 不同来源冲突 | 同时保留并标明来源/时间，按可信等级排序 | 说明存在差异，不替用户隐藏冲突 |
| 私有权限不明确 | 拒绝检索 | 不跨用户、跨组织降级查询 |
| 查询无结果 | 放宽同义词或非权限过滤重试一次 | 仍无结果则提出澄清或人工核验 |
| 模型输出无引用/引用不存在 | 结构化校验失败，重试一次；仍失败则降级 | 不落库无来源的事实型产出 |

降级只能放宽召回方式、同义词或非关键条件，不能放宽 `org_id`、`user_id`、内容状态和权限边界。

## 十一、缓存、日志与隐私

### 11.1 缓存

- 公共知识查询可缓存 10 分钟～24 小时；
- 缓存键至少包含环境、知识域、查询哈希、过滤哈希、知识版本和模型版本；
- 私有检索缓存必须包含 `org_id`、`user_id` 和资产版本；
- 知识版本变化、来源下架、资产版本 +1 或权限变化时主动失效；
- Embedding 请求可按规范化文本哈希 + 模型版本缓存，禁止跨模型复用。

### 11.2 检索日志

按已定口径只记录：

- `trace_id`、`org_id`；
- `namespace`、通道、`top_k`；
- 命中的 `source_id`；
- 延迟、是否降级；
- `query_hash`；
- 模型版本和知识版本；
- 无结果、回源丢弃、过期过滤等统计。

不记录用户查询原文、简历正文、会话全文和模型密钥。模型调用的独立审计进入 `agent_call_log`。

### 11.3 隐私与安全

- 公共知识库不得写入用户画像、简历、报告和会话片段；
- 私有域检索必须同时满足组织和用户范围；
- Prompt 只注入完成当前任务所需的最小片段；
- 外部模型 API 的数据使用范围、留存和训练条款必须由平台侧确认；
- 日志、错误信息和指标不得包含个人原文；
- 来源内容中的提示注入文本视为不可信数据，只作为引用材料，不能改变系统指令和工具权限。

## 十二、检索质量评测

### 12.1 固定评测集结构

现有 `data/evaluation/retrieval_cases.json` 只有 4 条冒烟样例。第三期需要扩充为按环节分层的固定集，每条至少包含：

```json
{
  "case_id": "diag-backend-gap-001",
  "stage": "diagnose",
  "namespace": ["occupation", "jd", "resume", "theory"],
  "query": "后端实习需要什么，我还差什么",
  "context": {
    "path_focus": "employment",
    "region": "上海"
  },
  "expected_relevant_ids": ["occupation:backend", "jd:backend-intern"],
  "expected_excluded_ids": ["jd:expired-example"],
  "required_source_level": ["A", "B", "C"],
  "expected_degradation": null
}
```

评测集应覆盖：

- 五环节各不少于 20 条，首版至少 100 条；
- 同义表达、错别字、中英文技能名；
- 多目标比较；
- 地区、时间、学历等硬过滤；
- 过期 JD、禁用来源、版本切换；
- 公共与私有数据混合；
- 跨组织和跨用户越权负例；
- 单通道故障和完全故障；
- 无答案场景；
- 提示注入和恶意内容样本。

### 12.2 指标

| 指标 | 说明 |
| --- | --- |
| Recall@K | 标准相关文档是否被召回 |
| MRR / nDCG@K | 高相关证据是否排在前面 |
| 过滤准确率 | 过期、禁用、权限不符内容是否全部排除 |
| 引用有效率 | 引用是否能回到存在且启用的权威记录 |
| 证据覆盖率 | 事实型结论是否都有引用 |
| 新鲜度命中率 | 时效问题是否优先返回有效新版本 |
| 降级成功率 | 单通道故障时是否仍能返回可识别结果 |
| 越权命中数 | 必须为 0 |
| 检索延迟 | 关键词、向量、融合、回源各阶段 P50/P95 |
| 无依据生成率 | 模型是否生成证据包以外的外部事实 |

### 12.3 建议验收线

以下是第三期首版建议值，评审后写入动态配置或 CI 基准，不在业务代码中硬编码：

| 指标 | 建议门槛 |
| --- | --- |
| 公共知识 Recall@10 | ≥ 0.85 |
| nDCG@10 | ≥ 0.75 |
| 权限/禁用/过期过滤准确率 | 100% |
| 引用有效率 | 100% |
| 事实型结论证据覆盖率 | ≥ 95% |
| 跨用户/跨组织越权命中 | 0 |
| 单通道故障降级成功率 | 100% |
| 无依据生成率 | ≤ 2%，高风险事实为 0 |

不能以“API 返回 200”“向量库能搜到一条”或“人工看起来不错”代替检索质量验收。

## 十六、验收结论口径

只有同时满足以下条件，才能写“第三期 RAG 检索完成”：

1. 使用真实 API Embedding，不是哈希伪向量；
2. 生产知识内容通过来源、状态、版本和时效审核；
3. 至少关键词与向量两路中的主路径真实可用；
4. 命中后完成权限校验和 MySQL 权威回源；
5. 五环节的检索消费方已接入，不是只有底层组件；
6. 最终事实型产出带可追溯引用；
7. 降级、无结果和越权负例通过；
8. 固定评测集达到冻结门槛；
9. Phase 3 门禁通过；
10. 测试报告明确区分真实、Mock 和降级结果。

在真实模型凭据、知识内容或消费方接线缺任一项时，只能表述为“RAG 基础设施/流程骨架完成”，不能表述为“RAG 业务闭环完成”。
