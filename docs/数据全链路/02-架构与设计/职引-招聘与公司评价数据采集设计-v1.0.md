## 1. 结论先行

第一期以**学职平台 `xz.chsi.com.cn` 为专业、职业与职业发展内容的核心数据源**，但不把它误当作全部实时招聘和公司评价的来源。整体采用「三层供数」：

1. **权威基座**：学职平台的专业洞察、职业探索、职业人物/案例、微视频与就业指导内容，低频版本化更新；
2. **岗位事实**：官方招聘平台、企业官网及公开 ATS/API，按增量更新；
3. **公司体验**：用户主动提交且经脱敏审核的评价为主，第三方平台只做有授权的聚合信号，不复制原帖。

商业招聘站的公开页面可以作为受控补充，但必须逐站完成条款、robots、字段范围和保存期限评审。需要登录、验证码、设备签名或贡献内容后才能查看的数据，默认不自动采集。验证码或访问控制出现时立即停止，不做绕过。

## 2. 业务实际需要什么

| 业务场景 | 必要事实 | 时效 | 是否需要原文 |
| --- | --- | --- | --- |
| ② 诊断匹配 | 职业定义、技能/学历/经验要求、岗位样本分布 | 职业库季度；岗位周级 | 否，保留结构化要求和证据链接 |
| ③ 方向决策 | 城市/行业需求量、薪资区间、单位类型、趋势 | 周级或月级 | 否 |
| ④ 行动计划 | 网申/考试/宣讲/岗位截止时间 | 日级或周级 | 否，保留官方链接和截止时间 |
| ⑤ 复盘校准 | 岗位下架、窗口临近、资料过期 | 日级 | 否 |
| 公司体验 | 工作节奏、管理、成长、福利等维度的聚合信号 | 月级 | 否；原始评价仅短期隔离保存或不保存 |

系统不需要全网复制岗位和评论。P0 的验收目标是：针对用户的目标职业和城市，能返回**带来源、时间、样本量和置信度**的可解释事实。

## 3. 数据源分层与优先级

### 3.1 P0：优先接入

| 来源族 | 代表来源 | 用途 | 接入方式 | 更新建议 | 结论 |
| --- | --- | --- | --- | --- | --- |
| **学职核心源** | [全国大学生学业与职业发展平台](https://xz.chsi.com.cn/home.action) | 专业洞察、职业探索、职业案例、职业发展内容 | 公开页面/接口；逐栏目登记与适配 | 专业/职业季度；案例与课程月级 | **P0 核心来源** |
| 国内官方就业 | 24365、中国公共招聘网、地方人社/人才网 | 校招、公共招聘、招聘会、政策 | 公开页面/API，逐站适配 | 岗位每日/每周；政策每日检查 | 国内主来源 |
| 企业一方岗位 | 企业招聘官网 | 真实在招岗位和截止时间 | sitemap、RSS、公开 JSON 或低频 HTML | 6~24 小时 | 高可信 |
| 公开 ATS | Lever Postings API、Greenhouse/SmartRecruiters 公开 Job Board 接口 | 企业官网背后的结构化岗位 | 官方公开只读接口 | 6~24 小时，ETag/Last-Modified 优先 | 稳定补充 |
| 职业技能基座 | 国家职业分类、ESCO | 职业编码、职责、技能关系、跨语种别名 | 开放数据/API 或人工导入 | 季度检查、版本发布时更新 | 不等同于实时岗位 |
| 宏观事实 | 国家统计局、人社部公开报告 | 行业工资、就业规模、政策 | 官方文件/API，人工复核 | 月/季/年 | 报告背景证据 |

ESCO 提供开放的职业与技能分类、稳定 URI、下载文件和 Web API，适合作为技能图谱的国际补充，但中文本地化需要人工映射到国家职业分类。官方说明见 [ESCO API](https://esco.ec.europa.eu/en/use-esco/use-esco-services-api/esco-web-service-api) 和 [下载页](https://esco.ec.europa.eu/en/use-esco/download)。

学职平台的栏目边界：专业洞察和职业探索进入公共知识库；职业人物、微视频、就业指导课只保存内容索引和自编摘要；职业测评题目不采集，用户本人授权的测评结果才进入个人画像。核心业务优先级不等于无限制访问授权，自动任务上线前仍需确认版权声明、访问条款、频率与保存期限。

Lever 的公开 Postings API只返回公开职位并提供岗位 ID、地点、团队、工作方式、薪资等字段，适合按企业白名单接入；它不是跨企业搜索接口。官方文档见 [Lever Postings API](https://github.com/lever/postings-api)。

### 3.2 P1：条件接入

| 来源 | 条件 | 用途 | 默认状态 |
| --- | --- | --- | --- |
| 商业招聘平台公开岗位 | 服务条款/robots 允许，或取得书面授权；不需要登录/验证码 | 补足覆盖率、交叉验证薪资和技能 | `pending_review` |
| 招聘聚合 API | 明确展示、缓存、再分发、归属和删除条款 | 快速补充海外或远程岗位 | 逐源启用 |
| 工商/信用/投诉/裁判公开信息 | 仅使用官方公开接口/文件；禁止把争议事实直接推断为雇主评价 | 公司主体校验、合规风险证据 | 人工复核 |
| 公司评价商业数据 | 有数据许可、删除机制和用途限制 | 聚合评分、趋势 | 采购后启用 |

### 3.3 默认不自动采集

- 需要登录、扫码、付费或“贡献一条评价后解锁”的内容；
- 触发验证码、设备指纹或访问控制后仍需规避才能获取的内容；
- 匿名社区的用户名、头像、联系方式、精确时间地点等个人信息；
- 候选人简历、联系方式、申请记录和招聘者个人信息；
- 原始长评论、帖子、面经全文以及可反向识别个人的组合字段。

## 4. 公司评价策略

第三方“公司点评”不是可直接当事实使用的结构化数据，存在幸存者偏差、极端体验偏差、刷评和实体混淆。第一期采用下面的证据阶梯：

1. **L0 公司自述**：企业官网福利/制度，只能标记为 `company_claim`；
2. **L1 用户自愿评价**：职引用户主动提交，最小化采集、脱敏、同意用途、可撤回；
3. **L2 经授权聚合**：许可数据源的维度分、样本量、时间窗，不保存原帖；
4. **L3 公共风险事实**：官方公开的行政处罚、经营异常等，只描述事实，不自动推导“好/坏公司”；
5. **L4 网络讨论线索**：只供人工核查，不进入用户报告的确定性结论。

推荐聚合模型：

```text
CompanySignal {
  company_key, dimension, value, sample_size,
  time_window, evidence_level, source_id,
  source_url, fetched_at, expires_at,
  confidence, review_status
}
```

展示时必须同时呈现样本量、时间窗和证据级别；样本少于 5 条时不显示数值评分，只显示“样本不足”。不得根据单条匿名内容生成公司风险标签。

## 5. 统一采集契约

### 5.1 来源台账

每个适配器上线前必须登记：

```text
KnowledgeSource {
  source_id, name, base_url, acquisition,
  access_basis, allowed_scope, prohibited_fields,
  owner, parser_version, refresh_policy,
  raw_ttl, normalized_ttl, removal_method,
  status: pending_review | enabled | paused | disabled
}
```

`enabled` 是自动任务的硬门槛。没有明确 `allowed_scope`、负责人和下架方式的来源不得运行。

### 5.2 岗位规范模型

```text
JobPosting {
  id, source_id, source_item_id, source_url,
  title, company_key?, company_name?, location[], remote_mode,
  employment_type[], salary_min?, salary_max?, salary_currency?, salary_period?,
  education?, experience?, skills[], description_summary,
  published_at?, valid_through?, first_seen_at, last_seen_at,
  content_hash, parser_version, status,
  fetched_at, expires_at, review_status
}
```

规则：

- 主键为 `(source_id, source_item_id)`；没有稳定 ID 时才使用规范化 URL 哈希；
- `company_name` 只在许可允许和业务确有需要时保存，同时生成内部 `company_key` 做实体归一；
- 长 JD 不进入长期库，长期保存职责/要求摘要和技能结构；
- 薪资必须同时保存币种、周期和原始区间可信度，禁止把“面议”转换为 0；
- 所有事实必须可回到 `source_url`，且带 `fetched_at`。

## 6. 何时爬、爬什么、存多久

| 数据 | 触发方式 | 建议频率 | 原始响应 | 结构化数据 | 过期策略 |
| --- | --- | --- | --- | --- | --- |
| 学职专业/职业 | 版本探测 + 定时增量 | 季度全量；月级变更探测 | 默认不存；调试最长 24 小时 | 长期版本化 | 新版本并存，按代码/站内 ID 迁移 |
| 学职案例/课程索引 | 定时增量 | 月级 | 默认不存 | 元数据与自编摘要 12 个月 | 到期复核来源有效性 |
| 岗位发现列表 | 定时增量 | 6~24 小时；国内官方最低日级 | 1~6 小时 | 30~90 天 | 连续 2 次缺失标记疑似下架 |
| 岗位详情 | 新岗位、内容哈希变化、用户点开 | 按需 | 1~6 小时 | 有效期 + 30 天审计窗口 | 到期后 `expired`，不物理删统计摘要 |
| 招聘会/报名截止 | 定时增量 | 每日；临近 7 天加密到 6 小时 | 24 小时 | 截止后 1 年 | 转历史节点 |
| 公司聚合信号 | 批量窗口 | 月级 | 默认不存原文；必要时最长 7 天隔离 | 聚合值 12 个月 | 到期重算或隐藏 |
| 用户评价 | 用户提交 | 事件触发 | 脱敏后进入审核区 | 用户撤回前或政策期限 | 支持删除和重新聚合 |

调度采用带抖动的固定窗口，不以“随机行为模拟”规避检测。优先使用 `ETag`、`Last-Modified`、`updated_at`、分页游标和内容哈希减少请求。

## 7. 缓存、长期存储与索引

```text
Fetcher -> 原始隔离缓存(TTL) -> Parser -> Normalizer -> Validator
        -> Review -> Upsert(结构化事实) -> Index -> Evidence API
                    \-> Dead Letter + 告警
```

- **原始隔离缓存**：对象存储/Redis，按来源设置 TTL，加密、不可被业务检索；默认不保存。
- **结构化事实库**：MySQL/PostgreSQL，保存规范字段、来源、时间、版本和哈希。
- **统计快照**：按职业×城市×周聚合岗位数、技能频率、薪资分位，避免用户查询直扫明细。
- **检索索引**：只索引审核通过、未过期的结构化摘要；向量库不存原始受限文本。
- **下架索引**：按 `source_id`、`source_item_id`、`company_key` 支持禁用、重建和物理删除。

## 8. 调度与失败策略

来源状态机：

```text
pending_review -> enabled -> paused -> enabled
                     \-> disabled
```

一次任务必须具备 `run_id`、计划时间、游标、水位线、适配器版本和统计结果。失败处理：

- `429/503`：读取 `Retry-After`，指数退避，达到预算后暂停本轮；
- `401/403/验证码`：不重试，来源自动转 `paused` 并通知负责人；
- 字段缺失率或解析失败率突增：停止发布新数据，保留上一版可用快照；
- 内容哈希相同：只更新 `last_seen_at`，不产生新版本；
- 并发：同一来源一个分布式锁；跨来源可并行；
- 重跑：按 `(source_id, source_item_id, content_hash)` 幂等。

推荐首期计划：

| 任务 | 时间 | 说明 |
| --- | --- | --- |
| 官方/企业岗位发现 | 每日 02:00~06:00 分片 | 每源加稳定抖动，避免同刻突发 |
| 临近截止岗位刷新 | 每 6 小时 | 只刷新 7 天内到期的白名单岗位 |
| 下架确认 | 每日一次 | 连续缺失两次再置为 `expired` |
| 职业/技能版本探测 | 每月 1 日 | 只有版本变化才下载 |
| 公司信号聚合 | 每月 2 日 | 先脱敏与审核，再聚合发布 |

## 9. 质量与可观测性

每个来源至少上报：

- 请求成功率、`429/401/403` 数量、平均延迟；
- 抓取数、解析数、拒绝数、去重数、新增/更新/过期数；
- 关键字段完整率、薪资可解析率、时间可解析率；
- 数据新鲜度 P50/P95；
- 与昨日相比的数量突变、字段空值突变；
- 抽检通过率和用户报告中被引用次数。

发布门槛建议：关键字段完整率 ≥ 98%，解析拒绝率 ≤ 5%，抽检通过率 ≥ 95%。不达标的数据可进入隔离区，但不能进入用户报告。

## 10. 实验

### 10.1 核心源：学职平台

核心源实验代码位于 `experiments/xuezhi_data/xuezhi_experiment.py`，只读取无需登录的专业洞察和职业探索公开入口及列表接口：

- `GET /speciality/list.action`：专业代码、名称、学历层次、门类、专业类、满意度聚合；
- `GET /occupation/searchbyhy.action`：职业 ID、名称、类别、行业、公开简介；
- 两个入口页均返回 HTTP 200，页面 `meta robots` 为 `all`；站点根路径没有 `robots.txt`（实测 404）；
- 不登录、不读取个性化推荐/测评、不提交表单、不保存原始页面或接口响应。

2026-09-16 的单页低频实验中，源站报告专业总数 1778、职业总数 151；程序各规范化 5 条，共保存 10 条小样本，均带稳定来源 ID、详情链接、UTC 抓取时间和 SHA-256 内容哈希。结果见 `experiments/xuezhi_data/output/sample.json`。这证明公开入口的技术链路可行；生产调度仍需完成访问依据评审。

### 10.2 辅助源：公开岗位 API

实验选用 [Arbeitnow 公开 Job Board API](https://www.arbeitnow.com/blog/job-board-api)。官方页面说明该免费 API 无需 API Key，聚合多个 ATS 的公开岗位；它仅用于验证采集链路，不代表国内覆盖方案。实验遵守来源归属要求，每条记录保留原岗位 URL。

实验程序实现：

- 公开 API 拉取或本地离线响应；
- JSON 结构校验、关键词筛选、稳定 ID 去重；
- HTML 转纯文本并截断到 1200 字；
- 来源追溯、UTC 时间、内容哈希；
- 原子写入小样本 JSON；
- 不持久化原始 API 响应。

运行方式：

```powershell
cd experiments\job_data
python .\arbeitnow_experiment.py --keyword Python --limit 10 --output .\output\arbeitnow-python-sample.json
python -m pytest .\test_arbeitnow_experiment.py -q
```

2026-09-16 的实际联网运行成功获取并规范化 8 条岗位，拒绝 0 条；原始响应未持久化。结果见 `experiments/job_data/output/arbeitnow-sample.json` 的 `_meta`。数据量会随源站变化，这个结果只证明链路可行，不代表覆盖率或数据质量已达到生产标准。

## 11. 分期落地

### P0（1~2 周）

- 建立来源台账、统一 `JobPosting` 契约和禁采字段；
- 建成学职平台专业/职业两个只读适配器，完成详情字段清单和访问依据评审；
- 接 1 个公开 API/ATS + 1 个国内官方岗位来源；
- 完成原始缓存 TTL、幂等 upsert、过期标记、按来源下架；
- 产出职业×城市×周的岗位数和技能频率快照；
- 信息侦查员只引用审核通过的数据。

### P1（2~4 周）

- 企业官网/ATS 白名单扩到 20~50 家目标雇主；
- 接入 ESCO/国家职业分类映射；
- 建立用户自愿公司评价、脱敏审核和撤回链路；
- 解析漂移监控、数据质量看板和人工复核台。

### P2

- 与商业数据供应商签约后接入公司评价聚合；
- 做跨来源公司/岗位实体归一和可信度融合；
- 按用户目标职业触发按需刷新，而非扩大成全网爬虫。

## 12. 验收清单

- [ ] 未登记或非 `enabled` 来源无法运行；
- [ ] 登录、验证码、403 会停采，不存在绕过逻辑；
- [ ] 原始响应有 TTL 且不进入检索；
- [ ] 结构化数据具备来源、时间、版本、哈希；
- [ ] 同一批次重跑不重复写入；
- [ ] 字段漂移时停止发布而不是写入脏数据；
- [ ] 支持按来源和来源记录 ID 下架；
- [ ] 用户报告展示来源、样本量、时间窗和置信度；
- [ ] 公司评价支持脱敏、审核、撤回和重算；
- [ ] 全链路不采集候选人个人信息。
