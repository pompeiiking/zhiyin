## 一、为什么单独一份

复查中出现的下列情况，实现者无法自行决定，硬做等于替业务或架构拍板：

1. **改法本身有取舍**：两条路都能自圆其说，代价落在不同的契约或团队上；
2. **要动冻结契约或共享形状**：按《AGENTS.md》§2 / §5 / §11.2，必须先说明影响并取得确认；
3. **本质是口径问题**：例如"报告里要不要再放一份画像"是产品口径，不是技术选择；
4. **需要平台或内容方先到位**：代码已就绪，缺的是凭据或内容。

本文把这些集中起来，让每一次决策都有落点，而不是散在聊天记录或被"顺手做了"。

### D1 · 本地合成模型没有如实声明实现状态，占位产出可能不被拦住 —— 待决（P0）

| 项 | 内容 |
| --- | --- |
| 现象 | `LocalOrMockLLM` 未声明 `IMPLEMENTATION_STATUS`，装配报告按兜底逻辑把它报成 `wired`；它只在 `LLMResult.degraded=True` 里自述降级，而**该标记目前没有任何消费方** |
| 证据 | `zhiyin-infrastructure/zhiyin_infrastructure/local/llm.py`（类无状态声明；`chat()` 返回 `degraded=True`、`usage={"mock": True}`）；`zhiyin-boot/zhiyin_boot/report.py::_status_of` 的兜底分支；`zhiyin-boot/zhiyin_boot/container/ports.py` 把 `llm` 列为受门禁评分的能力位 |

| 为什么要斟酌 | 三条路各有真实代价，且都动共享面 |

| 改法 B | 把 `degraded` 透出到接口层（`ConversationTurnView` 加来源/降级标记）。代价：改公开 DTO + OpenAPI + 前端类型，等于把已"失去对象"的 MOCK-1 重新打开 |
| 改法 C | 装配期显式失败：未配置真实模型且未显式 opt-in 时**拒绝启动**。代价：改动运行前置，影响所有本地开发与 CI 的既有用法 |
| 建议 | **C 的变体**（加显式 opt-in 开关，默认拒绝启动）——它把"忘记开开关"变成启动即失败，不依赖任何界面标注，也不与"本地可跑通"冲突（本地开发显式开 opt-in 即可） |
| 决策人 | 架构负责人 + 共享装配负责人 |
| 不决策的后果 | 漏配环境会把占位内容当业务结果呈现，且现有全部门禁都不会报警 |

### D2 · 报告正文缺「个人画像」章节 —— 待决

| --- | --- |
| 现象 | `ReportFullTextView.sections` 的字段描述承诺"15 维全景 / 方案 / 行动计划 / **个人画像**"。2026-09-19 已补上方案与行动计划（修改日志第十节），**个人画像仍未产出** |

| 改法 A | 报告加 `profile` 章节（facade 从工作台聚合或读黑板）。代价：与工作台/对话页重复；且要先定"报告里的画像是版本快照还是活状态"——报告是**版本化只读资产**，画像会继续变化，混在一起会出现"报告里的画像与工作台不一致" |

| 项 | 已实施的做法 | 依据 | 需确认什么 |
| --- | --- | --- | --- |
| 交接口径 | ①只有 `ready_to_handoff=True` 才自动交接给②；⑤按 `next_handoff_stage` 再入环；**②③④一律等用户表达意图**，不自动推进 | `FR-COLLECT-007`（采集结束条件是达到最低置信度）+ 决策 4=A（意图→环节） | 产品是否希望"②诊断完成后自动进③"。当前按"方向必须由用户显式选定"处理；若希望自动推进，需要新增口径 |
