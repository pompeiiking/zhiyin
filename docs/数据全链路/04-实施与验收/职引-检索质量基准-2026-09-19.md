## 一、结论先说：**现在这个数字不是质量结论**

| 指标 | 实测值 |
| --- | --- |
| 用例数 | 100（`top_k=10`） |
| Recall@K | **0.0000** |
| MRR | **0.0000** |
| **期望 id 覆盖率** | **0/100 = 0.0000** |

`expected_coverage = 0` 意味着**评测集里的期望文档一条都不在语料里**。此时 Recall / MRR
必然是 0——它衡量的是"评测集与语料没对上"，**不是检索质量**。所以本报告只作为
**可复现的基准与诊断**，门槛**不能**据此冻结（第三期设计 §12.3 的建议值也不适用）。

按 namespace 的期望覆盖：

| --- | --- | --- | --- |
| theory | 16 | 0/16 | 6 |
| occupation | 17 | 0/17 | 6 |
| jd | 17 | 0/17 | 0 |
| report | 16 | 0/16 | 0 |
| memory | 17 | 0/17 | 0 |
| resume | 17 | 0/17 | 0 |

## 二、为什么覆盖率为 0：两个各自独立的原因

1. **评测集的期望指向一份"测试知识快照"，而该快照不在仓库里。**
   `data/evaluation/` 下只有评测集与 `retrieval_schema.json` 两个文件；评测集自己的
   description 写着"expected_ids 由测试知识快照提供"，但那份快照从未落地。
   实测期望 id 形如 `resume:benchmark-001` … `theory:benchmark-006`，全仓搜不到第二处引用。

2. **两边的 id 口径不一致（这是一个真实缺陷，不只是缺数据）。**
   评测集的期望**一律**写成 `namespace:id`；而 `LocalSearchGateway` 返回的
   `evidence_id` 是 JSON 里的**裸 id**（`raw["id"]`，如 `occ-2-06-03-02`、`theory-clover`）。
   影响不止于评测：
   - 内容明明存在也可能匹配不上；
   - 关键词通道与向量通道的**同一篇文档在 RRF 融合时会被当成两篇**（`RrfHybridSearchGateway`
     的去重键就是 `hit.evidence_id`，见 `infrastructure/search.py:132`）→ 证据重复、挤占 top_k。

   > 顺带说明：权威文档存储的唯一键是 `(namespace, source_id, version)`，其 `id` 在
   > `RetrievalDocumentStore` 的用例里也是 `namespace:id` 形态；**裸 id 是关键词通道这一处的
   > 特例**，不是既定契约。已按待决问题登记（改它会动检索行为，属需评审的改动）。

## 三、要让门槛真正可冻结，需要先满足什么

按依赖顺序（前两条不解决，后面都是空跑）：

1. **平台侧修好 RAG 知识库解析**（`callback_url` 指向宿主网关导致 embedding 取不到，
   实测 `Connection refused`）——见[修改日志 §18](../../日志-袁/01-职引-数据全链路修改日志.md)；
2. **真实内容进索引**：理论卡补齐方法步骤/边界/示例/来源（需领域负责人定稿）、
   职业/专业/行业/政策来源台账、招聘来源合规审核（需你或合规确认）；
3. **统一 id 口径**（`namespace:id`）并补上或重写测试知识快照；
4. 然后重跑本基准，与 §12.3 的建议门槛（如公共知识 Recall@10 ≥ 0.85）对比；
5. 通过评审后冻结门槛，并把本报告升级为回归门禁。

## 四、复现方式

```bash
cd zhiyin-src/template
python scripts/eval_retrieval.py --top-k 10 --out /tmp/baseline.json
```

输出含：指标、期望覆盖率、按 namespace 拆解、语料 id 数、id 口径不一致的诊断。
`--out` 写出的 JSON 里带 `usable_as_quality_baseline` 字段——**为 false 时不得把
`recall_at_k` / `mrr` 当作质量数字引用**。

## 五、顺带修掉的一件事

`evaluate_retrieval()`（Recall@K / MRR）此前**在仓库里没有任何调用方**：指标算得出来，
却没人跑，于是"达到质量门槛"这条一直悬着——属于典型的"看起来有、实际没有"。
本次接上了可执行入口，并加了一条状态记录型测试
（`test_eval_set_expectations_are_not_yet_covered_by_the_corpus`）：一旦内容或快照就位、
或 id 口径被统一，该用例立刻变红，提醒出新的基准并冻结门槛。

## 六、补充实测：线上三处存储各自有多少内容（2026-09-19 追加）

§一的"覆盖率 0"是**语料侧**的结论。为把"到底有没有内容"钉死，在 `zhiyin-api` 容器内做了
只读普查（数据来源为容器自己的装配与配置，命令与输出见[修改日志 §20.5](../../日志-袁/01-职引-数据全链路修改日志.md)）：

| 存储 | 实测 | 含义 |
| --- | --- | --- |
| 向量库 `zhiyin_vectors` | **0 行** | 向量通道**不可能**有任何命中；`Recall@K` 与向量侧完全无关 |
| 权威文档表 `retrieval_document` | **0 行** | `RrfHybridSearchGateway` 的 authority 回填无数据可回填；引用溯源目前无权威来源可查 |
| 检索审计表 `retrieval_log` | 30 行（`jd`7 / `memory`1 / `occupation`5 / `report`7 / `resume`7 / `theory`3） | 检索**确实被执行过**——不是"没人调"，而是"调了也没内容" |
| 本地知识库 `data/knowledge` | `occupation` 3 + `theory` 3 = **6 条**，均标注 DEMO；`jd`/`memory`/`report`/`resume` 为空文件 | 这是当前**唯一**的内容来源，而且它是演示数据 |

两条随之而来的结论：

1. §二 的第 1 条根因可以写得更确定：**不是"快照没找到"，而是整个内容层（向量库 + 权威表）
   是空的**，仓库里只有 6 张演示卡，评测集的 100 条期望不可能被覆盖。
2. 那 6 张演示卡会经 `LocalSearchGateway` 进入证据包、**并可能被报告引用**；而系统对此没有
   任何标记机制。已作为新问题登记为[待决问题 D12](职引-待决问题与改法选项-v1.0.md)。

## 七、追加实测：**线上检索其实恒为空**，被权威回填挡住（2026-09-19 二次修正）

§六 第 2 条要再限定一层。D12 上线后做真实验证时发现：同一个问题

| 调法 | 结果 |
| --- | --- |
| 真实装配的 `search`（挂 authority） | **0 条** |
| 同一个 `search`，临时摘掉 authority | **2 条**（`theory:theory-holland-riasec`、`theory:theory-clover`，且 `demo=True`） |
| 关键词通道单独查 | 同样 2 条（`demo=True`） |
| `retrieval_document` 行数 | **0 行** |

也就是说命中**确实被检索出来了**，但在 `hydrate()` 权威回填那一步被**全部丢弃**——因为权威表是空的。
所以线上今天的实际行为是**一条证据都拿不到**，而不是"拿演示卡当依据"；这也解释了真实报告里
`sources` 为空。

这层叠加对基准的含义：`Recall@K=0` 与"内容层为空"之外，还有**第三个**原因——**权威门静默丢弃**。
它已登记为 **D13**，并已于同日按建议落地改法 A（**零 schema 变更**的可观测性）：

- `hydrate()` 改为返回 `HydrationOutcome(hits, checked, dropped)`，把丢弃量交出去；
- 丢弃量写入**审计 `degraded=True`**（一条都没幸存时的主通道）与幸存命中的 `metadata["retrieval"]["dropped_non_authoritative"]`；
- 实测前后对照：改动前 46 行审计**全部** `degraded=0`（其中多行 `命中=0`，与"没命中"同形）；改动后同一次真实检索写入 **`degraded=1, 命中=0`**。

也就是说，"这次空结果到底是没内容还是被门挡掉"现在**在审计里能看出来了**。仍未做的是给 `retrieval_log` 加列，以在日志里区分"通道故障"与"权威门挡"（DB 语义变更，待确认）。

## 八、经 PAMI 的真实检索基准（2026-09-19 新增，**自检索冒烟**）

§一–§七 跑的都是**本地关键词通道 + 冻结的 100 条评测集**，因此覆盖率恒为 0、数字不是质量结论。
本节补上另一半：**用真实平台（PAMI RAG，含真实 embedding 与 rerank）检索我们导入的 22 份自有内容**。

| 项 | 内容 |
| --- | --- |
| 运行入口 | `python scripts/eval_pami_retrieval.py --top-k 5` |
| 通道 | **PAMI RAG（真实平台）**，经 `PamiSearchGateway` |
| 用例 | **22 条，机械化生成**：查询取自文档自身的标题/名称，期望为平台回传的文件名（与语料 id 一一对应） |
| 判定 | 按**标题（文件名）**命中判定——平台不返回文档 id 与 score（见 §25.5） |

**实测结果**：

| 指标 | 值 |
| --- | --- |
| Recall@5 | **1.0000（22/22）** |
| MRR | **0.9545** |
| 召回条目总数 | 28（22 例中多数返回 1–2 条） |

除 2 例（`theory-clover`、`theory-casve` 这两条**语料切片**排在第 2，前面是同名的理论卡）之外，全部 **rank=1**。

**这个数字能用来做什么、不能用来做什么**：

- **能**：确认召回链路真的可用、排序合理——目标文档在全部 22 例中都进了 top-5，且 20/22 排第一。这是**首次**对真实检索质量的量化观测。
- **不能**：**不能单独用来冻结面向用户的质量门槛**。用例是机械自检索（拿文档标题去问它自己），天然偏乐观；真实用户问法（"我该选哪个方向"这类）远难于自检索。把它当门槛基准会高估系统能力。
- **要冻结门槛还需要**：① 一批**真实问法**的用例（含真实用户问题与"该召回哪几条"的人工标注）；② 内容定稿（16 张理论卡目前是摘要级）；③ 来源回填口径（否则命中缺少可溯源的文档 id）。三者齐了再跑，门槛才有意义——**建议仍由你冻结**。

> ⚠️ 本节第一次跑的时候 22 例全部 `UnavailableError`、报告一度显示 `Recall@5 = 0.0000`——原因是脚本从 `.env` 读了**容器内**地址 `http://nginx:8081`，在宿主机上解析不了 `nginx`。**它看起来像一个质量结论，其实是环境错误。**现已固定为宿主机默认 `127.0.0.1:8081` 并在脚本注释里写明；这也是"工具本身会骗人"的又一例。
