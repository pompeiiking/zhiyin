## 一、开工前先明确三个概念

### 1.1 负责人可以跨层，代码不能乱层

数据能力负责人需要端到端交付，但不同职责必须放在各自层中：

| 内容 | 正确落点 | 不应放在 |
| --- | --- | --- |
| 跨层共用的数据形状、枚举 | `zhiyin-kernel` | Infrastructure 私有模型、Service 内重复定义 |
| Repository / Gateway / Transaction 抽象 | `zhiyin-data-sdk` | Business、Infrastructure 重复定义 |
| 版本增长、会话续接、资产传播等业务行为 | `zhiyin-business/services` | Repository、SQL 模型 |
| 影响范围、阈值等业务规则 | `zhiyin-business/policies` | Service 内联、基础设施配置 |
| MySQL、Redis、pgvector、采集器、对象存储实现 | `zhiyin-infrastructure` | Data SDK、Business |
| 选择并注入具体实现 | `zhiyin-boot/container` | Controller、Service |
| 菜单、文案、任务入口、智能体、理论卡、开关、规则参数 | `data/registry` | Python/TypeScript 常量 |
| 公共知识演示数据 | `data/knowledge` | 个人画像、前端组件 |

#### 第一期关系数据库部署冻结（历史规则）

- 第一期暂不部署 MySQL/PostgreSQL，不创建真实数据库实例、不实现真实数据库 Repository、
  不执行 schema migration。
- 必须等待平台负责人提供数据库接口、部署位置和复用方案，并由架构/数据负责人完成评审后，
  才能在 M3 开始真实数据库接入。
- 冻结期间七类 Repository 继续使用第一期本地/内存实现；不得为了让健康检查变绿而将
  `TransactionManager`、`RawQuery` 或真实 Repository 伪装成 `wired`。
- 第一期 Redis 已由团队单独确认直接接入，只承载缓存与临时状态，不等同于部署关系数据库，
  也不得成为画像、记忆、资产等权威数据的唯一副本。
- 2026-09-16 平台接口与选型决策已到位，M3 基础设施代码可以开工；复用 PAMI MySQL 时必须
  使用独立库 `zhiyin_service` 和独立账号，禁止写入 PAMI 自有 schema。向量库独立部署
  PostgreSQL 16+ + pgvector。业务表、迁移和七类 Repository 仍须逐项通过表结构评审。

### 1.2 Service 与 Repository 的边界

```text
Service：为什么写、写什么、版本怎么变化、是否发事件
Repository：怎样保存、怎样查询、怎样保证存储语义
Infrastructure：用哪种数据库/缓存/向量库实现 Repository 或 Gateway
```

例：

- `AssetService` 决定版本 `+1`、diff、影响范围和事件。
- `AssetRepository` 保存并读取 `AssetVersion`、Report、DirectionPlan、ActionPlan。
- MySQL Adapter 把这些操作实现为事务和 SQL。

不得为了“数据都归我负责”而把业务规则下沉到 Repository。

### 1.3 公共知识、缓存和个人数据必须分开

| 分类 | 示例 | 存储原则 |
| --- | --- | --- |
| 公共知识 | 专业、职业、岗位要求、政策、理论 | 可长期复用，带来源、版本和更新时间 |
| 临时缓存 | 原始 HTML/JSON、实时岗位列表、抓取中间产物 | 可丢、可重建、必须有 TTL |
| 个人数据 | 简历、测评、画像、行为、记忆、资产 | 按用户隔离，最小化收集，不得回流公共库 |

### 1.4 `ownership.json`、排期表和开发指南分别管什么

这三个东西不是一回事：

| 文件/概念 | 回答的问题 | 是否决定你当前写什么代码 |
| --- | --- | --- |
| `data/registry/ownership.json` | 某个能力长期归哪个**角色**负责 | 否，只用于能力归属和装配缺口提示 |
| 《第一期排期与认领表》 | 当前这一波具体由**哪个人**实现哪些文件 | 是，决定本期认领 |
| 《开发指南》 | 一项功能应该放在哪一层、如何依赖和验收 | 是，决定代码落位与开发规则 |

白话理解：

```text
ownership：出了问题长期找哪个岗位
排期表：这一次具体由谁动手
开发指南：代码应该写在哪里、不能越过什么边界
```

例如：

- `assets` Repository 在 `ownership.json` 中归“数据访问负责人”，表示它长期由数据角色维护。
- 排期表把 `AssetService` 分给后端-2，表示本期由袁明阳具体实现这个业务服务。
- 开发指南规定 `AssetService` 仍放在 `zhiyin-business/services/asset.py`，不能因为负责人是数据角色就移动到 Data SDK。

你的当前执行顺序是：

1. 先看[工作清单](职引-数据能力全链路工作清单.md)的第一波、第二波、第三波，确认这波做什么；
2. 再看本开发须知，确认代码放哪、怎么实现和怎么验收；
3. `ownership.json` 平时不用维护进度，只有能力的长期角色归属发生变化时才需要调整。

当前 `ownership.json` 保存的是“数据访问负责人”等角色名，不是个人日报。不要为了记录个人进度把所有 `owner` 改成姓名；个人完成情况统一写入[完成情况记录](职引-数据能力全链路完成情况记录.md)。

## 二、数据能力开发的标准落位链条

新增或修改一项数据能力时，按下列顺序判断，不要先建文件再找归属。

### 2.1 第一步：确认数据形状

先在 `zhiyin-kernel` 搜索是否已有模型或枚举：

```powershell
rg "目标模型名|目标字段名" zhiyin-kernel
```

- 已有形状：直接复用。
- 仅某个 Adapter 内部使用：放在该 Adapter 私有模块，不进内核。
- 确实需要跨层共用：经评审后加到内核；内核必须保持零依赖且只保存形状/最小契约。
- 禁止在不同层复制同名 Pydantic 模型或 Enum。

### 2.2 第二步：确认数据访问契约

在 `zhiyin-data-sdk` 查找已有 Repository/Gateway：

```powershell
rg "class .*Repository|class .*Gateway|目标方法名" zhiyin-data-sdk
```

只有现有契约确实无法表达需求时才修改 Port。修改前必须说明：

1. 当前契约为什么不能表达；
2. 哪些调用方会受影响；
3. 本地与真实实现如何同时兼容；
4. 对应契约测试如何补充。

本层所有公开 IO 方法必须是 `async`。Data SDK 只允许依赖 `zhiyin-kernel`，不得依赖具体 Infrastructure。

### 2.3 第三步：实现业务数据行为

涉及“版本、传播、续接、聚合、成就、日历”等业务语义时，代码进入 `zhiyin-business`：

- 数据读写编排：`services/`。
- 纯规则判断：`policies/`。
- 后台业务事件消费：`workers/`。
- 跨服务接口：`ports/`。

Service 只能依赖 Port、Data SDK 契约、编排原语和内核形状，不得 import `zhiyin_infrastructure`。

### 2.4 第四步：实现基础设施适配器

| 实现类型 | 落点 |
| --- | --- |
| 本地/内存 | `zhiyin-infrastructure/zhiyin_infrastructure/local/` |
| MySQL/关系数据库 | `zhiyin-infrastructure/zhiyin_infrastructure/mysql/` 或 `persistence/` |
| Redis | `zhiyin-infrastructure/zhiyin_infrastructure/redis/` |
| pgvector | `zhiyin-infrastructure/zhiyin_infrastructure/pgvector/` |
| Kafka | `zhiyin-infrastructure/zhiyin_infrastructure/kafka/` |
| 真实模型/Embedding | `zhiyin-infrastructure/zhiyin_infrastructure/llm/` |
| pami 平台 | `zhiyin-infrastructure/zhiyin_infrastructure/pami/` |
| MinIO | `zhiyin-infrastructure/zhiyin_infrastructure/minio/` |
| 纯数据管道 Worker | `zhiyin-infrastructure/zhiyin_infrastructure/workers/` |

Infrastructure 只实现契约，不得 import `zhiyin_business` 或 `zhiyin_orchestration`，也不得重新定义一套 Repository/Gateway。

### 2.5 第五步：装配

具体实现只能在 `zhiyin-boot` 选择：

- Repository、事务、功能开关：`container/repositories.py`。
- Gateway：`container/gateways.py`。
- Service、编排原语、Worker：`container/services.py`。
- Container 与应用启停：`container/__init__.py`。

这些是共享写点。按排期约定，本人完成实现和测试后，请共享装配负责人统一接线；不要多人同时修改装配文件。

## 三、第一波开发须知：Memory 与 Asset

第一波同时完成第一期 Redis 基础接入。Redis 属于数据底座，不把 Redis Client 注入 Memory/Asset Service；Service 仍只依赖 Repository/Gateway。

### 3.1 ConversationMemoryService

必须保证：

- `(user_id, task_id)` 是读取和更新边界，不能只按 `task_id` 查询。
- 不存在时创建；存在时更新当前环节、主理、摘要和活跃时间。
- `summary_delta` 是追加语义，不得覆盖已经确认的摘要。
- 并发追加使用 Repository CAS/版本检查重试，不得用普通“读取后覆盖”丢失摘要。
- 空增量不得制造无意义分隔符或重复内容。
- `list_by_user` 不得返回其他用户的数据。
- 不在记忆中无限保存完整对话原文；长期记忆采用摘要和必要事实。

至少测试：新建、更新、空摘要、连续追加、用户隔离、任务隔离、列表查询。

### 3.2 AssetService

必须保证：

- 第一版从 1 开始，后续严格递增。
- 同一用户、同一资产类型的版本序列独立。
- `depends_on_profile_keys` 是影响面判断依据，保存时去重并保持稳定。
- 首版 diff 可为空；后续版本必须能解释变化原因。
- `save_version` 成功后再发布 `asset_version_changed`；保存失败不得发成功事件。
- 正文与对应版本必须通过 Repository 原子快照契约同时提交，禁止出现正文和版本半写入。
- `propagate` 只执行 `ImpactPolicy` 返回的受影响资产，未命中资产版本不变。
- 重复事件不得造成同一变化重复升版。
- 报告、方案和行动计划的内容读取与版本元数据边界清晰。

第一波规则负责人尚未交付具体 `ImpactPolicy` 时，用测试 Fake 验证 Service 对 Policy 结果的执行，不在 AssetService 内临时写影响范围规则。

至少测试：首版、连续升版、多资产类型、用户隔离、命中/未命中传播、重复事件、保存失败不发事件。

## 四、第二波开发须知：Workspace 与 Function

### 4.1 WorkspaceService

- 它是只读聚合服务，不写状态、不发事件、不触发资产重算。
- 可使用 `asyncio.gather` 并行读取 Profile、Behavior、Memory、Asset。
- 必须明确部分数据缺失时的降级结果，不能因为一个空报告让整个工作台 500。
- ①至⑤的 `StagePanel` 顺序、状态和版本来源保持稳定。
- 依赖关系来自真实的 `depends_on_profile_keys`，不在页面层猜测。
- 不把 Infrastructure 实体或 ORM Model 暴露给 API。

### 4.2 FunctionService

- 报告全文只读已有资产，不重新调用模型生成。
- M2 导出是明确占位，返回 `available=false`；不要提前伪造文件链接。
- 日历、成就、跟踪时间线没有稳定 Repository 出口时，先发起契约评审。
- 第一期日历复用 `ObjectStoreGateway`，使用 ETag 条件写和原子文件替换；不得依赖单个 Service 实例锁冒充并发安全。
- 成就只能由行为日志驱动，登录、浏览、刷新页面不能解锁。
- 自动演示只读 DEMO 数据，不写用户真实黑板。

至少测试：空工作台、部分数据、完整数据、报告版本选择、导出占位、行为驱动成就、用户隔离。

## 五、第三波开发须知：Impact Worker 与 E2E

### 5.1 ImpactPropagationWorker

- 只消费 `profile_field_updated`，不实现影响范围规则。
- 从事件中提取用户和变更字段后调用 `AssetService.propagate`。
- `run_once()` 无任务返回 0，有任务返回实际处理数。
- 必须具备幂等键或等效去重机制；重复投递不能重复升版。
- 失败不能确认成功消费，需保留重试可能。
- Worker 注册后由 boot lifespan 或独立 Worker 入口统一驱动，不自行创建永久后台线程。

### 5.2 E2E

本人负责把以下数据相关验收从 skip 改为真实断言：

1. 跨会话恢复记忆和前序资产；
2. 画像更新只传播到受影响资产；
3. 资产版本严格递增且 diff 可见；
4. 行为、记忆、资产按用户隔离；
5. 重复事件不产生重复资产版本。

E2E 必须在功能实现的同一波完成，不允许只删除 skip 而不补断言。

## 六、采集与知识库开发须知

### 6.1 合规优先

开始任何来源开发前，建立数据源登记：

| 字段 | 必填内容 |
| --- | --- |
| source_id | 稳定来源编号 |
| owner | 来源责任人 |
| access_basis | 开放数据、公开 API、书面授权或允许访问的公开页面 |
| allowed_scope | 允许采集的页面、字段和使用目的 |
| refresh_interval | 更新频率 |
| removal_method | 停采与下架方法 |
| retention | 原始响应与结构化数据保留期 |

禁止绕过登录、验证码、访问控制、付费墙或明确禁止的自动化限制。触发风控、授权不明或页面声明禁止时立即停止该来源。

### 6.2 标准处理链

```text
Fetch → Parse → Normalize → Dedup/Version → Review → Store → Index
```

每一步应可以独立测试、重试和记录状态：

- Fetch：只获取许可范围内的数据，记录请求时间和来源 URL。
- Parse：解析失败保留错误，不把空字段当成功结果。
- Normalize：统一编码、枚举、名称、城市、学历、技能等口径。
- Dedup：来源唯一键优先，没有唯一键时使用稳定指纹。
- Version：内容哈希变化才生成新版本。
- Review：规则校验失败进入人工检查，不直接发布。
- 未配置 Reviewer 时条目必须保持 `pending_review`，本地检索只读取 `approved/enabled` 条目。
- Store：按公共知识、缓存、个人数据分流。
- Index：索引成功后记录模型版本和索引批次。

### 6.3 知识库与向量

- 文档、Chunk、Embedding、索引记录必须有稳定 ID。
- Embedding 必须记录 provider、model、dimension、model_version。
- 不同模型版本必须使用不同命名空间或明确路由，禁止混查。
- 原文更新或删除时，对应 Chunk 和向量必须同步更新/删除。
- RAG 结果必须返回来源、片段、抓取时间和内容版本。
- 建立固定评测集，不以“能搜到结果”代替召回质量验收。

## 七、数据库与 Repository 开发须知

### 7.0 真实数据库开工门槛

只有同时满足以下条件，才能开始对应的 M3 数据库工作：

1. 平台数据库接口及其负责人已经明确；
2. PostgreSQL/MySQL 选型和部署位置已经确认；
3. 已决定复用平台数据库还是独立部署；
4. 表清单、事务边界、迁移与回滚方案已经评审；
5. 联调环境、账号权限和敏感数据边界已经确认。

截至 2026-09-16，五项数据库门槛均已闭合，ORM、迁移、七类 Repository 与部署覆盖已完成；
真实 MySQL/Redis/pgvector/MinIO、HNSW 查询计划、WAL、备份与隔离库恢复也已运行验收通过。
PAMI Embedding 的模型 ID、组织/应用凭据仍未配置，因此只能标“适配代码完成/待平台联调”，
不得把 MockTransport 契约测试写成真实模型调用通过。

### 7.1 Repository 通用语义

每个实现必须明确并测试：

- 不存在时返回 `None`、空列表还是抛错；与 ABC 文档保持一致。
- 列表排序、分页和 limit 的稳定性。
- 用户隔离和任务隔离。
- 重复写入的幂等语义。
- append-only 数据不得被覆盖更新。
- 返回对象不能因调用方修改而污染内存存储中的原值。
- 时间统一使用带时区 UTC，展示层再转换。
- 错误转换为 Data SDK 定义的错误，不泄露数据库驱动异常。

### 7.2 事务

- 跨 Repository 的原子写由 `TransactionManager` 管理。
- 明确 begin、commit、rollback、异常传播和资源释放。
- 事件采用“事务成功后发布”或 Outbox；不得数据库回滚但事件已经成功发出。
- 禁止 Service 自行管理具体 SQLAlchemy Session。

### 7.3 数据库模型

- ORM 模型属于 Infrastructure，不直接返回给 Business/API。
- 唯一键、外键、非空、检查约束和版本单调尽可能由数据库兜底。
- 索引根据真实查询路径设计，不因字段存在就全部加索引。
- schema 变化必须通过迁移脚本，不允许生产环境手工改表。
- 迁移需可重复验证，并提供回滚或前滚恢复方案。
- 版本化资产的业务 ID 与历史版本键不能混淆：例如同一 `report.id` 可以有多个
  `version`，报告历史唯一键应是用户与版本组合，不得把 `report.id` 设为跨版本唯一。

### 7.3.1 第二波资产正文对接

- 诊断、决策、行动产出必须分别走 `AssetService.save_report`、
  `save_direction_plans`、`save_action_plan`；`save_version` 只保存版本元数据，不能代替正文写入。
- Service 只调用 Repository 的 `save_snapshot` 原子操作；正文写失败时不得留下版本或发布成功事件。
- Repository 必须用最终落库的 `AssetVersion.version` 覆盖报告正文版本，保证列表与全文一致。
- 保存方向候选只保存模型给出的候选内容，不得自动设置 `selected=True`；选择动作必须由用户显式触发。
- 数据/知识适配层不负责把 `DiagnoseOutput`、`DecideOutput`、`ActOutput` 转为资产模型；
  该映射属于业务编排负责人。未合入生产调用方时保留 OPEN 注释和 xfail，禁止数据侧越权“代闭合”。

### 7.4 RawQuery

- 仅 Infrastructure 可调用。
- 限制只读/写入类型、超时、最大返回行数和允许访问的表。
- 参数必须绑定，禁止字符串拼接 SQL。
- 记录调用者、用途、trace id、耗时和结果量。
- 常规业务查询应进入 Repository，不把 RawQuery 当通用逃生口。

### 7.5 第一期 Redis 分库与 Key 规范

第一期直接接入 Redis，采用单实例逻辑分库：

完整的分库映射、Key、TTL、降级、测试和 Cluster 演进要求见[《职引 · 第一期 Redis 分库策略》](职引-第一期Redis分库策略.md)；下表是开发时的速查摘要。

| DB | 用途 | 允许的数据 | 禁止的数据 |
| ---: | --- | --- | --- |
| 0 | 通用应用缓存 | 可重建查询结果、配置读取缓存 | 画像/资产唯一副本 |
| 1 | 临时会话 | 游客状态、短期认证会话 | 长期会话记忆唯一副本 |
| 2 | 调度 | 到期任务、冷却期、执行状态 | 永久业务事实 |
| 3 | Guard | 限流计数、幂等键、短期去重 | 无期限集合 |
| 4 | Crawl | 采集任务状态、短期原始响应 | 长期保存原始受限内容 |
| 5 | Knowledge | 检索/RAG结果缓存 | 公共知识权威原文唯一副本 |
| 6 | VectorSync | 短锁、检查点、待同步状态 | 最终向量数据唯一副本 |
| 15 | 自动化测试 | 测试键 | 开发共享数据、生产数据 |

Key 必须同时包含产品、环境、业务域和实体：

```text
zhiyin:{env}:{domain}:{entity}:{id}
```

示例：

```text
zhiyin:dev:cache:workspace:user-001
zhiyin:dev:session:guest:guest-001
zhiyin:dev:schedule:stall-check:user-001
zhiyin:dev:guard:idempotency:event-001
zhiyin:dev:crawl:snapshot:sr-1:batch-001
zhiyin:dev:knowledge:query:sha256-xxx
zhiyin:dev:vector-sync:lock:occupation
```

开发要求：

- 使用 `redis.asyncio` 等异步客户端，不在 async 调用链里使用同步 Redis Client。
- Redis URL、认证、TLS、连接池和 DB 编号由 Settings/环境变量提供。
- 业务 Service 不直接 import Redis；具体实现只能位于 Infrastructure。
- 每个 Adapter 在构造时绑定 DB，不允许业务请求处理中临时 `SELECT`。
- 即使不同逻辑库允许键名重复，也必须保留统一前缀；逻辑库不是安全边界。
- 写入前定义 TTL、最大值、序列化格式和失败策略。
- 分布式锁必须设置所有者 token 和过期时间，释放时校验 token。
- 幂等键需要明确保留期，不得永久增长。
- 测试不得执行无范围 `FLUSHALL`；只清理 DB 15 或本用例前缀。
- 画像、行为、记忆、资产等权威业务数据不得只保存在 Redis。
- Redis Cluster 只支持 DB 0；迁移 Cluster 时用独立实例或命名空间替代逻辑分库。

第一期至少测试：连接失败、TTL 到期、命名空间隔离、逻辑库隔离、序列化错误、重复幂等键、锁超时、测试数据清理。

## 八、状态、装配与生成物规则

### 8.1 状态必须诚实

- 真正实现完成并通过测试后才标记 `IMPLEMENTATION_STATUS = "wired"`。
- 仍会抛 `NotImplementedError` 的类必须保持 `skeleton`。
- skeleton 不得通过装配冒充可用能力。
- 每波结束运行 `python -m zhiyin_boot --check` 查看实际缺口。

### 8.2 不手改生成物

- `contracts/openapi.json` 由 `python scripts/export_openapi.py` 生成。
- `zhiyin-web/src/api/types.ts` 由 `npm run gen:api` 生成。
- 冲突时重新生成，不手工合并。

### 8.3 不建模糊公共包

禁止新增 `utils`、`common`、`helpers` 等无边界包。代码按真实职责进入 repository、gateway、adapter、policy、service 或 worker。

## 十、个人开发流程

### 10.1 领取任务

1. 在工作清单确认所属波次和依赖。
2. 阅读目标文件顶部 docstring、对应 Port、Kernel 模型和 Repository。
3. 用 `rg` 搜索已有实现、测试、事件名和动态资源，禁止凭记忆另建同义类型。
4. 确认共享文件负责人和联调对象。

### 10.2 开发中

1. 先写最小失败测试，固定语义。
2. 只修改本人责任文件和独立测试文件。
3. 需要改共享契约或装配时提交变更请求，由负责人统一处理。
4. 每完成一个方法运行相关测试；完成一个能力再跑全量测试。
5. 不顺手重构无关代码，不覆盖其他人的工作区修改。

### 10.3 提交前

- [ ] 若涉及真实数据库，平台接口与复用方案已经书面确认，且 M3 部署冻结已正式解除。

- [ ] 用户隔离、版本、幂等和事务测试通过。

## 十一、需要立即升级确认的情况

遇到以下情况不要自行猜测：

1. 需要新增或改变跨层数据模型、Repository/Gateway 方法；
2. 日历、成就、跟踪时间线等能力没有持久化出口；
3. 影响范围、摘要格式、数据保留期等业务口径不明确；
4. 数据源授权、站点协议或个人信息处理依据不明确；
5. 需要改变数据库选型、Embedding 模型、向量维度或索引空间；
6. 跨 Repository 原子写没有事务或 Outbox 方案；
7. 现有门禁允许 skeleton，但阶段目标要求真实可用；
8. 为完成任务必须修改他人独占的共享文件。

升级时带上：问题、当前契约、两个可选方案、影响文件、数据迁移影响和推荐选择。
