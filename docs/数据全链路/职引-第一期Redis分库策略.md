## 一、目标与边界

本策略用于隔离不同性质的临时数据，降低键冲突、误删和跨用途读取风险，并为缓存、会话、调度、限流幂等、采集和知识检索提供统一 Redis 基线。

本文所称“分库”是 Redis 单实例中的逻辑 DB，不是 MySQL 等关系数据库的分库分表。

逻辑 DB 只能隔离键空间，不能隔离变量、账号、权限、内存、CPU 或故障。因此即使不同 DB 允许出现相同键名，也必须使用统一 Key 前缀，不得依赖逻辑 DB 代替命名规范或安全控制。

---

## 二、逻辑库分配

| DB | 数据域 | 典型用途 | Key 前缀 | TTL / 数据性质 |
| ---: | --- | --- | --- | --- |
| 0 | 通用缓存 | 可重建的查询结果、配置读取缓存 | `zhiyin:{env}:cache:*` | 5–60 分钟，必须可重建 |
| 1 | 临时会话 | 游客会话、登录态辅助数据、短期会话上下文 | `zhiyin:{env}:session:*` | 游客 30 分钟–24 小时；认证会话最长 7 天 |
| 2 | 调度状态 | 提醒、冷却、下次执行时间、短期调度标记 | `zhiyin:{env}:schedule:*` | 截止时间后再保留 1–7 天 |
| 3 | 防护控制 | 限流、幂等、去重、短期互斥 | `zhiyin:{env}:guard:*` | 窗口期或业务幂等期，通常 1 分钟–7 天 |
| 4 | 采集任务 | 爬虫任务状态、原始响应/岗位快照缓存、批次去重 | `zhiyin:{env}:crawl:*` | 原始响应 1–24 小时；状态按任务周期清理 |
| 5 | 知识检索 | 知识查询结果、RAG 中间结果、Embedding 请求缓存 | `zhiyin:{env}:knowledge:*` | 10 分钟–24 小时，数据变更时主动失效 |
| 6 | 向量同步 | 同步检查点、短期锁、待处理批次状态 | `zhiyin:{env}:vector-sync:*` | 锁 5–30 分钟；检查点按同步策略保留 |
| 7–14 | 预留 | 未经评审不得占用 | `zhiyin:{env}:{approved-domain}:*` | 评审时明确 |
| 15 | 自动化测试 | Redis 契约测试、集成测试临时键 | `zhiyin:test:{suite}:*` | 用例结束按前缀清理，禁止连接生产实例 |

分配理由：

- DB 0 只放通用、可重建缓存，避免与业务控制状态混在一起。
- DB 1 单独承载临时会话，便于按会话生命周期清理。
- DB 2 和 DB 3 分开，避免调度状态被限流或幂等清理任务误删。
- DB 4–6 分别对应采集、知识和向量同步，便于独立观测容量与命中率。
- DB 15 固定给测试，避免测试清理污染开发数据。

## 三、Key 命名规范

统一格式：

```text
zhiyin:{env}:{domain}:{entity}:{identifier}[:{subkey}]
```

示例：

```text
zhiyin:dev:cache:workspace:user-001
zhiyin:dev:session:guest:guest-001
zhiyin:dev:schedule:stall-check:user-001
zhiyin:dev:guard:idempotency:event-001
zhiyin:dev:crawl:snapshot:sr-1:batch-001
zhiyin:dev:knowledge:query:sha256-xxx
zhiyin:dev:vector-sync:lock:occupation
```

禁止事项：

- Key 中不得放手机号、身份证号、简历原文、Token 等敏感信息。
- 禁止使用 `data`、`temp`、`cache1` 等无法判断归属和用途的名称。
- 禁止省略环境和数据域前缀。
- 禁止把用户输入的长文本直接拼入 Key；应使用稳定 ID 或摘要哈希。
- 禁止因为不同逻辑库允许同名键，就故意复用含义不同的键名。

## 四、TTL 与容量规则

| 数据类型 | 建议 TTL | 失效要求 |
| --- | --- | --- |
| 通用查询缓存 | 5–60 分钟 | 权威数据更新时主动失效；超时后可重建 |
| 游客会话 | 30 分钟–24 小时 | 用户转正式身份或会话过期后清理 |
| 认证会话辅助数据 | 不超过 7 天 | 不得超过登录凭证本身有效期 |
| 调度/冷却状态 | 到期时间 + 1–7 天 | Worker 成功处理后可提前清理 |
| 限流计数 | 窗口期 + 小量缓冲 | 必须设置过期时间，禁止永久计数 |
| 幂等/去重键 | 24 小时–7 天 | 以业务允许的重复提交周期为准 |
| 采集原始响应 | 1–24 小时 | 可追溯信息转存后及时清理 |
| 知识/RAG 缓存 | 10 分钟–24 小时 | 知识版本变化时主动失效 |
| 分布式锁 | 5–30 分钟 | 必须有所有者 token，并防止误释放 |

- 所有临时键必须有 TTL；例外必须在代码评审中说明负责人、用途和清理机制。
- 禁止无界增长的 List、Set、Sorted Set 或 Stream；必须限定长度、时间窗口或消费保留策略。
- 大型 HTML、文件和长文档不长期放 Redis；Redis 只保存短期快照或对象存储引用。

## 五、Redis 与权威数据的边界

以下数据不得只保存在 Redis：

- 用户画像、行为记录和长期会话记忆；
- 报告、方向方案、行动计划及其版本；
- 公共知识库的权威版本、来源和审核记录；
- 用户上传原件和长期留存的采集原始文件；
- 需要审计、恢复或长期追溯的数据。

Redis 可作为这些数据的缓存、短期状态或并发控制组件。缓存丢失后，系统应能从权威存储恢复或明确降级。

## 六、配置与代码落位

建议统一配置项：

```text
ZHIYIN_REDIS_URL
ZHIYIN_REDIS_PASSWORD
ZHIYIN_REDIS_SSL
ZHIYIN_REDIS_POOL_SIZE
```

逻辑 DB 映射由 Infrastructure 集中维护，不由各个 Service 自行填写数字。

| 内容 | 正确落点 |
| --- | --- |
| Cache/Repository/Gateway 契约 | `zhiyin-data-sdk` |
| Redis Client、序列化和各数据域适配器 | `zhiyin-infrastructure/zhiyin_infrastructure/redis/` |
| 环境变量与配置读取 | `zhiyin-boot` 的 settings/config 模块 |
| 具体实现选择和依赖注入 | `zhiyin-boot/container/` |
| 契约和集成测试 | `tests/contracts/`、`tests/integration/` |

- 使用异步 Redis Client 和连接池，公开 IO 接口保持 `async`。
- 每个适配器创建时绑定固定 DB；请求处理过程中不得执行 `SELECT` 动态切库。
- `zhiyin-business` 不得直接导入 Redis Client，也不得出现 DB 编号和 Redis Key 拼接。
- 业务层只依赖 Repository/Gateway；Redis 是基础设施实现细节。

## 七、序列化、并发与安全

- 结构化值使用 UTF-8 JSON，并包含必要的 schema/version 字段；禁止不安全的任意对象反序列化。
- 时间统一保存为 UTC ISO 8601 或约定的 Unix 时间戳，不混用本地时间字符串。
- 计数、限流和多键状态变更使用 Redis 原子操作或经过评审的 Lua 脚本。
- 幂等键优先使用 `SET key value NX EX ttl` 一类原子语义。
- 分布式锁必须设置所有者 token 和过期时间，释放时校验 token。
- Redis 不暴露公网；凭证不得写入仓库、Key、日志或错误响应。
- 日志不得打印完整缓存值、会话内容、简历或其他个人数据。
- 逻辑 DB 不是权限边界；需要权限隔离时使用独立实例、ACL 或网络边界。

## 八、故障与降级策略

| 数据域 | Redis 不可用时的第一期策略 |
| --- | --- |
| 通用缓存 | 旁路缓存，直接读取权威数据；限制回源并记录告警 |
| 临时会话 | 明确返回会话暂不可用或重新创建；不得伪造已恢复状态 |
| 调度状态 | 暂停/重试并保留待处理来源，不静默丢任务 |
| 限流 | 按接口风险评审选择 fail-open 或 fail-closed，禁止全局默认 |
| 幂等 | 优先保守拒绝或转权威存储校验，避免重复副作用 |
| 采集任务 | 暂停领取新任务，已领取任务按可重入规则恢复 |
| 知识检索缓存 | 回源本地知识或权威检索；必要时降级关键词检索 |
| 向量同步 | 暂停同步并保留检查点，恢复后继续 |

错误日志至少记录数据域、DB、操作类型、耗时、异常类型和 trace id，不记录完整 Key 中的敏感标识或 Value。

## 九、测试与清理

第一期至少覆盖：

1. DB 0–6 的连接和用途映射正确。
2. 同一 Key 后缀在不同逻辑库互不覆盖。
3. 所有 Key 带环境和数据域前缀。
4. TTL 设置、续期和到期行为正确。
5. 幂等键的首次成功、重复拒绝和过期重试正确。
6. 锁超时、所有者校验和异常释放正确。
7. JSON 序列化版本、非法数据和时间字段处理正确。
8. Redis 断连、超时和恢复后的降级/重试符合本策略。
9. 缓存失效后可从权威数据恢复。
10. 测试数据只清理 DB 15 或当前用例前缀。

测试优先使用独立 Redis 实例；共用开发实例时固定使用 DB 15 和唯一测试前缀。禁止在共享环境或生产环境执行无范围 `FLUSHALL`、`FLUSHDB`。

## 十、监控指标

第一期至少保留可观测字段，M3 接入正式监控：

- 各逻辑 DB 的键数量、内存占用和过期键数量；
- 命中率、回源量和缓存重建耗时；
- 命令延迟、连接池使用率、超时和连接失败；
- 限流拒绝数、幂等命中数和锁等待/超时；
- 采集任务积压、知识缓存失效和向量同步检查点滞后；
- 大 Key、热 Key、无 TTL Key 和异常增长趋势。

## 十二、M3 演进说明

第一期逻辑分库适合单实例开发和联调。M3 需要补齐认证/TLS、高可用、持久化、备份、监控、容量和故障切换。

Redis Cluster 只支持 DB 0。若迁移 Cluster，DB 0–6 的逻辑隔离必须改为独立实例、独立集群或统一 DB 0 下的严格命名空间；Repository/Gateway 契约保持不变，迁移细节留在 Infrastructure 和 Boot。
