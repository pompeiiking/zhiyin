### 2.3 “重复”和“分层”的判定标准

本审计不按“文件名相似”或“字段相似”直接判断重复，而按职责判断。

#### 判为真正重复

同时满足以下特征时，判为真正语义重叠：

1. 两个公开契约都在表达同一种业务或外部能力；
2. 调用参数、返回结果虽然改名，但可以直接互相映射；
3. 一个实现只是调用另一个契约后转换字段，没有新增清晰独立职责；
4. 上层调用方难以判断应该依赖哪个入口；
5. 继续扩展会导致过滤、命名空间、降级或审计语义在两处演化。

#### 判为架构要求的能力分层

满足以下任一情况时，不判为重复：

1. ABC/Port 与其具体实现；
2. 业务语义接口与数据访问接口；
3. 语义编排契约与外部传输契约；
4. Kernel 业务模型与 ORM Row；
5. local、MySQL、Redis、MinIO、PAMI、pgvector 等可替换实现；
6. Controller、Facade、业务 Service、Repository 各自在调用链中承担不同职责；
7. 同一冻结契约的测试替身、内存实现和生产实现。

## 四、确实存在的重叠部分

> 数量口径：以下是 **2 组语义重叠关系**，不是“只有两个文件”。它们涉及多个契约模型和多个适配器实现。

### 4.1 重叠一：KnowledgeGateway 与 SearchGateway

#### 4.1.1 契约位置

文件：`zhiyin-src/template/zhiyin-data-sdk/zhiyin_data_sdk/gateways/ai.py`

| 契约 | 方法 | 返回模型 |
| --- | --- | --- |
| `KnowledgeGateway` | `search(query, top_k, namespace, filters)` | `list[KnowledgeHit]` |
| `SearchGateway` | `keyword(query, top_k)` | `list[SearchHit]` |
| `SearchGateway` | `hybrid(query, top_k)` | `list[SearchHit]` |

模型对应关系：

| `KnowledgeHit` | `SearchHit` | 实际含义 |
| --- | --- | --- |
| `doc_id` | `id` | 命中文档标识 |
| `snippet` 或 `title` | `content` | 命中文本 |
| `score` | `score` | 相关度 |
| `metadata` | `metadata` | 来源和附加信息 |

#### 4.1.2 当前实现证据

本地实现位于 `zhiyin-infrastructure/zhiyin_infrastructure/local/knowledge.py`：

```text
LocalKnowledgeRepo.search()
    ↓ 返回 KnowledgeHit
LocalKeywordSearch.keyword()
    ↓ 逐条映射
SearchHit(id=doc_id, content=snippet/title, score=score, metadata=metadata)
```

PAMI 实现位于 `zhiyin-infrastructure/zhiyin_infrastructure/pami/adapters.py`：

```text
PamiKnowledgeGateway.search()
    ↓ 返回 KnowledgeHit
PamiSearchGateway.keyword()
    ↓ 逐条映射
SearchHit(...)

PamiSearchGateway.hybrid()
    ↓
直接调用 keyword()
```

#### 4.1.3 为什么判为真正重叠

`LocalKeywordSearch` 和 `PamiSearchGateway` 没有增加新的关键词检索数据源，而是将 `KnowledgeGateway.search()` 的结果改字段后再次暴露。调用方可能同时面对 `knowledge` 和 `search` 两个能力位，却无法仅根据职责判断应该使用哪个。

主要风险：

- `namespace` 和 `filters` 只存在于 `KnowledgeGateway`；
- `keyword/hybrid` 只存在于 `SearchGateway`；
- 同一次知识检索可能分别记录成 Knowledge 和 Search；
- PAMI 的 `hybrid()` 当前实际上不是本地可控的混合检索；
- 第三期继续增加过滤、引用、租户隔离、检索解释时容易在两套入口分叉。

#### 4.1.4 责任来源

这组契约在袁明阳开发前已经存在于 Data SDK。袁明阳的改动是补齐 Local/PAMI 实现和装配，没有新增这两个冻结接口。

#### 4.1.5 当前可执行约束

在不修改冻结接口的前提下：

1. 第三期业务/RAG 流程只选择一个检索入口；
2. 建议业务侧统一依赖 `SearchGateway`；
3. `KnowledgeGateway` 仅作为平台知识库的底层适配能力；
4. 不允许业务 Service 同时调用 Knowledge 和 Search 再自行拼结果；
5. 后续若合并契约，必须单独评审调用方、实现方、测试、Boot 装配和兼容影响。

### 4.2 重叠二：SearchGateway.vector 与 VectorGateway.search

#### 4.2.1 契约位置

| 文件 | 契约 | 方法 |
| --- | --- | --- |
| `zhiyin-data-sdk/zhiyin_data_sdk/gateways/ai.py` | `SearchGateway` | `vector(embedding, top_k)` |
| `zhiyin-data-sdk/zhiyin_data_sdk/gateways/vector.py` | `VectorGateway` | `search(namespace, embedding, model, top_k, filters)` |

返回模型也存在一一映射：

| `VectorHit` | `SearchHit` |
| --- | --- |
| `id` | `id` |
| `text` | `content` |
| `score` | `score` |
| `metadata` + `source_id` | `metadata` |

#### 4.2.2 当前实现证据

`zhiyin-infrastructure/zhiyin_infrastructure/search.py::RrfHybridSearchGateway.vector()` 的实现链路是：

```text
SearchGateway.vector(embedding)
    ↓
VectorGateway.search(namespace, embedding, model, top_k)
    ↓ 返回 VectorHit
转换为 SearchHit
```

也就是说，`SearchGateway.vector()` 本身没有独立的存储或召回逻辑，实际向量查询仍由 `VectorGateway.search()` 完成。

#### 4.2.3 为什么判为真正重叠

这不是“接口与实现”的关系，而是两个公开 Gateway 都暴露向量检索语义。它们的区别主要是参数完整度和返回模型字段名，不是独立能力。

主要风险：

- 直接调用 `SearchGateway.vector()` 时无法传 `namespace`、`model` 和 `filters`；
- 直接调用 `VectorGateway.search()` 时绕开统一检索审计和 RRF 结果模型；
- 模型版本隔离可能只在 VectorGateway 生效；
- 调用方可能绕开 `RrfHybridSearchGateway`，形成两条生产检索路径。

#### 4.2.4 当前可执行约束

1. 业务/RAG 只依赖统一 Search 入口；
2. `VectorGateway` 只作为 Search 实现内部的向量存储能力；
3. `RrfHybridSearchGateway` 负责关键词与向量的组合、显式降级和审计；
4. 不新增第四种检索 Gateway；
5. 是否最终删除 `SearchGateway.vector()` 或收敛 Hit 模型属于冻结契约变更，不能在本次审计中直接修改。

### 4.3 与两组重叠直接相关的实现文件

| 文件 | 作用 | 审计结论 |
| --- | --- | --- |
| `zhiyin-data-sdk/.../gateways/ai.py` | Knowledge/Search 契约和 Hit 模型 | 两套检索语义的主要重叠点 |
| `zhiyin-data-sdk/.../gateways/vector.py` | Vector 契约和 Hit 模型 | 与 Search.vector 重叠 |
| `zhiyin-infrastructure/.../local/knowledge.py` | 本地 Knowledge/Search 实现 | 显示 KnowledgeHit → SearchHit 的直接映射 |
| `zhiyin-infrastructure/.../pami/adapters.py` | PAMI Knowledge/Search 实现 | 显示 PAMI Search 对 Knowledge 的包装 |
| `zhiyin-infrastructure/.../search.py` | RRF 混合检索 | 显示 Search.vector 对 Vector.search 的包装 |
| `zhiyin-infrastructure/.../pgvector/__init__.py` | VectorGateway 的 pgvector 实现 | 正常的具体实现，不是重复契约来源 |
| `zhiyin-boot/.../container/gateways.py` | 根据配置选择并组合检索实现 | 正常的唯一装配点 |

| `InterventionPolicy` | `ConfiguredInterventionPolicy` | 判断是否允许主动干预，不发送通知 |

ABC 与默认策略实现共同存在是正常的策略模式。Policy 负责纯业务判断，Service/Worker 负责执行，不能为了减少文件而合并。

架构依据：`AGENTS.md:156-164` 和 `docs/开发指南.md:107-124`。

### 5.3 Facade 接口与实现：1 个能力簇

| 接口 | 实现 | 职责 |
| --- | --- | --- |
| `ApplicationFacade` | `DefaultApplicationFacade` | 为 Controller 聚合业务调用，并把结果交给 Mapper |

Facade 不能直接访问数据库、模型、知识库或鉴权 Gateway，也不能替代 Service。该分层保证 API 层不依赖 Data SDK。

架构依据：`AGENTS.md:219` 和 `docs/开发指南.md:47-71`。

### 5.4 数据访问和外部能力：17 个能力簇

#### 5.4.1 七个 Repository 能力

| 契约 | 本地/测试实现 | MySQL 实现 | 判定 |
| --- | --- | --- | --- |
| `ProfileRepository` | `InMemoryProfileRepository` | `SqlAlchemyProfileRepository` | 同一契约的两套后端 |
| `BehaviorRepository` | `InMemoryBehaviorRepository` | `SqlAlchemyBehaviorRepository` | 同一契约的两套后端 |
| `ConversationMemoryRepository` | `InMemoryConversationMemoryRepository` | `SqlAlchemyConversationMemoryRepository` | 同一契约的两套后端 |
| `AssetRepository` | `InMemoryAssetRepository` | `SqlAlchemyAssetRepository` | 同一契约的两套后端 |
| `TaskSessionRepository` | `InMemoryTaskSessionRepository` | `SqlAlchemyTaskSessionRepository` | 同一契约的两套后端 |
| `UserRepository` | `InMemoryUserRepository` | `SqlAlchemyUserRepository` | 同一契约的两套后端 |
| `RegistryRepository` | `LocalJsonRegistryRepository` | `SqlAlchemyRegistryRepository` | JSON/数据库两套后端 |

这些类的方法名相同是刻意的，因为契约测试必须能够对不同实现运行同一套断言。删除本地实现会破坏第一期独立运行和快速测试；删除 MySQL 实现会失去生产持久化能力。

#### 5.4.2 九个 Gateway 能力

| Gateway 契约 | 具体实现或组合实现 | 判定 |
| --- | --- | --- |
| `ObjectStoreGateway` | `LocalFileStore`、`MinioObjectStore` | local/生产替换点 |
| `RawQueryGateway` | `SqlAlchemyRawQueryGateway` | 受限数据库逃生口，只给基础设施使用 |
| `CacheGateway` | `InMemoryCache`、`RedisCacheGateway` | local/Redis 替换点 |
| `KnowledgeGateway` | `LocalKnowledgeRepo`、`PamiKnowledgeGateway` | 本地/PAMI 替换点；与 Search 存在跨契约重叠 |
| `SearchGateway` | `LocalKeywordSearch`、`PamiSearchGateway`、`RrfHybridSearchGateway` | 不同检索策略；契约与 Knowledge/Vector 有重叠 |
| `VectorGateway` | `LocalVectorStore`、`PgVectorGateway` | 本地/pgvector 替换点 |
| `LLMGateway` | `LocalOrMockLLM`、`PamiLLMGateway` | Mock/远程 API 替换点 |
| `EmbedGateway` | `LocalHashEmbedder`、`PamiEmbedGateway` | 骨架/远程 API 替换点 |
| `AuthGateway` | `DefaultPassAuth`、`PamiAuthGateway` | 本地/PAMI IAM 替换点 |

此处“同一个 Gateway 有多个实现”不是重复；真正的问题是 Knowledge、Search、Vector 三个 Gateway 之间边界交叉，已在第四章单独列出。

#### 5.4.3 一个事务能力簇

| 契约 | 实现 |
| --- | --- |
| `Transaction` / `TransactionManager` | `SqlAlchemyTransaction` / `SqlAlchemyTransactionManager` |

事务对象描述一次事务的生命周期，事务管理器负责创建/管理事务。二者属于同一个事务能力簇中的不同角色，不是重复类。

数据访问层分层依据：

- `AGENTS.md:42-43`：Data SDK 只放抽象，Infrastructure 放实现；
- `AGENTS.md:73`：Repository/Gateway/Transaction 只定义在 Data SDK；
- `docs/开发指南.md:197-242`：Data SDK 与 Infrastructure 的完整落位表；
- `AGENTS.md:274`：同一套 Port 契约测试覆盖本地和真实实现。

### 5.5 Worker 契约与执行者：1 个能力簇

共同契约：`zhiyin_kernel.worker.Worker`。

| Worker | 位置 | 类型 |
| --- | --- | --- |
| `ActiveEventWorker` | `zhiyin-business/workers` | 业务规则驱动 |
| `ImpactPropagationWorker` | `zhiyin-business/workers` | 业务规则驱动 |
| `VectorSyncWorker` | `zhiyin-infrastructure/workers` | 纯数据管道 |

三者共享一个最小 Worker 契约，但业务 Worker 与纯数据 Worker 分目录，符合“业务规则驱动进入 business，纯数据管道进入 infrastructure”的落位规则。

架构依据：`AGENTS.md:40`、`AGENTS.md:64`、`docs/开发指南.md:140-152`。

### 5.6 Boot 装配不是又一套业务能力

`zhiyin-boot/zhiyin_boot/container/gateways.py`、`repositories.py`、`services.py` 中出现和上述能力相同的名字，是在选择和连接实现，不是在重新实现能力。

正确链路示例：

```text
ProfileService（业务能力）
    ↓ 构造注入
ProfileRepository（数据访问契约）
    ↓ Boot 根据配置选择
InMemoryProfileRepository 或 SqlAlchemyProfileRepository
```

```text
RrfHybridSearchGateway（统一搜索实现）
    ├── keyword SearchGateway
    ├── EmbedGateway
    └── VectorGateway
```

架构依据：`AGENTS.md:44`、`AGENTS.md:90`、`docs/开发指南.md:429-447`。

## 六、项目全局中容易误判的三组契约

以下三组不是袁明阳提交中新增的，但因为前次问题涉及 `orchestration`、`data-sdk`、`infrastructure`，在本审计中一并说明。

### 6.1 EventBus 与 EventBusGateway

| 层 | 契约 | 职责 |
| --- | --- | --- |
| Orchestration | `EventBus`、`DomainEvent` | 业务事件语义、统一信封、订阅和幂等 |
| Data SDK | `EventBusGateway` | 最小传输能力：event type + payload |
| Orchestration 实现 | `GatewayEventBus` | 将 DomainEvent 单向映射到传输契约 |
| Infrastructure | 内存/Kafka 实现 | 实际消息投递 |

业务层必须发布 `DomainEvent`，不能直接调用 `EventBusGateway`。因此两层不能直接删除任意一层。

### 6.2 Scheduler 与 SchedulerGateway

| 层 | 契约 | 职责 |
| --- | --- | --- |
| Orchestration | `Scheduler`、`ScheduleSpec` | 调度语义、业务策略和事件触发 |
| Data SDK | `SchedulerGateway`、`ScheduledTask` | 外部调度设施的最小注册/取消能力 |
| Orchestration 实现 | `GatewayScheduler` | 语义模型到传输模型的映射 |

### 6.3 Notifier 与 NotifyGateway

| 层 | 契约 | 职责 |
| --- | --- | --- |
| Orchestration | `Notifier`、`NotifyMessage`、`NotifyDelivery` | 通知语义与业务可见结果 |
| Data SDK | `NotifyGateway`、`NotifyResult` | 外部通知平台传输能力 |
| Orchestration 实现 | `GatewayNotifier` | 单向映射和结果转换 |

### 6.4 为什么这三组允许存在

`docs/开发指南.md:353` 明确允许唯一一种双层契约形态：

```text
语义契约 + 传输契约
```

条件是：

1. 语义规则只在 Orchestration；
2. 传输契约保持最小；
3. 只能由单向适配器映射；
4. 业务层不得直接依赖传输 Gateway；
5. 不得再增加第二套事件、调度或通知抽象。

架构最终评审 C2 也明确指出这类双份契约存在字段分叉风险，因此应“保留但克制”，而不是继续扩展。

## 七、Kernel 为什么没有修改

### 7.1 Kernel 的“数据模型”不是数据库表模型

Kernel 保存的是跨层共享业务形状，例如：

| 文件 | 已有模型 |
| --- | --- |
| `zhiyin_kernel/blackboard.py` | `ProfileField`、`ProfileGap`、`Profile`、`BehaviorLog`、`ConversationMemory`、`AssetVersion`、`TaskSession` |
| `zhiyin_kernel/assets.py` | `Report`、`DirectionPlan`、`ActionPlan`、`TrackEvent`、`Achievement`、`CalendarNode` |
| `zhiyin_kernel/identity.py` | `ProfileSummary`、`UserAccount`、`AuthSession`、`GuestSession` |
| `zhiyin_kernel/registry.py` | `TheoryCard`、`OutputContractSpec`、`AgentDescriptor`、`PolicyParamSet`、`TaskEntrySpec` |
| `zhiyin_kernel/dynamic_content.py` | 菜单、路由、文案、横幅、信任块、FAQ 形状 |
| `zhiyin_kernel/enums.py` | 环节、资产、行为、身份、任务、通知等跨层枚举 |
| `zhiyin_kernel/worker.py` | 业务和基础设施共同依赖的最小 Worker 契约 |

这些模型在第一期开始前已由架构外壳提交建立。第一、二期实现直接引用即可，不需要复制或改名。

### 7.2 复用证据

袁明阳修改过的 115 个文件中，当前有 **40 个文件直接引用 `zhiyin_kernel`**，包括：

- 业务 Port、Policy、Service 和 Worker；
- API Controller、Facade、Mapper；
- Data SDK Repository；
- 内存 Repository 和 MySQL Repository；
- PAMI 适配器、持久化模型和向量同步 Worker；
- 契约测试与端到端测试。

因此“Kernel 没改”不等于“没有使用 Kernel”，而是复用了已有公共模型。

### 7.3 ORM Row 为什么放 Infrastructure

`zhiyin-infrastructure/zhiyin_infrastructure/persistence/models.py` 中的：

- `ProfileRow`
- `BehaviorLogRow`
- `ConversationMemoryRow`
- `AssetVersionRow`
- `TaskSessionRow`
- `UserAccountRow`
- `AuthSessionRow`
- `EmbedTaskRow`
- `RetrievalLogRow`

描述的是表名、列类型、主键、索引和数据库约束，是 SQLAlchemy 持久化模型，不是跨层业务模型。

例如：

```text
Kernel Profile
    ↓ Repository 契约的输入/输出
SqlAlchemyProfileRepository
    ↓ 映射
Infrastructure ProfileRow
```

`Profile` 与 `ProfileRow` 字段相近属于“业务对象—数据库行”的正常映射，不是重复契约。把 `ProfileRow` 放进 Kernel 反而会导致 Kernel 依赖 SQLAlchemy，直接违反零依赖规则。

### 7.4 EmbedTask 与 RetrievalLog 为什么也不进 Kernel

| 类型 | 当前作用域 | 当前落位判断 |
| --- | --- | --- |
| `EmbedTask` / `EmbedTaskRow` | 向量同步内部任务状态 | Infrastructure 内部模型，正确 |
| `RetrievalLogRow` / `RetrievalLogStore` | 检索审计与评估落库 | Infrastructure 内部模型，正确 |
| `CrawlReport` / `ReviewDecision` | 数据采集、审核管道内部结果 | Infrastructure 内部模型，正确 |

这些形状目前没有作为业务 Port、API DTO 或跨包公共契约向外传递，因此不满足进入 Kernel 的条件。

### 7.5 什么情况下第三期需要修改 Kernel

只有当第三期正式出现一个被多个层共同引用的稳定业务形状，例如：

- 业务 Service 和 API 都要返回统一的检索证据；
- 诊断、决策、行动环节共同消费统一 Citation；
- 资产版本需要持久化并公开统一的证据引用；
- 生产方和消费方目前准备各自复制同字段模型；

此时才应评估在 Kernel 增加类似 `RetrievalEvidence` 或 `Citation` 的共享形状。

但 Kernel、业务 Port、Data SDK Gateway 都是冻结契约。增加公共模型前必须先说明：

1. 生产方；
2. 消费方；
3. Repository/Gateway/API 是否需要变化；
4. 数据库是否需要迁移；
5. OpenAPI 和前端类型是否受影响；
6. 兼容旧资产和旧记录的方式。

不能仅因为“Kernel 应该放数据模型”就把 ORM Row、Gateway Hit 或内部任务对象迁入 Kernel。

## 八、结构相似但不属于真正重复的部分

### 8.1 内存 Repository 与 MySQL Repository

七组 Repository 方法高度相似是 Port 多实现的直接结果。它们分别服务：

- 本地开发、单元测试和第一期独立运行；
- 第二期真实数据库持久化。

判断标准不是代码行是否相似，而是能否在 Boot 中互换且通过同一套契约测试。

### 8.2 Local/PAMI/真实基础设施适配器

以下都是规定的替换点：

- `LocalFileStore` / `MinioObjectStore`；
- `InMemoryCache` / `RedisCacheGateway`；
- `LocalVectorStore` / `PgVectorGateway`；
- `LocalOrMockLLM` / `PamiLLMGateway`；
- `LocalHashEmbedder` / `PamiEmbedGateway`；
- `DefaultPassAuth` / `PamiAuthGateway`。

这些实现不能通过“合并文件”解决，因为它们连接不同外部系统、依赖不同配置并具有不同故障模式。

### 8.3 Kernel 模型与 API View DTO

Kernel 表达业务公共形状，API DTO 表达前端视图和统一响应。Mapper 是唯一转换点。两者字段可能相似，但不能让 API 直接把数据库或业务内部模型裸露出去。

### 8.4 Kernel 模型与 ORM Row

Kernel 模型负责跨层语义；ORM Row 负责数据库物理结构。二者必须映射，不能共用 SQLAlchemy 类。

### 8.5 测试 Fake 与生产实现

`FakeRedis`、`FakeVectorPool`、`FakeKeywordSearch` 等只存在于测试中，用于隔离外部依赖，不属于生产能力重复。

## 十、治理建议与禁止事项

### 10.1 当前可以做且不改变冻结接口

1. 在第三期设计和业务调用规范中指定 `SearchGateway` 为统一检索入口；
2. 将 `KnowledgeGateway` 定位为 PAMI/知识库底层检索能力；
3. 将 `VectorGateway` 定位为向量存储和原始召回能力；
4. 统一由 `RrfHybridSearchGateway` 处理 Embedding、向量召回、RRF、显式降级和审计；
5. 增加架构测试，禁止业务 Service 同时直接依赖 Knowledge/Search/Vector 三者；
6. 在文档中统一“知识库检索”“统一搜索”“向量存储”的术语。

### 10.2 需要确认后才能做

1. 删除或改名 `KnowledgeGateway`、`SearchGateway`、`VectorGateway`；
2. 删除 `SearchGateway.vector()`；
3. 合并 `KnowledgeHit`、`SearchHit`、`VectorHit`；
4. 在 Kernel 新增检索证据公共模型；
5. 修改 Boot 能力位名称或数量；
6. 改变 PAMI、pgvector 的调用边界；
7. 修改 OpenAPI、业务 Port 或数据库语义。

### 10.3 明确禁止

1. 为了隐藏重叠再新增第四个检索 Gateway；
2. 在业务层复制 `SearchHit` 或 `VectorHit`；
3. 让业务 Service 直接创建 PAMI、pgvector 或 SQLAlchemy 实现；
4. 把 ORM Row 放入 Kernel；
5. 让 API 直接 import Data SDK；
6. 用临时兼容层或静默降级掩盖接口边界不清；
7. 为了减少文件删除 local/测试实现或放宽架构守卫。

## 十一、最终审计结论

| 问题 | 结论 |
| --- | --- |
| 袁明阳正式提交触达多少唯一文件 | 115 个 |
| 其中 Kernel 文件多少 | 0 个 |
| 是否完全没有使用 Kernel | 否；当前有 40 个已触达文件直接引用 Kernel |
| 正常分层能力有多少 | 35 个能力簇 |
| 真正语义重叠有多少 | 2 组，均在检索领域 |
| Event/Scheduler/Notifier 是否重复 | 不是；属于语义契约与传输契约分层 |
| ORM Row 是否应放 Kernel | 不应；必须留在 Infrastructure |
| 第三期是否应继续增加检索抽象 | 不应；先固定唯一业务入口 |
| 能否现在直接删除重复接口 | 不能；它们是冻结契约，需要影响分析和确认 |

最终判定：**袁明阳的绝大多数改动符合现有分层架构；代码量看起来分散，主要是接口、实现、装配和验证的规定分层。真正需要架构治理的不是 115 个文件本身，而是 Knowledge/Search/Vector 之间的两组检索语义交叉。Kernel 未修改符合当前职责边界，不构成漏做。**
