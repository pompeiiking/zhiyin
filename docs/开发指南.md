## 一、先用一句话理解这个架构

> 代码分成「外部边界」和「业务内圈」两部分。
> **外部边界**（契约 + 实现 + 装配）只做一件事：让第二期的八个替换点各只改一处。
> **业务内圈**按五环节纵切，一人一列，列内自成工作单元。

八个替换点：MySQL、Kafka、pgvector、SSE、MinIO、Redis ZSET、pami IAM、真实模型。

**最重要的认知转换**：以前你找功能是「找文件夹」，现在要「找链条」。一个功能会横跨 4–6 个包，没有一个文件夹叫它的名字。

## 二、八个包各干什么

| 包 | 角色 | 一句话职责 | 只允许依赖 |
| --- | --- | --- | --- |
| `zhiyin-api` | 接入层 | HTTP 进出、DTO 转换、统一信封 | 业务发布面（+ 共享形状） |
| `zhiyin-business` | 业务内圈 | 职引的业务规则、领域行为、五环节 | 编排层 + 数据契约 + 共享形状 |
| `zhiyin-orchestration` | 通用能力 | 六原语：Agent / Workflow / EventBus / Schedule / State / Notify | 数据契约 + 共享形状 |
| `zhiyin-data-sdk` | 数据契约 | 只定义 Repository / Gateway 抽象，**不实现** | 共享形状 |
| `zhiyin-infrastructure` | 外部世界 | 契约的具体实现：local / mysql / pami / kafka | 数据契约 + 共享形状 |
| `zhiyin-boot` | 装配 | 唯一决定「用哪套实现」，并把服务接上 | 全部 |
| `zhiyin-web` | 前端 | Vue 3 + Vite，三栏对话页与工作台 | — |
| 共享形状 | 横切 | 跨层共用的枚举与数据形状 | 仅自身 |
| `data/` | 动态资源 | 文案 / 智能体 / 理论卡 / 产出契约 / 开关 | — |

> **已按建议落地**：共享形状已从 `zhiyin-data-sdk/zhiyin_data_sdk/contracts/` 迁出为独立包
> `zhiyin-kernel/zhiyin_kernel/`，并且**零依赖**（不得 import 任何其它 `zhiyin_*` 包），
> 由 `tests/test_architecture.py::test_kernel_has_no_dependencies` 守卫。

## 四、如何对齐（四条规则）

「对齐」指：层与层之间传递的东西，双方理解必须完全一致。靠这四条保证。

### 规则 1 · 契约对齐：五类契约各有唯一归属

| 契约类别 | 唯一归属 | 内容 |
| --- | --- | --- |
| 共享形状 | `zhiyin-kernel/zhiyin_kernel/` | 跨层枚举、画像 / 资产 / 身份 / 动态资源的数据形状（零依赖，**不得** import 其它 zhiyin 包） |
| 数据访问契约 | `zhiyin_data_sdk` | Repository / Gateway / Transaction 抽象 |
| 语义编排契约 | `zhiyin_orchestration` | EventBus / Scheduler / Notifier / State / Agent / Workflow |
| 业务产出契约 | `zhiyin_business.contracts` | 五环节 `*Output` |
| 对外发布面 | `zhiyin_business.published` | api 可见的读模型与枚举 |

**同一能力不得在两处定义。** 若必须同时存在，只允许「语义契约 + 传输契约」这一种形态，且字段由单向适配器映射。
`test_no_duplicate_contract_definitions` 会拒绝任何与内核同名的 class 影子定义。

### 规则 2 · 数据形状对齐：双方引用同一个模型

生产方和消费方不各写一份。比如 `TaskSession` 只有一份（在 `zhiyin_kernel/blackboard.py`），生产它的 Repository 和使用它的 Loop 引用同一个类。**新增跨层数据时，先加到共享形状，再在两边引用它。**

### 规则 3 · 枚举对齐：所有跨层枚举只在 `zhiyin_kernel/enums.py`

`LoopStage` / `AssetType` / `BehaviorEventType` / `TaskStatus` 等，全仓只有一处定义。新增枚举值直接加在那里，不要在业务层另建同义枚举。

### 规则 4 · 动态资源对齐：JSON 与代码的交叉引用必须闭合

这条**目前没有守卫，是个已知隐患**。约定：

- `task_entries.json` 里每个 `lead_agent` 必须能在 `agents.json` 找到
- `agents.json` 里每个 `output_contract_id` 必须能在 `output_contracts.json` 找到
- 代码里引用的 `agent_id` / `task_code` 必须与 JSON 一致

一旦对不上，系统**不会报错，而是静默回落**（例如主理展示名退化成 agent_id 本身）。建议补一条守卫：解析 `data/registry/*.json`，校验上述交叉引用完整。

## 五、如何对接（装配机制）

### 5.1 唯一装配点

`zhiyin-boot/container/` 是**全系统唯一决定「用哪套实现」的地方**。装配顺序固定：

```text
container/gateways.py       外部能力：模型 / 嵌入 / 向量 / 缓存 / 知识 / 对象 / 事件 / 调度 / 通知 / 鉴权
   ↓
container/repositories.py   数据访问：7 个 Repository + 事务 + 动态资源
   ↓
container/services.py       build_orchestration：把 Gateway 包装成业务面向的语义原语
   ↓
container/services.py       build_services / build_workers：服务与异步执行者
   ↓
container/__init__.py       wire_application：挂路由 + 上报装配状态 + lifespan 启停
```

**换实现的唯一动作就是改这张装配表。** 如果某次替换需要动业务代码，说明分层被破坏了。

新增一个 Worker 同样只改装配：

```python
# zhiyin_boot/container/services.py::build_workers
container.workers.append(ImpactPropagationWorker(container.asset_service))
```

注册后由 lifespan 统一启停；成长期用 `python -m zhiyin_boot worker impact` 独立部署，
**部署形态变了，代码不变**。

### 5.2 依赖注入方式：构造注入，不用全局单例

服务通过构造函数拿到依赖。业务层从不自己 `new` 一个 Repository —— 它只接收。

**两个已知的注册点例外**（因为 api 不允许依赖 boot）：

| 注册点 | 位置 | 用途 |
| --- | --- | --- |
| `configure_facade()` | api | boot 启动时把 Facade 实现注入 api |
| `configure_runtime()` | api | boot 启动时把装配报告注入 api，供 `/healthz` 读取 |

这两个是「单向依赖」逼出来的设计，不是缺陷。

### 5.3 层间通信只有两种方式

1. **同步调用**：上层直接调下层的方法（api → business → orchestration）。
2. **异步事件**：通过 `EventBus` 发布，**发布方不知道订阅方是谁**。

第 2 种是「环节之间解耦」的关键。比如画像字段更新后发 `profile_field_updated`，资产影响面传播订阅它 —— 更新画像的代码完全不需要知道资产服务存在。**跨环节协作优先用事件，不要互相调用。**

### 5.4 启动与自检

```bash
cd zhiyin-src/template

python -m zhiyin_boot                    # 启动，http://127.0.0.1:8000/docs
python -m zhiyin_boot --check            # 只做装配检查，打印报告，恒退出 0
python -m zhiyin_boot --check --strict   # 全绿门禁：有未装配部件则退出 1
python -m zhiyin_boot --check --phase=1  # 里程碑门禁：只校验 M1 的退出条件
python -m zhiyin_boot --check --phase=2  # M2：业务主干端到端
python -m zhiyin_boot worker impact --once   # 手动跑一轮某个 Worker
```

`/healthz` 返回 `status: ok|degraded` 与逐部件状态。**`degraded` 不等于启动失败**，它表示有部件还是骨架，`assembly.missing` 会列出缺口与归属。

**门禁为什么分级**：`healthy: true` 只有一个含义（全绿），无法表达"框架已就绪但业务未接"，
于是第一期长期处于"未达标"，信号失去价值。分级后 CI 可以精确卡口：
`--phase=1` 本期必须过，`--phase=2` 是下一阶段的退出条件。

## 六、一个功能要改哪几个文件（走位示例）

需求：**用户上传简历 → 解析成结构化信息 → 写入画像**

| 顺序 | 层 | 改什么 | 为什么在这里 |
| --- | --- | --- | --- |
| 1 | 共享形状 | 加 `Resume` 数据形状 | 要被多层引用 |
| 2 | 数据契约 | 加 `ResumeParserGateway(ABC)`，只写签名 | 解析是外部能力，业务层不许直调模型 |
| 3 | 基础设施 | 加 `local/resume.py` 实现 | 具体实现只在这里；换真实解析服务只改这格 |
| 4 | 业务 | 加 `ResumeService`，写「解析结果怎么变成画像字段、置信度给多少」 | 业务规则只有职引有 |
| 5 | 接入 | 加路由 + DTO + Facade 方法 | 只做转换 |
| 6 | 装配 | `container/gateways.py` 注册第 3 步的实现 | 唯一认识所有实现的地方 |

**注意第 4 步里没有「解析简历」这个动作** —— 它只写「解析完的结果怎么办」。解析动作在第 3 步。

这就是分层的实质：**同一个功能被拆成「规则」和「能力」两半，规则在业务层，能力在外部边界。**

## 七、找路速查表

**看到不认识的代码，先问三个问题**：

1. **它 import 了谁？** import 越少，位置越靠下（共享形状一个都不 import）。
2. **它是 ABC 还是实现？** 有 `(ABC)` 的是契约，没有的是实现。两者永远在不同包里。
3. **是谁 new 它的？** 谁负责 new，谁就在装配层附近。

**看名字定位**：

| 你看到这个 | 它在哪 | 依据 |
| --- | --- | --- |
| `class XxxRepository(ABC)` | 数据契约 | 实现必然在 infrastructure |
| `class XxxGateway(ABC)` | 数据契约 | 外部能力的抽象 |
| `class XxxService(ABC)` | 业务层 `ports/` | 实现就在同层 `services/`，规则在 `policies/` |
| 目录 `local/` `mysql/` `pami/` | 基础设施 | 一个目录一套实现 |
| 只有字段没有方法的 `BaseModel` | 共享形状 | 跨层共用 |
| 纯 `Enum` 类 | 共享形状 | 跨层共用 |
| `raise NotImplementedError` | 骨架，还没实现 | `--check` 会告诉你 |
| `IMPLEMENTATION_STATUS = "skeleton"` | 骨架，且已自报家门 | `/healthz` 会标出来 |
| `*_controller.py` / `*_dto.py` | 接入层 | 不该有业务判断 |
| `container/` 里的 `build_*` | 装配点 | 换实现改这里 |

## 八、不可违反的五条底线

1. **业务层不直接 import 具体实现**（只能通过契约）。这一条单独守住，就能保住全部八个替换点。
2. **不建 `utils` / `common` / `helpers` / `shared` 这类通用包**（`business/shared/` 是明确的共享面，例外）。通用依赖按「收编根不收编枝、收编实现不收编调用点」处理。
3. **动态资源不进代码**：文案、任务入口、智能体、理论卡、产出契约、功能开关一律走 `data/registry/`。
4. **编排层不出现业务语义**（五环节 / 画像 / 主理），由 AST 守卫强制。
5. **基础设施不得引用业务层与编排层**，由 AST 守卫强制。
