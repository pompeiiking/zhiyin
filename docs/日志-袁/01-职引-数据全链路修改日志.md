## 十六、2026-09-19 15 维呈现口径定案：只给证据等级，不给分值（本轮追加）

本节记录一个**冻结契约变更**及其依据。触发问题是"为什么那批可视化 CSS 会被删掉"，查到底后发现根因不是"没有预留接口"，而是**契约里没有分数字段、当年前端只好自己编**。拍板结果见《业务口径决策记录》**决策 17**。

### 16.1 事实核对（先摆证据，再定口径）

| 问题 | 核对结果 |
| --- | --- |
| 15 维有没有契约？ | **有**。`zhiyin_kernel/assets.py::ReportDimensionGroup`（`SELF-PORTRAIT`/`JOB-MARKET`/`DECISION-RISK`）与 `ReportDimensionItem`；`Report.dimensions` 是其列表 |
| 运行期真的产出吗？ | **真的**。查容器内 MySQL `report.payload`：1 份报告、3 组、**6 + 5 + 4 = 15 条**，每条带 conclusion 与 evidence |
| PRD 要求什么？ | `FR-DIAG-001`（P0）："输出自我画像 6 维 / 职业环境 5 维 / 决策与风险 4 维，**每维有结论与证据引用**"——**没有分值要求** |
| 契约里有分值吗？ | **没有**。`ReportDimensionItem` 只有 `index/name/tag/conclusion/evidence`；`Verdict` 只有 `title/summary` |
| 那被删的样式在渲染什么？ | **编造的分数**。旧模板 `radarTarget = [82, 82, 78, 80, 75, 76]`、`matchScore` 取自 `agents.analysis?.matchScore`（前端 store 臆造）、`.ov-ring` 用 `--score: matchScore * 3.6deg` |
| 设计要求呢？ | 《前端改版需求说明》§2「**15 维热力图或雷达图**」；该文件 §1 自己也写了"若实现新界面需要新数据，按 §9.3 提出"——即规定了正确走法：**先提数据需求、定契约，再实现**，而不是前端编数字 |

**结论**：缺的不是"接口"，是**一个数值轴**；而 PRD 从未要求该数值轴。所以正确解法不是补分数字段，而是换一个**报告能自证**的轴。

### 16.2 定案内容

1. **新增内核枚举** `zhiyin_kernel/enums.py::DimensionEvidenceLevel`（英文值 + 中文注释，沿用 `PlanRole` 范式）：
   `confirmed`（字段或检索证据直接支撑、可溯源）/ `partial`（有支撑但证据链不完整）/ `pending`（有线索未确认）/ `missing`（无任何证据）。
2. **收紧冻结字段**：`ReportDimensionItem.tag` 由自由字符串改为该枚举。实测模型原本产出 **11 种措辞**（已确认/待验证/未定义/缺失/待确认/部分匹配/无依据/严重不足/未知/低/未建立），既无法上色，又把"证据够不够"和"这一维好不好"混在一句里。
3. **模型受强制约束**：`output_contracts.json` 的 `json_schema` 为空，`loop.py::_output_schema` 回落到 `model_json_schema()`，因此枚举自动进到发给模型的 Schema（实测 `$defs.DimensionEvidenceLevel.enum` 已生效）。
4. **提示词补四档语义**：`services/loop.py::_STAGE_DUTIES[DIAGNOSE]` 明确写出四档判据，并强调"tag 只表示证据够不够，好坏写在 conclusion 里"。
5. **前端**：报告页新增「15 维证据覆盖」热力图（等级色块 + 悬停出结论与证据 + 四档计数）；四档中文名按既有 `ROLE_LABELS` 范式在前端映射；明细列表的 tag 也改走等级中文名。
6. **不做雷达图**：需求写的是"热力图**或**雷达图"，选热力图即在授权内；雷达半径必须是数值，用四级等级硬撑会制造假精确。

**定案**：`Report` 增加 `profile_snapshot: list[ProfileField]`——`ProfileField` 已是内核形状，**不需要新造**。②诊断生成报告时把**当次所用画像**冻结进去（构造点 `orchestrator.py` 里 `profile` 变量本来就在手边，正是本次诊断用的那一份）；`mappers.report_full_text_view` 在快照非空时追加 `profile` 章节；前端渲染为「本版本生成时的画像快照」并显示生成日期。旧报告该字段为空 → 不生成章节，**向后兼容、无需数据迁移**。

**为什么"快照"是这件事的关键**：报告是版本化只读资产、画像是活状态。实时读会让用户在 v1 报告里看到今天的画像，与工作台对不上——这正是原记里识别出的风险，只是原记的结论（不做画像）选错了方向。

## 十九、2026-09-19 D7 代码侧收口：④JD 过期下架、⑥溯源到版本、⑦检索基准

### 19.1 ④ JD 过期与下架机制

设计口径（第三期设计 §4.3）：已过截止时间、来源下架、连续复核失败的记录必须标记 `expired`，不得作为"现在可以申请"的证据；历史 JD 可保留用于要求分析，但要明确标记为历史样本。

**核心判断**：`_visible()` 早已让过期文档**查不出来**，但记录本身仍是 `enabled`——于是"过期内容不能进入生产索引"**在索引侧不成立**（向量库仍留着它），报表与审计也看不出它已过期，只剩"查不到"这一个现象。所以要**落状态**，不能只靠查询过滤。

| 触发 | 实现 |
| --- | --- |
| 已过截止时间 | `RetrievalDocumentStore.expire_due()`：`status=enabled` 且 `expire_at <= now` → `expired`，并写 `expired_reason` / `expired_at` / **`historical_sample=True`** |
| 来源下架 | `RetrievalDocumentStore.expire_by_source(source_id)`：供采集/治理流程调用（来源台账的 `removal_method` 就是按 `source_id` 下架） |
| **连续复核失败（未做）** | 依赖"复核"流程本身，而招聘来源的条款/robots/频率/保存期审核尚未完成。在复核机制落地前实现只能靠猜，故留空并在模块 docstring 写明**不做看起来有、实际没有的东西** |

**落位**：`infrastructure/workers/document_expiry.py`。它是纯数据治理管道（扫表落状态、无业务判断、无阈值、不发通知），按《AGENTS.md》§3 属 `infrastructure/workers`（与 `vector_sync` 同类），因此**不需要新增跨层 Port**。

**新增能力位必须整体同步**（§5/§11）——这是本轮真正花时间的地方：`WORKER_PORTS`、`build_workers` 装配（与 `vector_sync` 分开装配：过期治理不该因为向量链路没开而停摆）、`assembly_gates.json` phase 3/4 的 `require.workers`、`ownership.json` 归属、以及三处守卫登记（`WORKER_SHELL` 落位表、`SKELETON_PORTS` 基类、**`PORT_NOT_A_CONTAINER_FIELD`**——worker 按自身 `name` 寻址、不是 container 字段）。另有一条文档守卫顺带抓到了《开发指南》里"3 Worker"的硬编码计数，已改为 4。

### 19.2 ⑥ 检索引用溯源：补上**版本**

**已就绪的部分**（复核确认，无需改动）：`RetrievalEvidence` 自带 `source_id` / `source_url` / `version`；`_report_sources()` **已经做引用核对**——模型自述的来源必须出现在证据包里才允许进入资产。

**真正的缺口**：`Report.sources` 只是一串来源字符串，而权威文档的唯一键是 `(namespace, source_id, version)`——**没有版本就指不到具体那一版**，"可追溯"只做到一半。故新增 `Report.source_versions: dict[str, int]`（纯增量、有默认值、向后兼容），由 `_report_source_versions()` 从证据里取：

- 键的取法与 `_report_sources` **完全一致**（`source_url or source_id or evidence_id`）——否则两个字段对不上，反而更难查；
- 同一来源出现在多版证据里时取**最大版本**（报告依据的是它当时看到的最新一版）；
- 测试直接锁这条不变式：`set(Report.sources) ⊆ set(Report.source_versions)`。

### 19.3 ⑦ 检索质量基准：跑起来了，而且知道为什么这个数字不能用

`evaluate_retrieval()`（Recall@K / MRR）此前**在仓库里没有任何调用方**——指标算得出来、没人跑，于是"达到质量门槛"这条一直悬着（又一个"看起来有、实际没有"）。本轮接上可执行入口 `scripts/eval_retrieval.py` 并跑出基准，报告见《[职引-检索质量基准](../数据全链路/04-实施与验收/职引-检索质量基准-2026-09-19.md)》。

**实测（100 例，top_k=10，本地关键词通道）**：`Recall@K = 0.0000`、`MRR = 0.0000`、**期望 id 覆盖率 = 0/100**。

**这个 0 不是质量结论**，而是两个各自独立的原因：

1. 评测集的 `expected_ids` 指向一份**"测试知识快照"，而该快照从未落地**（`data/evaluation/` 下只有评测集与 schema，全仓搜不到第二个引用）；
2. **id 口径不一致**——发现的新缺陷：评测集期望一律写 `namespace:id`，而 `LocalSearchGateway` 返回**裸 id**。影响不止评测：同一篇文档在关键词通道与向量通道里 `evidence_id` 不同，**RRF 融合的去重键就是它**，于是同一篇文章会被当成两篇、重复证据挤占 `top_k`。已登记为[待决问题 D11](../数据全链路/04-实施与验收/职引-待决问题与改法选项-v1.0.md)（改它会同时动引用核对与跨通道融合，属需评审的检索契约调整）。

脚本还带一条**状态记录型测试**：一旦内容/快照就位、或 id 口径被统一，用例立刻变红，提醒出新的基准并冻结门槛——避免这件事再次悬空。

### 20.2 顺手修掉一个真缺陷：降级"不可分辨"

原来两条通道的故障处理都是 `except Exception: degraded.append("<通道>")`，**异常被整个吞掉**。于是"向量维度配错"（改配置就好）与"向量库宕机"（要重启依赖）在结果里长得一模一样。现新增 `metadata["retrieval"]["degraded_reasons"]`：

- **只写异常类名，不写异常消息**——消息可能带 DSN、口令、上游地址，而检索 metadata 会随报告与接口响应外流（《AGENTS.md》§10）。类名已足够区分两类故障，细节按类名去查日志；
- 落点是 `RetrievalEvidence.metadata`（自由字典），**不动冻结的 `EvidencePacket`**（它的 `degraded_channels` 是"按 namespace 的失败清单"，与本字段不是一回事）。

2. 但**线上检索恒空**是另一个、更靠前的病根——已登记为新问题 **D13**：**权威回填静默丢弃全部命中，"没有内容"与"内容都不权威"不可分辨**（`degraded=False`、结果就是空列表，调用方无从区分）。这与《AGENTS.md》§5/§10"降级必须可识别"直接相关；

## 二十四、2026-09-19 D13 落地（按建议选改法 A）：权威门挡掉的命中不再"静默变空"

### 24.1 问题回顾（为什么必须修）

`RrfHybridSearchGateway` 在返回前做权威回填：命中必须能在 `retrieval_document` 里找到才算数。权威表为空时**每一条**都被丢掉，返回一个空列表——而它与"确实没有命中"**完全同形**：`degraded=False`、审计里看不出、`/healthz` 正常。这正是真实报告 `sources` 为空的原因，也是《AGENTS.md》§5/§10 明令禁止的"静默降级"。

### 24.2 改了什么（**零 schema 变更**）

| 落点 | 改动 |
| --- | --- |
| `RetrievalDocumentStore.hydrate()` | 返回值由裸列表改为 `HydrationOutcome(hits, checked, dropped)` + `all_dropped`——把**丢弃量**交出去 |
| `RrfHybridSearchGateway` | 丢弃量写进两处：幸存命中的 `metadata["retrieval"]["dropped_non_authoritative"]`；审计 `degraded=True` |
| 测试 | 全丢光 → 审计必须 `degraded=True`；部分丢 → 幸存命中带计数；没丢 → **不得**标降级（避免"到处都降级"而失效） |

**为什么整条链路一条都没幸存时还能被发现**：`metadata` 挂在命中上，没命中就没处写——所以**审计是主通道**，metadata 只是补充。用例把这两种情形都锁上了。

**为什么没做成"在 store 上记一个 `last_dropped` 属性"**：容器里同一个 store 被并发请求共享，那样读到的可能是别人那一次的丢弃数（串味）。改成返回值最干净。

### 24.3 为什么**不加** `retrieval_log` 的列（一个刻意的克制）

理想情况是把"通道故障"与"权威门挡"在审计里**分别**记成两个字段。但那需要给 `retrieval_log` 加一列，而：

1. 这是**数据库语义变更**，《AGENTS.md》§2/§11.2 要求先确认；
2. 更现实的风险：本项目 `DatabaseContext.ensure_ready()` 用的是 `Base.metadata.create_all`，它**只建缺失的表、不给已有表加列**；运行中的容器若没跑迁移就写入新列，插入会失败——而审计写失败会让**检索本身**失败。为一个可观测性改进去冒"检索挂掉"的风险不值得。

所以本轮只做零 schema 变更的最小改动：`degraded=True` 已足以回答"这次空结果是不是被门挡掉的"，只是暂时无法与"通道故障"在日志里自动区分（现只能靠"有没有通道故障"反推）。**加列这件事登记为待确认项**，见 D13 条目的"残留"。

### 24.4 实测（前后对照）

| 时点 | `retrieval_log` |
| --- | --- |
| 改动前 | 46 行**全部** `degraded=0`，其中多行 `命中=0`——即"被门挡掉"看起来与"没命中"一模一样 |
| 改动后 | 同一次真实检索（真实装配的网关，返回 0 条）写入的新行为 **`degraded=1, 命中=0`** |

复跑方式：容器内 `python /tmp/d13_live_verify.py`（先 `docker cp`），它会打印最新审计行并断言 `degraded=1 且 命中=0`。

### 24.5 验证

`pytest` **480 passed / 1 skipped**（新增 3 条 D13 用例）；`ruff` 全绿；OpenAPI 一致；容器内重建后 `/healthz` 仍为 `status=degraded`、`demo_content=["search"]`、`missing=[]`；审计前后对照见 §24.4。

### 25.3 转换桥的实现与落位

## 二十七、2026-09-19 让检索证据真正到达模型：内容登记进权威表 + 修掉两个只有"真接上"才会暴露的缺陷

### 27.1 病根：权威表**从来没有生产方**

`retrieval_document` 是检索的权威来源——`RrfHybridSearchGateway` 返回前调
`RetrievalDocumentStore.hydrate()`，命中在这张表里找不到就**整条丢弃**。而这张表此前
**没有任何代码写入**（全仓只有测试与装配引用它）。于是：

- 无论关键词通道多准、向量库多空，**命中都会被丢光**（D13 已让这件事在审计里可见：`degraded=1, 命中=0`）；
- 模型**拿不到任何检索上下文**，只能靠通用知识作答；
- 引用溯源无从谈起（没有权威行就没有版本、没有出处）。

这正是 §19.3 基线报告里"语料从未落地"的真正含义。本轮补上这条链路。

### 27.2 三步改动

| 步 | 落点 | 内容 |
| --- | --- | --- |
| ① 命名约定 | `zhiyin_infrastructure/pami/doc_naming.py`（新增） | 平台不回文档 id（响应只有 `kb_name/title/snippet`），所以**文件名必须能反解出 `(namespace, id)`**。约定写在**一处**、导入侧与检索侧共用：`<ns>_<id>.txt` 与 `<ns>_card_<id>.txt`；反解不了返回 `None`（调用方回落内容哈希，**不猜**） |
| ② 来源回填 | `pami/adapters.py` | PAMI 命中按 ① 反解出 `source_id`，`evidence_id` 直接用 `namespace:id`——**与权威表主键同形**，权威回填与溯源才可能对上；解析结果记 `id_parsed` / `doc_kind` |
| ③ 内容登记 | `scripts/load_retrieval_documents.py`（新增）+ `.dockerignore` 白名单 | 把 22 份自有内容登记进权威表（`document_id = namespace:id`），并把它们放进 `embed_task` 队列，由既有 `vector_sync` Worker 嵌入并写 pgvector。**演示标记照搬**（三份源都自述 DEMO → `metadata["demo"]=True`），D12 护栏因此继续成立 |

### 27.3 登记过程中撞出的两个真缺陷（**只有真接上才会暴露**）

**缺陷 1：权威表的 `source_id` 不是"来源台账 id"**

第一次 `--apply` 报 `IntegrityError: Duplicate entry 'theory-src-theory-demo-1'`——权威表的唯一键是
`(namespace, source_id, version)`，而我错把语料里的**来源台账 id**（三个 theory 条目共用
`src-theory-demo`）当成了文档身份。改为 **`source_id = 文档 id`**（与检索侧比对口径一致），
台账 id 移入 `metadata["source_ledger_id"]`。

**缺陷 2（更严重）：启用 PAMI 后，真实对话里的检索**恒为 0

修完权威表后发现：直接调 `search` 能拿 5 条，但**真实对话**里证据包是空的、且无降级。逐层隔离后定位到两个叠加原因：

1. **PAMI 适配器拒绝带 filters 的请求**。编排器的检索计划给**每一条** query 都带
   `filters={"status": "enabled"}`（私有域还带 `user_id`），而适配器原来"见 filters 就抛错"
   → 关键词通道**整条打挂**，还伪装成"通道降级"，看着像平台坏了。
   改为：**接受并忽略**（PAMI 的 OpenAPI 请求体只有 `query/stream`），但命中带
   `metadata["filters_ignored"]`——忽略**也要可见**（与 D12/D13 同一条原则）。
2. **向量 metadata 缺少可过滤字段**。`PgVectorGateway` 用 `metadata @> filters` 过滤，
   而 `VectorSyncPlanner` 原来只透传来源字段，向量行里没有 `status` → 过滤**恒不命中**
   → 向量通道恒 0 条。改为透传 `status` / `user_id` / `org_id`。

修完这两处，证据包从 **0 条 → 8 条**，且 `channels=['keyword','vector']` **两条通道都工作**。

## 三十五、2026-09-20 补齐对话消息落库 + 读历史接口：前端刷新与切换会话恢复真实历史与环节进度

§33 的 P1-3 与 §34.2 都留了一条**同一件事**的尾巴：交接会话项点了没反应只能"如实空态"，理由是「第一期**没有『读历史会话』接口**」。用户侧的实际反馈是这句话的另一面——**"前端界面根本不能对话"**：输入框发得出消息，但一刷新整段对话就没了，换一条会话中栏与右栏全空，用户无法确认自己刚才说过什么、走到哪一步。

本轮把这条尾巴**按用户选定的改法（"后端补消息落库 + 读历史接口，前端恢复历史与进度"）**彻底修掉，而不是继续把空态写成合理。

### 35.1 三个根因（先摆事实，再动手）

| # | 事实 | 证据 |
| --- | --- | --- |
| R1 | **对话从未落库**：编排器每轮只把本次消息放进 `ConversationTurnView` 返回，没有任何持久化写入，进程一重载即丢 | 改造前 `services/orchestrator.py` 无 `ConversationMessage*` 依赖，构造参数里也没有消息仓储 |
| R2 | **没有读历史端点**：前端切会话只能 `clearTurnState()`，中栏气泡与右栏管线卡一律清空 | `GET /app/conversation/history` 改造前 404；前端 `selectSession` 改造前只有清空逻辑 |
| R3 | **新增表不会自动出现在生产库**：生产装配 `DatabaseContext(settings.database_url, echo=settings.db_echo)` **没有 `auto_create=True`** | `zhiyin-boot/zhiyin_boot/container/repositories.py:22`；`zhiyin-infrastructure/.../mysql/repositories.py:118` 的 `ensure_ready()` 只在 `auto_create=True` 时才 `Base.metadata.create_all` |

> R3 是本轮**唯一一个"只有真跑起来才会暴露"的坑**，单独在 35.3 展开。
