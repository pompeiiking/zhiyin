## 〇、决策原则（本轮统一判据）

1. **严格按架构设计执行**：分层、契约与存储分工以《职引技术架构文档》《开发指南》为准；决策不得偏离架构，要偏离先改架构文档。
2. **依赖放对层**：该由基础设施层提供的依赖就放在基础设施层（pami 模块内），不往职引侧搬自建件。
3. **避免复杂度**：同一个能力不造第二套实现。

**存储分工已按架构定稿：业务权威库＝MySQL（复用 pami 实例），向量库＝PostgreSQL + pgvector（职引新增，部署在 pami 基础设施层）。**

## 七、实施顺序（决策已全部闭环）

**第 0 步 · pami 侧落存储（D-1、D-2）**

- 新增职引专属 **PostgreSQL + pgvector 独立实例**（与 pami MySQL 解耦）：database `zhiyin_vector`、账号 `zhiyin_vector_app`、PostgreSQL 16+ / pgvector 0.7+；MVP 规格 4C8G / SSD 200G；备份＝每日全量 + WAL 归档
- 在 pami 的 MySQL 实例里划出职引独立 schema `zhiyin_service` 与账号
- 命名与隔离：Redis `zhiyin:` 前缀 + 独立 DB、Kafka `zhiyin.`、ES `zhiyin_`、MinIO `zhiyin-*`

**第 1 步 · 同步归属（`DEC-M3-13`）**

- `ownership.json` **不动**（它是装配报告的事实源）
- 改《排期表》§三/§六：四个缺口归数据访问负责人 / 基础设施负责人，平台侧写"支援"
- 建议把"嵌入与检索质量的**评测集与验收**"交给平台-2 认领——数据侧须知 6.3 要求"建立固定评测集，不以能搜到结果代替召回质量验收"，目前无人认领

**第 2 步 · 门槛内并行推进（不等存储就绪）**

- 接 `OPEN-1`（资产正文落库接线）与 `OPEN-2`（检索接进诊断 / 决策）的消费方
- M3 相关的契约与本地实现维护

**第 3 步 · 门槛第 4 条**：表清单、事务边界、迁移与回滚方案评审

**第 4 步 · 数据库与检索实现**

- 关系侧：ORM 与迁移 → `TransactionManager`（MySQL）→ 七个真实 Repository → 受限 RawQuery
- 向量侧：`sync_state` + `embed_task` + `VectorSyncWorker`（按架构 §七 的分类型同步策略与 `content_hash` 幂等）→ pgvector 六个命名空间（**统一 1024 维**、HNSW `m=16, ef_construction=64`）
- 检索：`vector.search` / `vector.hybrid_search`（**RRF**）+ 降级链（ES ↔ pgvector 互备）
- 检索日志：**只存元数据、不落原文、保留 180 天**
- 不做：RLS（并入 M4-02）、双写过渡、自建嵌入模型

**第 5 步 · 验收**：`--check --phase=3`、e2e、五场景联调

## 十、存储分工定案（原冲突已裁决）

**裁决（2026-09-16）：按架构执行。** `DEC-M3-01` / `02` / `14` 已回归《职引技术架构文档》§3.1 / §3.2 的存储分工；
原先"PostgreSQL 取代 MySQL 做业务库"的记录作废（该理解为记录失误，不是架构变更）。

架构原文规定的存储分工：

| 存储 | 角色 | 承载数据 | 来源（架构原文） |
| --- | --- | --- | --- |
| MySQL | 业务权威库、唯一事实源 | 业务数据、用户域、领域知识、外部事实 | **复用 pami** |
| PostgreSQL + pgvector | 向量库 | 向量、分块原文、检索元数据（MySQL 的读模型副本） | **职引新增** |
| Redis / Kafka / ES / MinIO | 热状态、事件流、全文检索、对象存储 | —— | 复用 pami |

同节还要求：向量检索命中后**必须回 MySQL 补全权威详情**；ES 负责关键词与全文检索、pgvector 负责语义检索；
PostgreSQL 16+ / pgvector 0.7+。

三条决策的最终口径：

| 决策 | 最终口径 |
| --- | --- |
| `DEC-M3-01` | 业务权威库＝MySQL（复用 pami 实例）；向量库＝PostgreSQL 16+ / pgvector 0.7+（职引新增，部署在 pami 基础设施层） |
| `DEC-M3-02` | MySQL / Redis / Kafka / ES / MinIO 复用 pami 既有实例；仅 PostgreSQL + pgvector 为职引新增 |
| `DEC-M3-14` | 撤销：`infrastructure/mysql/` 与 `ZHIYIN_USE_MYSQL` 保持不变 |

**实施时必须遵守的边界约束（架构原文）**：向量检索命中后必须回 MySQL 补全权威详情；ES 负责关键词与全文检索、
pgvector 负责语义检索；pgvector 只存向量、分块原文与检索元数据，是 MySQL 的读模型副本。

同时作废的还有一条旧顾虑：原先"因数据边界不该共用 pami 的 MySQL"——pami 是自有平台模块，不构成第三方边界。
