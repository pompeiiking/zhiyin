## 三、架构合理性（最终结论）

判断架构不看风格，看**每条约束有没有机械落点**。

### 3.1 合理且必须保留

| # | 设计 | 为什么 | 守卫 |
| --- | --- | --- | --- |
| R1 | 四层 + BFF + 装配层单向依赖 | 每层职责单一；`infra → data_sdk` 是依赖倒置 | `test_no_cross_layer_or_reverse_dependency` |
| R2 | 内核独立、零依赖、准入规则 | 数据形状与最小契约的归属唯一；带方法体的类进内核即失败 | `test_kernel_has_no_dependencies`、`test_kernel_holds_only_shapes_and_contracts` |
| R3 | 五类契约各有唯一归属 | 共享形状 / 数据访问契约 / 语义编排契约 / 业务产出契约 / 业务读侧出口 | `test_no_duplicate_contract_definitions` |
| R4 | 装配可观测 | "文件存在 ≠ 能力具备"，缺口带归属 | `describe_assembly` |
| R5 | 动态资源不进代码 | 文案 / 任务入口 / 智能体 / 理论卡 / 契约 / 开关 / 规则参数全走 registry | 交叉引用 + 文件存在守卫 |
| R6 | 分级门禁 M1–M4 | 二值 healthy 会让本期长期"未达标"而失去信号 | `--check --phase=N` |
| R7 | 接口契约快照链路 | 代码 → 快照 → 前端类型，两端都有卡口 | `test_api_contract` + `npm run check:api` |

### 3.2 必须克制（不再加抽象）

| # | 风险 | 处置 |
| --- | --- | --- |
| C1 | 编排层为"未来复用"预付抽象 | 冻结六原语，不再新增 |
| C2 | 语义契约与传输契约双份，字段可能分叉 | 传输契约只保留最小能力；语义策略收敛到编排层 |
| C3 | 读/写侧分离目前只在接口层 | 读侧不写状态、不发事件（口径已写进 ports） |
| C4 | 加一个能力位要动 4–5 个文件 | 保持现状：可观测性 > 单点便利；漂移由守卫挡 |
| C5 | 跨语言常量只能手抄一处（错误码） | 抄写处由编译期 + 断言双重对齐，不再新增手抄表 |

## 四、外壳落地历程（浓缩版）

`v1.0 → v1.2 → 本轮` 依次修掉的问题，按"症状是否静默"归类：

| 批次 | 修掉的洞 |
| --- | --- |
| v1.1 | BFF 无动态资源取数通道（`RegistryService`）；DTO 无 Mapper；代码里有影子文案；功能开关不可观测；数据管道 Worker 无落位；门禁引用不存在的 `tests/e2e/` |
| v1.2 | `trace_id` 有契约无生产者；前端类型来源不可用（需后端在跑）；跨语言口径无守卫；M3 替换点无落位；装配守卫有盲区（重名/拼错/字段脱节） |
| 本轮 | 16 项业务口径全部拍板并落库：`AxisAStage` / `PathFocus`、`policy_params` 三项 confirmed、埋点归属表、`POST /app/track`、Mock Facade 外壳 |

这些洞的共同特征是**不报错**（静默空值、静默 404、静默回落），比缺文件贵得多。
现在每一类都有断言兜底。

## 六、耦合与修改成本基线

| 需求 | 要动的文件 |
| --- | --- |
| 加一条任务入口 / 文案 / 开关 / 阈值 | `data/registry/*.json`（0 行代码） |
| 改一个前端字段 | `dto/mappers.py` + 导出契约快照 + 生成前端类型 |
| 加一个业务服务 | 新文件 + 落位表一行 + `container/ports.py` 一行 + `ownership.json` 一行 + 装配一行 |
| 加一个前端页面/组件 | 组件 + 路由 + `routes.json` + 前端 README 落位表一行 |
| 换 MySQL / Kafka / pgvector / Redis | 装配一行 + 对应抽屉实现；业务层零改动 |

已知并行冲突点：`container/ports.py`、`services/__init__.py`、`dto/mappers.py`、
`ownership.json`、生成物 `contracts/openapi.json` 与 `types.ts`（生成物冲突时重新生成，不手工合并）。

## 九、一句话结论

这套架构值得按原样推进：分层正确、依赖倒置处理得当、约束已变成可执行断言。
从"改造前快照"到"最终版"，做的是把**不会报错的缺口清零**和把**业务口径拍板落库**；
现在任何人认领一个格子都不需要动别人的代码，剩下的是把方法体填上——
在动手写 Orchestrator 与主动干预前，四项阻塞口径已定，无需再猜。
