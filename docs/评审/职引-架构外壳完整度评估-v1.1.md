## 一、结论摘要

| 维度 | 判定 | 依据 |
| --- | --- | --- |
| 架构分层与依赖方向 | **高（保留）** | 依赖矩阵由 AST 逐文件校验；内核零依赖；无重复契约定义；实测通过 |
| 契约归属 | **高（本轮补齐最后一处）** | 四类契约各有唯一归属；本轮补上「api 需要但契约在 data_sdk」的第二个通道 |
| 外壳完整度 | **高** | 43 个能力位全部有落位（27 wired / 1 skeleton / 15 not_wired 但**文件、类名、签名、归属齐备**） |
| 前端可并行 | **中高 → 高** | 本轮补齐 `/app/bootstrap` 的取数通道与前端组件落位表；前端不再需要等后端定义字段 |
| 可机械守卫程度 | **高** | 越层、落位缺失、骨架冒充完成、动态资源引用、动态资源文件缺失、Mapper 被绕开、**文档路径 / 数量 / 门禁落点漂移**均有守卫 |
| 剩余风险 | **中（已定位、已分配）** | 4 项业务规则未定稿；M2 的 15 个能力位待实现；后端跑真存储前仍是内存实现 |

一句话：**这份骨架已经可以交给 3–5 个人并行开工**——每个人的格子有文件、有类名、有冻结签名、
有归属、有守卫；剩下的工作是把方法体填上，而不是"先把结构想清楚"。

## 三、架构合理性复核

### 3.1 合理且应当保留的六处

| # | 设计 | 为什么合理 | 守卫 |
| --- | --- | --- | --- |
| R1 | 四层 + BFF + 装配层，单向依赖 | 每层职责单一；`zhiyin-data-sdk → zhiyin-infrastructure` 表示为层次顺序，真实代码方向是 infra → sdk（依赖倒置），最难画对的一跳处理正确 | `test_no_cross_layer_or_reverse_dependency` |
| R2 | 共享内核独立成包且零依赖 | "领域模型归谁"不再有歧义；任何层都能安全引用 | `test_kernel_has_no_dependencies`、`test_kernel_holds_only_shapes_and_contracts` |
| R3 | 四类契约各有唯一归属 | 共享形状 / 数据访问契约 / 语义编排契约 / 业务产出契约，一类一个家 | `test_no_duplicate_contract_definitions` |
| R4 | 装配可观测（wired / skeleton / not_wired + 归属） | "文件存在 ≠ 能力具备"被机械保证；缺口带负责人，红灯有行动含义 | `describe_assembly` + `test_skeleton_is_reported_not_hidden` |
| R5 | 动态资源不进代码 | 文案、任务入口、智能体、理论卡、产出契约、开关、规则参数一律走 `data/registry/`；改配置不发版 | `test_registry_cross_references_are_closed` + 本轮新增的文件存在守卫 |
| R6 | 分级门禁（M1–M4） | 二值的 `healthy` 只有一个含义（全绿），会让本期长期"未达标"而失去信号；分级后 CI 能精确卡口 | `--check --phase=N` + `test_gates_reference_known_ports` |

### 3.2 合理但需克制的地方

| # | 设计 | 风险 | 处置 |
| --- | --- | --- | --- |
| C1 | 编排层"通用、零业务语义"（为 pami 平台将来复用） | 第一期只有职引一个消费者，为未来预付抽象成本 | **冻结进一步抽象**：现有六原语保留，不再新增原语 |
| C2 | 语义契约（orchestration）与传输契约（data_sdk）双份 | 同义概念字段集可能分叉（历史上 `ScheduleSpec` / `ScheduledTask` 已分叉过一次） | 已定案：传输契约只保留最小能力；新增字段必须单向映射 |
| C3 | CQRS-lite（读侧 / 写侧分离）目前只是"接口上分开" | 读侧服务尚未实现，容易在实现时又混在一起 | 口径已写进 `ports/workspace.py` 与 `ports/registry.py`：读侧**不写状态、不发事件** |
| C4 | 一个能力位的装配要同时改 4 个地方（`container/ports.py`、`container/*.py`、`ownership.json`、`assembly_gates.json`） | 加能力位的操作跨 4 文件，是并行冲突点 | **保持现状**：把"现状可见"看得比"改一处"重要；漂移由 `test_assembly.py` 挡住 |

## 四、耦合与修改成本分析（本轮重点）

判断标准不是"好不好看"，而是**改一处要动几个文件、会不会牵动别人**。

### 4.1 本轮修掉的六个结构洞

| # | 洞 | 现象（改之前的真实状态） | 修改成本 | 处置 |
| --- | --- | --- | --- | --- |
| H1 | **BFF 到动态资源没有通道** | `/app/bootstrap` 要返回菜单 / 路由 / 任务入口 / 文案 / 开关，但取数契约在 `data_sdk`，而 api 被禁止 import `data_sdk`。**没有合法实现路径**：只能越层，或让字段恒为空 | 不修则前端第一条请求就卡住；修晚了所有页面字段都要返工 | 新增 `business/ports/registry.py::RegistryService` + 骨架实现（与 `IdentityService` 同源的第二个通道） |
| H2 | **Mapper 层缺失** | 文档与 Facade docstring 都写"转换在 Mapper"，但 `dto/` 下没有 Mapper。每个人会自己在 Facade 里拼 View，字段口径当场散开 | 改一个字段要翻遍 facade 包；前端拿到漂移的 JSON 而无人发现 | 新增 `api/dto/mappers.py`（签名冻结 + 12 个映射函数骨架）+ 守卫禁止 Facade 内联构造 View |
| H3 | **代码里的影子文案** | `BootstrapView.app_name = "职引"`、`trust_copy` 带默认中文——文案写进了代码，改 JSON 不生效 | "改配置不发版"这条口径被静默破坏 | 去掉全部默认文案；文案只能经 `copy_bundle` 下发 |
| H4 | **配置型动态资源不可观测** | 功能开关只有 boot 内部一个 JSON 读取器：不在能力位清单、不在 `--check`、不在归属表、业务与前端都拿不到 | 开关"看起来有、实际没人管"；第二期换配置中心时无落位 | 升级为 `FeatureFlagGateway` 契约 + 能力位 `feature_flags` + 契约测试 |
| H5 | **数据管道 Worker 没有落位** | `infrastructure/workers/` 只有一段 docstring；文档与 `vector_sync` 的说明都指向一个不存在的文件 | 第一个数据管道任务落地时没有家 | 新增 `vector_sync.py` 骨架 + 能力位 `vector_sync` + 归属 |
| H6 | **门禁引用了不存在的目录** | `--check --phase=2` 的退出条件写着"`tests/e2e/` 主路径通过"，而该目录不存在——验收悬空 | 实现者不知道 e2e 该测什么，实现完才发现口径不一致 | 建 `tests/e2e/`，把 7 项验收的断言写出来，用"Facade 是否装配"自动门控（未装配→跳过，装配→开始跑） |

### 4.2 仍然存在的耦合点（已定位，暂不改）

| # | 耦合点 | 现状 | 影响 | 处置 |
| --- | --- | --- | --- | --- |
| E1 | 加能力位要改 4 个文件（见 C4） | 有守卫防漂移 | 并行时的冲突点，但冲突是"行级追加"，可接受 | 在 `开发指南` 写明步骤；冲突时以 `container/ports.py` 为准 |
| E2 | `business/services/__init__.py` 是落位表 + 全部 import 的汇合点 | 每次加服务都改它 | 多人同时加服务会撞同一文件 | 保持（它是唯一能"一眼看全 10 个服务"的地方）；表格与目录一致性由守卫保证 |
| E3 | 业务规则参数仍标 `draft`（`policy_params.json`） | 参数是动态资源、已落位 | **4 项业务规则未定稿，直接阻塞 Orchestrator** | 见 §6.1 待定稿清单——这是当前投入产出比最高的下一步 |
| E4 | 对话 / 工作台字段还没有"来源守卫" | 只有 `BootstrapView` 有字段→出口的对照表 | 新增字段可能再次出现"有字段没出口" | 已建模式；实现 Facade 时把同样一张表补到 `ConversationTurnView` / `WorkspacePageView` |
| E5 | 后端仍是纯内存实现（重启即丢） | 契约与装配位已就绪 | M3 前"跨会话续接"只在同进程内成立 | 已在 `数据层设计文档` 与门禁 M3 如实标注，不当作已完成 |

### 4.3 修改成本基线（改一处要动几个文件）

用三个典型需求说明现在的成本结构，团队可以据此估算排期：

| 需求 | 要动的文件 | 关键收益 |
| --- | --- | --- |
| 加一条首页任务入口 | `data/registry/task_entries.json`（1 个文件，0 行代码） | 动态资源的直接价值；产出契约由守卫校验闭合 |
| 加一个业务服务 | `services/<新文件>.py` + `services/__init__.py` 表格一行 + `container/ports.py` 一行 + `ownership.json` 一行 + `container/services.py` 接一行 | 签名先冻结，调用方可以用 Fake 并行开工 |
| 换 MySQL / Kafka / pgvector | `container/*.py` 装配一行 + 新实现目录 | 业务层零改动；语义由同一套契约测试锁住 |

### 4.4 文档漂移：一种被低估的修改成本

本轮全文核对文档对代码的描述时，找到的都是"不会报错、只会让人白干"的那类问题：
服务数量写在文档里（8 个 / 9 个 / 10 个三种说法并存）、`tests/e2e/` 被门禁引用却不存在、
启动地址写成 `:8000/docs`（真实是 `:8000/api/v1/docs`）、前端组件在设计文档里有选型但代码里没有文件。

代价不是"文档难看"，而是**照错抄**：新人照着文档去改一个不存在的文件、或者以为缺口只剩那几个。
因此本轮把三类最贵的漂移变成机械断言（`tests/test_docs_alignment.py`）：

| 守什么 | 为什么它最容易漂 |
| --- | --- |
| 文档里用代码片段引用的**仓库路径必须存在** | 改名 / 删文件 / 拆目录之后，链接没人点、代码片段更没人点 |
| 文档里的**能力位数量必须与 `container/ports.py` 一致** | 数字写死在正文里，加能力位时最容易漏 |
| 门禁 `manual` 提到的**目录必须存在** | 门禁引用不存在的验收落点，等于验收悬空 |

历史名（`domain/`、`workers/base.py` 等）与"按需新增"的计划目录（`kafka/`、`pgvector/`）在测试里
**逐条登记理由**——这样"故意不存在"与"忘了改"能被区分开。

## 六、剩余缺口与分工（一人一列，互不阻塞）

### 6.1 先定稿，再动手（4 项，阻塞 Orchestrator）

| # | 待定稿 | 现状 | 为什么必须先定 |
| --- | --- | --- | --- |
| 1 | 轴 A 阶段判定信号 | 未定稿 | 主理选择依赖"轴 A × 轴 B × 意图"，缺一维只能靠猜 |
| 2 | 意图识别 → 环节判定的兜底规则 | 半定 | 决定"识别不准时回落追问"的行为，写错会硬跳环节 |
| 3 | 画像置信度算法与缺口表达（采集结束条件） | 未定稿 | 决定 ①采集 何时收尾 |
| 4 | 主动干预参数（停滞阈值 / 冷却期 / 打扰上限） | `policy_params.json` 标 `draft` | 决定 ⑤复盘 的打扰边界 |

> 这 4 项是**产品/业务口径**，不是技术问题。技术上它们已经全部有落点
> （`policies/` 五条规则 + `policy_params.json` 参数），定稿后改 JSON 即可生效，不需要动结构。

投入产出比最高的一步。
