## 二、架构设计合理性

### A1 分层与依赖方向 —— 合理（本次评估中质量最高的部分）

「基础设施层 → Data Access SDK → 编排层 → 业务逻辑层 + BFF 接入层」的划分成立，且最难画对的一跳处理正确：**SDK 只定义契约，代码依赖方向是 `infra → SDK`（依赖倒置）**。文档 §1.4 已用显式说明修正了原先 ASCII 图的方向误导，`tests/test_architecture.py` 用 AST 逐文件校验允许矩阵，越层即 CI 失败。

这是把"架构约束"变成"可执行断言"的正确做法，避免了此类约束在多人协作中自然腐化。**结论：保留，不要动。**

### A2 编排层通用化 —— 概念合理，第一期性价比偏低

编排层被要求"不出现任何职引业务语义、可被 pami 平台其他垂直应用复用"，方向正确。但实测：9 个文件 765 行，**全仓仅 `zhiyin-business/services/loop.py` 一处消费**；六原语中 `WorkflowEngine`、`StateStore` 无业务消费者，`AgentEngine` 的实际调用也只是"透传给 LLM + 校验 Schema"。

第一期只有职引一个消费者，为"未来复用"预先支付的抽象成本已经开始产生副作用——同一件事在编排层与 SDK 各声明一遍（见 A3）。

**建议**：保留契约与实现，但**冻结进一步抽象**。等到第二个业务真正接入时再决定哪些原语值得保留。

### A3 语义契约 vs 传输契约 —— 方向对，但存在双份定义的分叉风险

`zhiyin_orchestration`（语义：信封 + 幂等 + 冷却策略）与 `zhiyin_data_sdk.gateways`（传输）的二分法是成立的，`GatewayEventBus` / `GatewayScheduler` / `GatewayNotifier` 是两者唯一的粘合点。但实测暴露出分叉已经开始：

- `ScheduleSpec` 有 `cooldown_s` / `max_triggers`，`ScheduledTask` 有 `owner_id` —— 同义概念的字段集不一致；
- `GatewayEventBus.unsubscribe()` 因 Gateway 契约不提供退订，**只摘掉本层 handler，底层订阅依然存在**（`impl.py:144-154`）。切到 Kafka 后，退订语义会静默失效。

**建议**：把"一件事只有一处定义"作为硬规则。传输契约只保留"到点投递一个事件"这一最小能力，其余策略全部收敛到语义层；同时补齐 `unsubscribe` 的端到端语义。

### A4 领域模型归属（共享内核倒置）—— 最大的一笔设计债

`Profile` / `ProfileField` / `ProfileGap` / `AssetVersion` / `TaskSession` / `BehaviorLog` / `ConversationMemory` / `Report` / `DirectionPlan` / `ActionPlan` 全部定义在 `zhiyin_data_sdk/contracts/`。

这实际上是一个**共享内核（shared kernel）**，而不是"数据访问契约"。`zhiyin-business/published.py` 只解决了 API 边界越层的症状（避免 api 直连 data-sdk），**没有解决根因：业务层自己的领域模型不在业务层**。业务语义变更会持续牵动数据访问包。

**建议（二选一，但必须显式定调）**：
- 承认它是共享内核 —— 把包/模块重命名为明确的共享内核定位（如 `zhiyin_shared_kernel`），并在文档中写明它不承载数据访问实现；
- 或把领域模型上移到 `zhiyin-business`，SDK 只保留读写契约。

现状（模型在数据层、名字却叫"数据访问 SDK 契约"）是最容易让新人误判的一种。

### A5 黑板"统一访问模型"—— 设计成立，落地为零

`BlackboardView` 是只读快照，`domain/blackboard.py` 定义了 Profile / Behavior / Memory / Asset 四件套 Port，设计清晰。但实测：`AgentDrivenLoopCoordinator._build_context()` 的 `blackboard_loader` 默认为 `None`，落回**空黑板**（`services/loop.py:228-232`）。而唯一的黑板服务实现者从未被装配。

后果：产品最核心的承诺——**跨会话续接、前序资产继承、影响面传播**——在代码层面目前只有接口占位。验收项 2/4/5 因此不可能通过。

### A6 五环节状态机 —— 建模正确，但交接口径有实质错误

把"环节推进"与"主理解析"分离、把落库交给调用方统一完成（`LoopResult` 注释明确"环节只产出，不落库"）是正确的边界设计。

但 `_resolve_lead()`（`services/loop.py:332-344`）按 `task_code` 查任务入口的默认主理，**与目标环节无关**。实测结果：

```
advance → DIAGNOSE，主理解析为 profile_analyst
advance → DECIDE，  主理解析为 profile_analyst
advance → ACT，     主理解析为 profile_analyst
advance → REVIEW，  主理解析为 profile_analyst
```

即：**环节在推进，主理恒定不变**。"动态组队 + 交接换主理 + 换主理必须显式告知"这条产品主线，在第一期代码里是形式存在的。正式口径属于 `Orchestrator.select_lead`（按轴 A × 轴 B × 意图），而 Orchestrator 未装配。

### A7 SDK 契约与总架构不一致 —— 真实的契约缺口

总架构 §6.1 明确列出 SDK 能力：`db.query/db.tx`、`cache.get/set`、`EventBusGateway`、`search.query`、`object.put/get`、**`vector.search/upsert/delete`**、**`embed.text/batch`**。

实测 `zhiyin-data-sdk` 现有 Port：`LLMGateway`、`KnowledgeGateway`、`SearchGateway`、`EventBusGateway`、`SchedulerGateway`、`NotifyGateway`、`ObjectStoreGateway`、`AuthGateway`、`SecurityGateway`、`RateLimitGateway` + 7 个 Repository + `TransactionManager`。

**缺 4 类**：`db`、`cache`、`vector`、`embed`。其中 `vector` / `embed` 是 pgvector 方案的全部落点。

**影响**：第八章"检索路径设计"（纯向量检索 / 混合检索 / 降级策略）与第七章"数据同步机制"（sync_state / embed_task / retrieval_log）在 SDK 里**没有可挂载的契约**。若不补齐，第二期落地向量检索时会先在 SDK 层补一次接口，属于返工。

### A8 事件可靠性语义 —— 文档承诺高于实现能力

文档承诺"至少一次投递"。第一期 `InMemoryEventBus` 无持久化、无重试、无投递确认，订阅方异常被隔离（得当），但事件本身**失败即丢**。这在第一期可接受，但必须在文档中把"至少一次投递"标注为**第二期能力**，否则会误导下游对可靠性的判断。

## 三、代码结构合理性

### B1 包结构与文档映射 —— 好

六个包与总架构层的映射表清晰（README + §1.4），配套"三件套"齐备：依赖矩阵（文档）+ AST 守卫（测试）+ 装配可观测量（`--check` / `/healthz`）。`--check --strict` 可作 CI 门禁，是本期工程化最值得保留的资产。

### B2 契约/实现分离 —— 规范，但骨架密度过高

`zhiyin-business/domain/` 5 个文件（orchestrator / blackboard / loop / workspace / function）**全部是 ABC + Pydantic 契约**，无一个实现。`services/` 只有 `loop.py` 一个参考实现，其 docstring 也自述"是 reference implementation 而不是最终实现"。

这符合"接口先于实现冻结"的方法论，但配合 8 项 `not_wired`，直接后果是：**本期交付物是"可验证的脚手架"，不是"可运行的业务"**。这一点必须在交付说明里讲清，不能靠 `--check` 的 `degraded` 让读者自行推断。

### B3 `container.py` 职责过载 + 组织信息硬编码

`container.py`（475 行）同时承担：装配表、装配报告生成、缺口清单、最小可用校验、ASGI 应用装配、lifespan 调度启停。建议按"装配 / 报告 / 校验"拆分。

更值得注意的是 `_KNOWN_PENDING`（`container.py:335-344`）把**负责人/团队信息**写进了代码：

```python
"orchestrator": "业务编排负责人（Orchestrator 意图识别 / 环节判定 / 主理选择）",
```

这与 README 自订的"动态资源不许写进代码"直接冲突——同类信息（文案、任务入口、智能体、理论卡）都走了 `data/registry/*.json`，唯独负责人清单留在 Python 里。**建议移到 `data/registry/ownership.json`。**

### B4 同步 Repository × 异步编排混用 —— 前瞻性风险

Repository 全部为同步方法（`ProfileRepository.get()` 等），而编排层与 Loop 全部为 `async`（`AgentEngine.invoke`、`EventBus.publish`）。第一期的内存实现让这个矛盾不可见；一旦接上 MySQL / 网络 IO，同步阻塞会卡住事件循环。

**建议**：在第一期就统一为异步契约（内存实现照旧，只是加 `async`），或在 SDK 层显式引入执行器隔离。现在改成本最低。

### B5 Mock 策略与产品硬约束冲突 —— 一条关键链路无法验证

`LocalOrMockLLM` 刻意跳过"非必填且可空"的字段，理由是不凭空造出"换主理告知"。这个判断单看是合理的，但实测后果是：

```
disclosure: None
```

`LoopResult.disclosure` 恒为 `None` → **"换主理必须显式告知"这条产品硬约束在第一期永远无法被触发和回归验证**；前端 `DisclosureRow` 也就永远拿不到数据。

**建议**：给 Mock 加一个开关（如 `ZHIYIN_MOCK_FILL_OPTIONAL=1`），仅在测试中填充可空字段，让告知链路可回归。另需注意 Mock 产出的文案是"（第一期 Mock 产出，未接真实模型）"，会直接作为结论与主理标签流到 UI —— 前端需显式标注 Mock 来源，否则演示会被误读为真实能力。

### B6 `LoopResult.behavior_events` 声明但从未填充 —— 行为闭环断链

`domain/loop.py:93` 声明了 `behavior_events: list[BehaviorEventDraft]`，但全仓 grep 只有这一处出现 —— `AgentDrivenLoopCoordinator._to_loop_result()` 从不传该参数（恒为空列表）。而 Loop 的 docstring 明确写着"落库与事件发布由调用方 Orchestrator 统一完成"，Orchestrator 未装配。

**结论：行为日志在第 ①→⑤ 任一环节都不会被写入**，验收项 6「行为闭环」不成立。

### B7 MySQL 分支不可用 —— 存储策略是空头承诺

- `SqlAlchemyTransactionManager.begin()` 直接 `raise NotImplementedError`（`persistence/database.py:24-25`）；
- `persistence/` 下**没有任何 Repository 实现**，Repository 只有内存版；
- 第一期文档 §6.1 却写着"业务权威数据 → MySQL"。

即：第一期实际是**纯内存、进程重启即全部丢失**。这意味着"可拆可续跨会话续接"在重启后不成立。文档的存储策略表需要改写，或补齐实现。

### B8 前端全部为骨架

31 个 `.vue` / `.ts` 文件、510 行，全部为 TODO 注释 + 空模板（如 `ConversationPage.vue` 仅 22 行，模板里只有 `<!-- TODO(骨架): <SessionList /> <ChatStream /> <PipelinePanel /> -->`）。三栏布局、显式告知、行为引导这三条全局约束目前只存在于注释中。验收项 1「首页任务路由」无依托。

## 五、结论与建议动作

### 总体判定

| 维度 | 判定 | 说明 |
| --- | --- | --- |
| 架构设计合理性 | **高** | 分层边界清晰、依赖倒置处理正确、约束已固化为测试。4 处需修正（A3/A4/A5/A7） |
| 代码结构合理性 | **中上（有隐患）** | 包边界与契约冻结规范；但骨架密度过高，4 处实现级缺陷（B3/B4/B6/B7） |
| 第一期可行性 | **技术可行，口径不达标** | 现行 9 项验收中 5 项不具备通过条件 |

### P0（阻塞端到端，建议立即处理）

1. **补业务主干最小可用实现**：Orchestrator（规则版即可）+ 黑板四件套（内存版）+ Application Facade。这是唯一能同时解锁验收项 1/3/4/5/6 的动作。
2. **填充 `LoopResult.behavior_events`**：否则行为闭环永久断链。
3. **修正 `advance()` 的交接口径**：或明确第一期不做交接，同步下调文档与产品口径，避免"看起来有、实际没有"。
4. **重构第一期验收口径**：把 §九 9 项拆成两段——里程碑 1（接口冻结 + 装配可观测 + 单环节可跑，现已达成）与里程碑 2（端到端 9 项）。用一张无法达成的验收表驱动排期，会让团队持续处于"未达标"状态而失去信号价值。

### P1（影响第二期返工成本）

5. 补齐 SDK 的 `vector` / `embed` / `cache` / `db` 契约（或把总架构 §6.1 明确降级为第二期）。
6. Repository 统一为异步契约。
7. 明确 `data_sdk.contracts` 的定性：承认共享内核并重命名，或把领域模型上移业务层。
8. 给 Mock 增加"填充可空字段"开关，让"显式告知"链路可回归；前端标注 Mock 来源。

### P2（工程质量与协作）

9. 拆分 `container.py`；`_KNOWN_PENDING` 移入 `data/registry/ownership.json`。
10. ~~6 个包收敛为 2 个可安装包~~ —— **本条撤回**：实测 `pyproject.toml` 只有一个分发单元（`name = "zhiyin"`，6 个顶层包），并不存在多分发单元的协调成本，原判断有误。改为建议：`orchestration/impl.py`（605 行）按原语拆分为 `impl/`，降低多人并行时的单文件冲突率。
11. 总架构 §十五 的 16 项待确认事项中，有 4 项**直接阻塞 Orchestrator 实现**——轴 A 阶段判定信号、意图识别到环节判定的兜底规则、画像置信度算法与缺口表达、主动干预参数（停滞阈值/冷却期/打扰上限）。**建议在动手写 Orchestrator 之前定稿**，否则实现只能靠猜，后续必返工。

## 六、一句话结论

职引的架构设计是可长期保留的——分层正确、依赖倒置处理得当、约束已被 AST 测试固化，属于「值得按此推进」的水准；代码结构忠实地支撑了这套架构，但当前是**接口冻结完备、业务主干空置的脚手架**：8 个业务服务只装配了 1 个，端到端止步于 503，9 项验收中 5 项不具备通过条件。

可行性结论因此分两层：**技术路线可行**（补齐 Orchestrator + 黑板四件套 + Facade 即可解锁主干），**但现行验收口径不可行**（应拆成"框架可验证"与"端到端可演示"两个里程碑）。在写 Orchestrator 之前，先把 4 项阻塞性业务规则定稿——这是当前投入产出比最高的一步。
