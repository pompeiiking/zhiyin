## 一、文档定位与总体原则

### 1.1 第一期目标

1. 用最少的外部依赖，跑通「首页任务 → 编排器 → 五环节微循环 → 黑板 → 智能工作台」完整调用链。
2. 验证核心产品定义中的三轴模型、五环节、动态组队、可拆可续、增量重算和主动干预是否成立。
3. 让研发可以在本地启动、演示和调试，不追求线上可用性。

### 1.2 总体原则

| 原则 | 说明 |
| --- | --- |
| 业务优先 | 优先实现 Loop、Orchestrator、Profile、Behavior、Asset、Workspace、Function 的业务逻辑 |
| 骨架优先于真实实现 | 非业务能力只定义 Port 接口，提供 Local/Mock/Noop 默认实现 |
| 默认通过层 | 鉴权、安全、限流、加密等模块在第一期可返回“通过/不拦截”，但必须显式标记 |
| 模块化单体 | 服务先以模块化单体组织，按业务边界拆包，不引入微服务 |
| 与总体架构一致 | 实现层不得另起分层模型，必须沿用总架构的四层结构、依赖方向与接口契约 |
| 完整架构优先 | 团队开发必须保留清晰的分层、依赖方向、接口契约与模块归属，避免后续返工 |
| 内存事件总线 | 用进程内事件总线替代 Kafka，接口与事件契约保持一致 |
| 本地存储 | MySQL 存权威数据；对象、知识库、向量检索使用本地实现或 Mock |
| 不接真实敏感数据 | 第一期只允许演示数据、脱敏数据或本地测试数据 |

### 1.3 “默认通过层”的定义

默认通过层是指：接口存在、调用链完整，但实现为空或恒通过。它不承载真实能力，也不阻塞业务主流程。

示例：

- `AuthGateway.authenticate()` 默认返回本地演示用户；
- `SecurityGateway.encrypt()` 默认原样返回；
- `RateLimitGateway.allow()` 默认返回 `true`；
- `EventBusGateway.publish()` 默认同步调用内存监听器；
- `NotifyGateway.push()` 默认打印日志或写入本地消息表。

### 1.4 团队开发完整架构边界

第一期实现架构直接沿用总架构的四层结构。团队按层拆包并行开发，代码包可以在层内进一步拆分，但不能改变层间边界。

```text
前端 / BFF（zhiyin-api）
   ↓ 只依赖
业务逻辑层（zhiyin-business）
   ↓ 只依赖
编排层（zhiyin-orchestration）
   ↓ 只依赖
Data Access SDK（zhiyin-data-sdk：只定义契约，不实现）
   ↓ 只依赖
基础设施层（zhiyin-infrastructure）
```

> **最后一跳的方向要说清**：上图表达的是「层次顺序」，不是「代码依赖方向」。
> Data Access SDK 只定义 Repository / Gateway 抽象，**真正的代码依赖是
> 基础设施层 → Data Access SDK**（由 infra 提供 MySQL / Local / pami 适配器去实现 SDK 的抽象），
> 属于依赖倒置。因此 §九 验收项 1 要检查的是 `zhiyin-infrastructure` 不得 import
> 业务层与编排层，而不是相反。该方向已由 `tests/test_architecture.py` 静态守卫。

团队代码包到总架构层的映射：

| 代码包 | 对应总架构层 | 职责 |
| --- | --- | --- |
| `zhiyin-kernel` | 共享内核（横切全部层） | 跨层枚举、画像 / 资产 / 身份 / 动态资源的数据形状；零依赖，任何层可读 |
| `zhiyin-api` | 前端 / BFF | Controller、DTO、参数校验 |
| `zhiyin-business` | 业务逻辑层 | `ports/`（接口）、`policies/`（业务规则）、`services/`（实现）、`workers/`（异步执行者） |
| `zhiyin-orchestration` | 编排层 | Agent、Workflow、EventBus、Schedule、State、Notify 的通用原语 |
| `zhiyin-data-sdk` | Data Access SDK | 数据访问、事件、缓存、对象、向量检索接口封装 |
| `zhiyin-infrastructure` | 基础设施层 | pami 适配器、MySQL、本地文件、本地知识库、默认通过/Noop 实现 |
| `zhiyin-boot` | 装配层 | 依赖注入、配置、Demo 数据 |

> 共享内核原名 `zhiyin_data_sdk.contracts`（挂在数据访问包下），已按
> 《职引-目标架构设计-v1.0》§5.1 迁出为独立包 `zhiyin-kernel`：领域模型归共享内核，
> 数据访问契约只留在 SDK。两处命名失真（`data_sdk/contracts`、`business/domain`）
> 同时修正，前者改 `zhiyin_kernel`、后者改 `zhiyin_business.ports`。

依赖方向与总架构完全一致：

```text
zhiyin-api → zhiyin-business → zhiyin-orchestration → zhiyin-data-sdk → zhiyin-infrastructure
```

第一期只是把 `zhiyin-orchestration` 的 EventBus/Schedule/Notify 实现为 InMemory/Local，把 `zhiyin-infrastructure` 中的向量检索、对象存储、真实鉴权等实现为骨架；层边界和接口契约不因为第一期的简化而消失。

## 三、第一期总体架构

```text
┌──────────────────────────────────────────────────────────────┐
│  前端 / 演示入口（本地页面或命令行）                          │
└──────────────────────────┬───────────────────────────────────┘
                           │ HTTP / 本地调用
┌──────────────────────────v───────────────────────────────────┐
│  业务逻辑层（zhiyin-business）                                │
│  Orchestrator / Loop / Profile / Behavior                     │
│  Asset / Workspace / Function                                │
├──────────────────────────────────────────────────────────────┤
│  编排层（zhiyin-orchestration）                               │
│  Agent / Workflow / EventBus / Schedule / State / Notify      │
│  第一期：InMemory EventBus + Local Scheduler + Local Notify  │
├──────────────────────────────────────────────────────────────┤
│  Data Access SDK（zhiyin-data-sdk）                          │
│  连接 / 鉴权 / 审计 / 事务 / 检索 / 对象 / 事件               │
│  第一期：仅保留接口，默认通过或本地实现                        │
├──────────────────────────────────────────────────────────────┤
│  基础设施层（zhiyin-infrastructure）                          │
│  DefaultPassAuth / NoopSecurity / LocalOrMockLLM             │
│  LocalKnowledgeRepo / LocalFileStore / MySQL                 │
│  预留：Kafka / pgvector / ES / MinIO 骨架                    │
└──────────────────────────────────────────────────────────────┘
```

### 3.1 依赖规则

- 调用方向与总架构完全一致：`zhiyin-api → zhiyin-business → zhiyin-orchestration → zhiyin-data-sdk → zhiyin-infrastructure`。
  该链表示**层次自上而下**；其中 `zhiyin-data-sdk → zhiyin-infrastructure` 一节表示 SDK 只定义契约，
  代码依赖方向为 infra → SDK（依赖倒置），见 §1.4 说明。
- 业务层只能通过编排层原语或 Data Access SDK 访问底层能力，禁止跨层直连。
- 第一期把编排层 EventBus/Schedule/Notify 实现为 InMemory/Local，把基础设施层非核心能力实现为默认通过/本地骨架，但接口契约与层边界不变。
- 禁止业务代码直接写 SQL 拼装知识库、直接操作对象文件、直接调模型 API。

## 四、模块清单与实现策略

### 4.1 核心业务模块：完整实现

| 模块 | 第一期职责 | 关键输出 |
| --- | --- | --- |
| Orchestrator Service | 识别意图、判定环节、选择主理/协理/信息侦查员、处理交接与显式告知 | 编排决策结果 |
| Loop Service | 承载 ①-⑤ 的业务状态机与可拆可续 | 五环节产出 |
| Profile Service | 画像字段、置信度、缺口的读写 | 画像活状态 |
| Behavior Service | 行为日志写入、查询与事件发布 | 行为事件 |
| Conversation Memory Service | 会话记忆、摘要与跨会话续接 | 会话摘要与记忆查询 |
| Asset Service | 诊断报告、方案、计划、资产版本与影响面传播 | 资产版本 +1、diff |
| Workspace Service | 按 ①-⑤ 聚合工作台资产 | 工作台视图数据 |
| Function Service | 报告全文、日历、成就、导出、导师建议、演示的第一期逻辑 | 功能块数据 |
| Identity Service | 解析当前用户（包装 `AuthGateway`）+ 补齐本地用户记录 | 当前用户（`UserAccount`） |

> **Identity Service 为什么在业务层**：api 层被依赖矩阵禁止 import
> `zhiyin_data_sdk`，拿不到 `AuthGateway`；而"认证主体 → 本地用户记录"是业务行为
> （首次登录建号、游客合并）。因此由业务层包成
> `business/ports/identity.py::IdentityService`，Facade 只面对业务抽象。

### 4.2 编排与黑板：完整实现业务规则

| 模块 | 第一期实现 |
| --- | --- |
| 意图与环节判定 | 规则优先 + 简单关键词/LLM 兜底 |
| 轴 A 阶段推断 | 先用简化规则，不实现复杂统计模型 |
| 智能体能力池 | `AgentRegistry` 配置化，五个智能体的理论包/边界照 PRD 定义 |
| 单轮回复骨架 | 读黑板 → 环节判定 → 选主理 → 理论链产出 → 行为引导收尾 |
| 黑板 | 画像 + 行为日志 + 会话记忆 + 资产版本；权威数据落 MySQL |
| 影响面传播 | 画像字段更新后，按依赖字段只重算受影响资产，版本 +1 |

### 4.5 团队并行开发边界与接口契约

#### 4.5.1 模块归属

| 模块 | 归属团队/负责人 | 只依赖 |
| --- | --- | --- |
| `zhiyin-api` | 接口/前端联调负责人 | `zhiyin-business` |
| `zhiyin-business` | 业务编排负责人 | `zhiyin-orchestration`、`zhiyin-data-sdk` |
| `zhiyin-orchestration` | 编排层负责人 | `zhiyin-data-sdk` |
| `zhiyin-data-sdk` | 数据访问负责人 | `zhiyin-infrastructure` |
| `zhiyin-infrastructure` | 基础设施负责人 | 不依赖业务模块 |
| `zhiyin-boot` | 架构负责人 | 所有模块 |

#### 4.5.2 核心接口契约

| 接口 | 位置 | 说明 |
| --- | --- | --- |
| `Orchestrator` | `zhiyin-business` | 判定环节、选择主理、处理交接 |
| `LoopCoordinator` | `zhiyin-business` | 五环节状态机与可拆可续 |
| `IdentityService` | `zhiyin-business` | 当前用户解析（包装 `AuthGateway`）。api 与数据访问契约之间的唯一通道 |
| `Worker` | `zhiyin-kernel` | 后台执行者最小契约（`name` + `run_once`）；驱动在 `zhiyin_boot/workers.py` |
| `Agent.invoke` | `zhiyin-orchestration` | 智能体调用与产出契约校验 |
| `Workflow.run` | `zhiyin-orchestration` | 多步骤流程 |
| `EventBus.publish/subscribe` | `zhiyin-orchestration` | 领域事件发布/订阅 |
| `Schedule.register` | `zhiyin-orchestration` | 主动事件调度 |
| `State.read/write` | `zhiyin-orchestration` | 共享状态读写 |
| `Notify.push` | `zhiyin-orchestration` | 通知输出 |
| `ProfileRepository` | `zhiyin-data-sdk` | 画像活状态读写 |
| `BehaviorRepository` | `zhiyin-data-sdk` | 行为日志写入与查询 |
| `ConversationMemoryRepository` | `zhiyin-data-sdk` | 会话记忆读写 |
| `AssetRepository` | `zhiyin-data-sdk` | 报告/方案/计划版本与影响面 |
| `LLMGateway` | `zhiyin-data-sdk` | 模型调用 |
| `KnowledgeGateway` | `zhiyin-data-sdk` | 知识库检索 |
| `SearchGateway` | `zhiyin-data-sdk` | 关键词/向量/混合检索 |
| `ObjectStoreGateway` | `zhiyin-data-sdk` | 对象存储 |

#### 4.5.3 并行开发规则

- 各模块先冻结总架构中对应的接口契约，再并行开发。
- 业务模块不得直接 import 基础设施实现，必须通过 Port 注入。
- 跨模块通信只使用领域事件，不互相调用对方的私有 Service。
- 任何模块的 DTO 不得直接暴露数据库实体；跨层转换在 Data Access SDK 或业务层适配器完成。
- `zhiyin-boot` 是唯一允许装配具体实现的地方。
- **接口前缀只在 `zhiyin_api.app.create_app` 拼一次**（默认 `/api/v1`，取自
  `Settings.api_prefix`）。Controller 只写业务段（`/app/bootstrap`），前端 baseURL、
  vite proxy、反向代理、网关都只做原样转发——**任何地方再加一次 `/v1` 都会变成
  `/api/v1/api/v1/...`，结果是 404 而 OpenAPI 里看着有这条路由**。
  唯一例外是 `/healthz`（运维探针，不随版本变化）。守卫：`tests/test_api_prefix.py`。

## 五、核心调用流程

### 5.1 首次迷茫：首页进入 ① 采集建模

```text
用户点击「还不太清楚自己适合什么」
  → Home API
  → Orchestrator.readBlackboard()
  → Orchestrator.detectStage()
      ├─ 意图：迷茫 → 候选环节 COLLECT
      ├─ 轴 A：画像/行为少 → 探索自我
      └─ 轴 C：主理 = 建档分析师
  → LoopService.start(task, COLLECT, lead=建档分析师)
  → ProfileService.getGaps()
  → Agent.invoke(lead, 黑板上下文, collect_output_contract)
  → BehaviorService.log(answer)
  → ProfileService.updateField(confidence)
  → NotifyGateway.push(最短结论 + 下一个追问)
  → 返回前端
```

### 5.2 画像达标 → 交接 → ② 诊断匹配 → ③ 决策 → ④ 行动

```text
画像置信度达标
  → Orchestrator.handoff(COLLECT → DIAG, 职业顾问)
  → AgentRegistry.get(lead)
  → Agent.invoke(lead, 黑板上下文, report_output_contract)
      ├─ Agent 内部经 KnowledgeGateway.search(岗位/行业事实) 供事实
      └─ Agent 内部经 LLMGateway 生成结构化产出
  → AssetService.createReport(version=1, depends_on_profile_keys)
  → BehaviorService.log(diagnosis_view)
  → 用户认领差距 gap_claim
      → BehaviorService.log(gap_claim)
      → AssetService.updateGapClaim()
  → Orchestrator.move(DIAG → DECIDE)
  → Agent.invoke(lead, 黑板上下文, plan_output_contract)
  → 用户选择主攻方案
      → BehaviorService.log(decision_select)
      → AssetService.saveSelectedPlan()
  → Orchestrator.move(DECIDE → ACT)
  → Agent.invoke(lead, 黑板上下文, action_plan_output_contract)
  → 用户勾掉第一个任务
      → BehaviorService.log(task_done)
```

### 5.3 ⑤ 复盘与主动干预

```text
LocalScheduler 扫描行为日志
  → 检测 3 天无 task_done
  → Orchestrator.handoff(REVIEW, 陪伴教练)
  → 陪伴教练判别归因
      ├─ 任务太大 → 规划师重拆任务
      └─ 方向动摇 → 交接职业顾问，增量重算 ②③
  → 生成最小可执行动作
  → NotifyGateway.push(本地消息)
```

### 5.4 画像更新 → 影响面传播

```text
用户更新画像字段
  → ProfileService.updateField()
  → EventBus.publish("profile_field_updated")
  → AssetService.onProfileFieldUpdated()
      → 查找 depends_on_profile_keys 命中的资产
      → 只重算受影响片段
      → 资产版本 +1
      → 写 diff
```

## 七、非功能模块的骨架策略

### 7.1 安全默认通过层

```text
AuthGateway.authenticate(request)
    → DefaultPassAuth
    → return demo_user

SecurityGateway.encrypt(data)
    → NoopSecurity
    → return data

RateLimitGateway.allow(request)
    → NoopRateLimit
    → return true
```

约束：

- 第一期禁止写入真实手机号、真实简历、真实身份证等敏感信息。
- 所有演示数据必须显式标记 `DEMO`。

### 7.2 高并发默认单机骨架

```text
EventBusGateway.publish(event)
    → InMemoryEventBus
    → 同步调用本地监听器

SchedulerGateway.register(task)
    → LocalScheduler
    → 内存延迟队列 + 轮询
```

约束：

- 不引入分布式锁、消息队列、连接池调优。
- 业务代码不依赖多实例部署；若未来水平扩展，替换 Gateway。

## 一句话总结

第一期技术架构与总架构保持一致：仍采用「业务逻辑层 → 编排层 → Data Access SDK → 基础设施层」的四层结构，仅把编排层实现为 InMemory/Local，把基础设施层非核心能力实现为默认通过/本地骨架。团队按 `api / business / orchestration / data-sdk / infrastructure / boot` 拆包并行开发；优先落地 Orchestrator、五环节 Loop、黑板、工作台和影响面传播；高并发、安全、租户、真实推送、生产 RAG 等能力全部隔离在 Gateway 接口之后，用 Local/Mock/Noop 默认实现标记，确保业务逻辑和整体调用流程清晰、可运行、可演示、可验证。

### 11.2 三条可执行验收

| §九 验收项 | 验证方式 |
| --- | --- |
| 1 代码依赖图不存在反向依赖或跨层直连 | `tests/test_architecture.py`：AST 解析全部源码，按 §4.5.1 的允许矩阵逐条校验；越层即失败 |
| 8 骨架隔离（安全/限流/通知/知识库/向量检索均可通过 Gateway 替换） | `python -m zhiyin_boot --check`（或 `GET /healthz`）：逐部件输出 `wired / skeleton / not_wired` 与缺口归属；骨架状态由实现类的 `IMPLEMENTATION_STATUS` 自述，不靠目录名猜 |
| 里程碑门禁 | `python -m zhiyin_boot --check --phase=N`：按 `data/registry/assembly_gates.json` 校验某个里程碑的退出条件（M1 框架可验证 / M2 主干端到端 / M3 真实存储 / M4 生产化） |

### 11.3 实现边界

`--check` 会把未装配的部件标为 `not_wired` 并列在 `missing` 里，第一期预期为：
`orchestrator`、`profile_service`、`behavior_service`、`memory_service`、`asset_service`、
`workspace_service`、`function_service`、`identity_service`、`facade`（见 §4.5.1 模块归属）。
接口已冻结在 `zhiyin_business/ports/`，业务规则落位在 `zhiyin_business/policies/`，
异步执行者落位在 `zhiyin_business/workers/`；接上后 `not_wired` 自动变为 `wired`，
`--check --phase=2` 随即转绿，不需要改本文档。

> 本期已把上述能力位全部落为**类骨架**（文件、类名、签名就位，方法体
> `NotImplementedError`，`IMPLEMENTATION_STATUS = "skeleton"`，且**不进装配表**）。
> 因此 `--check` 仍如实报 `not_wired`：**文件存在不等于能力具备**。
> `--check` 输出里的 `skeletons` 是"外壳就位待实现"，`missing` 是"能力位没人管"。

> 约定：未实现的能力**必须**在 `--check` 中显式暴露，不允许出现「看起来装好了其实没实现」的假装配。
> 缺口归属读 `data/registry/ownership.json`（动态资源），不再硬编码在装配代码里。
