## 一、总体设计

### 1.1 总体架构图

```text
┌──────────────────────────────────────────────────────────────┐
│  前端 / BFF（zhiyin-api）                                     │
│  页面、任务入口、对话、工作台、资产、功能块                    │
└──────────────────────────┬───────────────────────────────────┘
                           │ HTTP / DTO
┌──────────────────────────v───────────────────────────────────┐
│  业务逻辑层（zhiyin-business）                                │
│  Orchestrator / Loop / Profile / Behavior / Asset / Workspace│
│  Function / 黑板                                              │
└──────────────────────────┬───────────────────────────────────┘
                           │ 编排原语
┌──────────────────────────v───────────────────────────────────┐
│  编排层（zhiyin-orchestration）                               │
│  Agent / Workflow / EventBus / Schedule / State / Notify      │
└──────────────────────────┬───────────────────────────────────┘
                           │ Repository / Gateway
┌──────────────────────────v───────────────────────────────────┐
│  Data Access SDK（zhiyin-data-sdk）                          │
│  Transaction / Cache / Search / Object / EventBus / Vector   │
└──────────────────────────┬───────────────────────────────────┘
                           │ Adapter
┌──────────────────────────v───────────────────────────────────┐
│  基础设施层（zhiyin-infrastructure）                          │
│  MySQL / Redis / Kafka / ES / pgvector / MinIO / pami / Local │
└──────────────────────────────────────────────────────────────┘
```

### 1.2 设计目标

1. 每一层都有单一职责，团队可独立开发与测试。
2. 业务逻辑只依赖抽象接口，不依赖具体基础设施。
3. 所有动态资源入库，所有跨层调用有显式契约。
4. 核心流程可本地运行、可演示、可验证。
5. 高并发、生产安全、多租户、真实推送、生产 RAG 暂不实现，但接口保留。

### 1.3 依赖约束

```text
zhiyin-api
  → zhiyin-business
    → zhiyin-orchestration
      → zhiyin-data-sdk
        → zhiyin-infrastructure
```

禁止反向依赖、禁止跨层直连。跨业务模块通信只能通过编排层 `EventBus`。

### 1.4 「事件 / 调度 / 通知」为什么只有两套接口（而不是两套重复定义）

这两类能力在本设计中是**分层**的，不是重复的。实现时不得再新增同义抽象：

| 层次 | 位置 | 形态 | 谁面向它编程 |
| --- | --- | --- | --- |
| **语义契约** | `zhiyin-orchestration`：`EventBus` / `Scheduler` / `Notifier` / `StateStore` | 带信封的领域事件（`DomainEvent`：event_id / occurred_at / idempotency_key）、调度策略（冷却期、触发次数上限）、一次性投递语义 | **业务层**。业务代码面向编排层编程，幂等与追溯由编排层保证 |
| **传输契约** | `zhiyin-data-sdk`：`EventBusGateway` / `SchedulerGateway` / `NotifyGateway` | `(event_type, payload)` 的裸投递、到点扫描、通道投递 | **基础设施层**实现，**编排层**调用 |

调用关系是「业务层 → 编排层语义契约 → SDK 传输契约 → 基础设施实现」，
即 `GatewayEventBus` / `GatewayScheduler` / `GatewayNotifier` 这三个包装类
（`zhiyin_orchestration/impl/`，一原语一文件）是两套接口之间**唯一**的粘合点。

> 判据：业务层只 import `zhiyin_orchestration`；编排层只 import `zhiyin_data_sdk`；
> 基础设施层只实现 SDK 的 Gateway。任一侧出现"另一套 EventBus/Scheduler"即为设计回退。

## 二、前端 / BFF 层详细设计

### 2.1 架构图

```text
┌──────────────────────────────────────────────────────────────┐
│  Browser / Demo Client                                        │
└──────────────────────────┬───────────────────────────────────┘
                           │ HTTP
┌──────────────────────────v───────────────────────────────────┐
│  zhiyin-api                                                   │
│  ┌──────────────┐  ┌──────────────┐  ┌──────────────┐        │
│  │ Controller    │  │ DTO Mapper    │  │ Validator     │        │
│  └──────┬───────┘  └──────────────┘  └──────────────┘        │
│         │                                                     │
│  ┌──────v──────────────────────────────────────────────┐      │
│  │ Application Facade                                  │      │
│  │  - 组装业务请求                                      │      │
│  │  - 读取动态资源                                      │      │
│  │  - 组装 View DTO                                    │      │
│  └──────────────────────────┬───────────────────────────┘      │
└───────────────────────────────┼────────────────────────────────┘
                                ↓
                    zhiyin-business 应用服务
```

### 2.2 实现逻辑

1. Controller 只做参数接收、格式校验和结果返回。
2. DTO Mapper 负责 API DTO 与业务 DTO 之间的转换。
3. Application Facade 调用业务层服务，并读取动态资源表组装页面数据。
4. BFF 不写业务规则，不直接访问数据库、模型、知识库。

### 2.3 详细要求

| 编号 | 要求 | 验收标准 |
| --- | --- | --- |
| `R-API-001` | 提供 `/app/bootstrap` 接口，返回菜单、路由、任务入口、文案、功能开关 | 前端启动只请求一次即可渲染首页 |
| `R-API-002` | 任务进入接口支持 `taskCode` 并返回任务会话 | 不同任务能路由到不同环节 |
| `R-API-003` | 对话消息接口支持会话续接 | 同一会话可跨请求恢复上下文 |
| `R-API-004` | 工作台接口按 ①-⑤ 聚合返回 | 工作台能展示画像、诊断、方案、计划、跟踪 |
| `R-API-005` | 资产接口返回资产版本与 diff | 前端能展示版本变化 |
| `R-API-006` | 所有接口统一错误码与 traceId | 前端可按错误码提示 |
| `R-API-007` | DTO 不直接暴露数据库实体 | 数据库字段变更不影响前端 |
| `R-API-008` | 登录鉴权通过 BFF 透传 | 第一期默认演示用户，后续替换真实鉴权 |

### 2.4 解析

BFF 层的核心是“翻译与组装”，不是“业务判断”。它把前端请求翻译成业务层调用，再把业务层返回的领域对象翻译成前端视图对象。动态资源读取放在这一层，能保证菜单、任务、文案等运营内容不需要前端发版。

## 三、业务逻辑层详细设计

### 3.1 架构图

```text
┌──────────────────────────────────────────────────────────────┐
│  zhiyin-business                                              │
│                                                              │
│  ┌────────────────────────────────────────────────────┐      │
│  │ Orchestrator                                       │      │
│  │  IntentRecognizer / StageResolver / LeadSelector   │      │
│  │  HandoffManager / DisclosureBuilder                │      │
│  └──────────────────────────┬─────────────────────────┘      │
│                             ↓                                 │
│  ┌────────────────────────────────────────────────────┐      │
│  │ LoopCoordinator                                    │      │
│  │  CollectLoop / DiagnoseLoop / DecideLoop / ActLoop │      │
│  │  ReviewLoop                                        │      │
│  └──────────────────────────┬─────────────────────────┘      │
│                             ↓                                 │
│  ┌────────────────────────────────────────────────────┐      │
│  │ 黑板访问服务                                        │      │
│  │  ProfileService / BehaviorService                  │      │
│  │  ConversationMemoryService / AssetService          │      │
│  └──────────────────────────┬─────────────────────────┘      │
│                             ↓                                 │
│  ┌────────────────────────────────────────────────────┐      │
│  │ WorkspaceService / FunctionService                 │      │
│  └────────────────────────────────────────────────────┘      │
└──────────────────────────────────────────────────────────────┘
```

### 3.2 核心实现逻辑

```text
Orchestrator.HandleMessage(sessionId, message)
  → 读取黑板
  → 识别意图
  → 判定环节
  → 选择主理 / 协理 / 信息侦查员
  → 调 LoopCoordinator 执行对应 Loop
  → 调编排层 AgentEngine 生成产出
  → 校验产出契约
  → 写行为日志和资产
  → 生成行为引导
```

### 3.3 详细要求

| 编号 | 要求 | 验收标准 |
| --- | --- | --- |
| `R-BIZ-001` | 编排器必须能按意图判定环节 | 六类首页任务至少路由到正确环节 |
| `R-BIZ-002` | 轴 A 阶段由后台推断，前端不要求用户选择 | 工作台和开场行为随阶段变化 |
| `R-BIZ-003` | 换主理、换理论、结论变化时生成显式告知 | 用户能看到依据 |
| `R-BIZ-004` | Loop 支持从任意环节进入 | 不需要重跑全部流程 |
| `R-BIZ-005` | 前序资产自动继承 | 会话续接不重复问、不整篇重生成 |
| `R-BIZ-006` | 画像字段更新带置信度和缺口 | 采集结束条件由置信度决定 |
| `R-BIZ-007` | 行为日志覆盖作答、认领、选择、勾任务、停滞、更新资料 | 行为闭环可统计 |
| `R-BIZ-008` | 诊断输出必须收敛到认领差距 | 诊断结束前出现差距认领 |
| `R-BIZ-009` | 决策输出主攻/平行/保底三套方案 | 用户可做可撤回选择 |
| `R-BIZ-010` | 行动计划任务可执行且有截止日期 | 任务颗粒度可勾掉 |
| `R-BIZ-011` | 复盘由真实行为信号触发 | 不出现自嗨式打扰 |
| `R-BIZ-012` | 影响面传播只重算受影响资产 | 资产版本 +1，diff 可见 |

### 3.4 解析

业务逻辑层是全系统最核心的一层。它不实现模型、知识库和数据库，但必须拥有完整的业务状态机。把 Orchestrator 与 LoopCoordinator 分开，是为了让“什么时候进入哪个环节”和“每个环节内部怎么做”解耦。黑板访问服务只负责读写状态，不负责跨环节编排。

## 四、编排层详细设计

### 4.1 架构图

```text
┌──────────────────────────────────────────────────────────────┐
│  zhiyin-orchestration                                         │
│                                                              │
│  ┌────────────┐  ┌────────────┐  ┌────────────┐             │
│  │ AgentEngine │  │ Workflow    │  │ EventBus    │             │
│  │ invoke      │  │ run         │  │ publish     │             │
│  └──────┬─────┘  └──────┬─────┘  └──────┬─────┘             │
│         │                │                │                   │
│  ┌──────v─────┐  ┌──────v─────┐  ┌──────v─────┐             │
│  │ Scheduler   │  │ StateStore  │  │ Notifier    │             │
│  │ register    │  │ read/write  │  │ push        │             │
│  └────────────┘  └────────────┘  └────────────┘             │
└──────────────────────────────────────────────────────────────┘
```

### 4.2 实现逻辑

- `AgentEngine` 负责根据 `agentId`、上下文和产出契约调用模型能力。
- `WorkflowEngine` 负责多步骤流程的串行、并行和失败降级。
- `EventBus` 负责领域事件发布、订阅、幂等消费。
- `Scheduler` 负责定时、延迟和主动事件触发。
- `StateStore` 负责共享状态读写和版本控制。
- `Notifier` 负责统一推送，第一期本地日志/消息表，后续接真实通道。

### 4.3 详细要求

| 编号 | 要求 | 验收标准 |
| --- | --- | --- |
| `R-ORC-001` | 编排层不得包含职引业务语义 | 代码中不出现五环节、画像、职业顾问等业务词 |
| `R-ORC-002` | Agent 调用必须校验产出契约 | 非法结构不会进入业务层 |
| `R-ORC-003` | 事件发布支持同步内存实现 | 第一期无 Kafka 也能触发影响面传播 |
| `R-ORC-004` | 调度任务可注册、取消、触发 | 停滞检测可运行 |
| `R-ORC-005` | 状态读写支持版本号 | 更新冲突可识别 |
| `R-ORC-006` | 通知接口支持本地与后续真实通道 | 替换 adapter 不影响业务层 |
| `R-ORC-007` | 事件类型与 payload 有明确契约 | 不同团队可按契约开发 |
| `R-ORC-008` | 编排层只通过 Data Access SDK 访问基础设施 | 不直连 MySQL、Redis、Kafka |

### 4.4 解析

编排层是“可复用的技术能力”，不是业务层。它的难点在于保持通用性：只能理解 `agentId`、`workflowId`、`eventType`，不能理解“建档分析师”“差距认领”。把业务语义留在业务层，后续才可能把编排层复用到 pami 平台其他应用。

## 五、Data Access SDK 详细设计

### 5.1 架构图

```text
┌──────────────────────────────────────────────────────────────┐
│  zhiyin-data-sdk                                              │
│                                                              │
│  ┌──────────────┐  ┌──────────────┐  ┌──────────────┐       │
│  │ Transaction   │  │ CacheGateway  │  │ SearchGateway │       │
│  │ executeTx     │  │ get/set/del   │  │ keyword/vector│       │
│  └──────┬───────┘  └──────────────┘  └──────┬───────┘       │
│         │                                    │                │
│  ┌──────v───────┐  ┌──────────────┐  ┌──────v───────┐       │
│  │ ObjectStore   │  │ EventBusGateway│  │ Repositories │       │
│  │ put/get/delete│  │ publish       │  │ Profile/Beh..│       │
│  └──────────────┘  └──────────────┘  └──────────────┘       │
└──────────────────────────────────────────────────────────────┘
```

### 5.2 实现逻辑

1. 业务层通过 Repository 接口访问数据。
2. SDK 统一处理租户上下文、事务、错误包装。
3. 检索类接口屏蔽 ES / pgvector 差异。
4. 对象类接口屏蔽 MinIO / 本地文件差异。
5. 缓存与事件接口保留，第一期可不启用真实实现。

### 5.3 详细要求

| 编号 | 要求 | 验收标准 |
| --- | --- | --- |
| `R-SDK-001` | 提供统一 Repository 接口 | 业务层不直接写 SQL |
| `R-SDK-002` | 事务接口保证业务写入一致性 | 黑板写入可原子提交 |
| `R-SDK-003` | 自动注入租户上下文 | 公共数据和私有数据查询可控 |
| `R-SDK-004` | 检索接口支持关键词、向量、混合检索 | 上层无需关心底层实现 |
| `R-SDK-005` | 对象接口支持本地文件与 MinIO 替换 | 切换存储不改业务代码 |
| `R-SDK-006` | 事件接口支持内存与 Kafka 替换 | 切换消息中间件不改业务代码 |
| `R-SDK-007` | 错误统一包装为 SDK 异常 | 业务层不感知数据库错误 |
| `R-SDK-008` | 向量、检索、对象不可用时提供降级 | 核心调用链不被阻塞 |

### 5.4 解析

Data Access SDK 是基础设施的“翻译层”。它不是为了加一层而加，而是为了把数据访问差异隔离在业务层之外。第一期先实现 Repository 和本地适配器，后续接 MySQL、pgvector、MinIO 时业务代码不变。

## 六、基础设施层详细设计

### 6.1 架构图

```text
┌──────────────────────────────────────────────────────────────┐
│  zhiyin-infrastructure                                        │
│                                                              │
│  ┌─────────────────────────────────────────────────────┐     │
│  │ Adapter 实现                                          │     │
│  │ PamiAuthAdapter / PamiLLMAdapter                     │     │
│  │ PamiKnowledgeAdapter / MySQLRepositories             │     │
│  │ PgVectorAdapter / ElasticsearchAdapter               │     │
│  │ MinioObjectStoreAdapter / KafkaEventAdapter          │     │
│  └──────────────────────────┬──────────────────────────┘     │
│                             ↓                                 │
│  ┌─────────────────────────────────────────────────────┐     │
│  │ 第一期默认实现                                        │     │
│  │ DefaultPassAuth / NoopSecurity / LocalOrMockLLM      │     │
│  │ LocalKnowledgeRepo / LocalKeywordSearch              │     │
│  │ LocalFileStore / InMemoryEventBus / LocalScheduler   │     │
│  └─────────────────────────────────────────────────────┘     │
└──────────────────────────────────────────────────────────────┘
```

### 6.2 实现逻辑

- 基础设施层只实现上层定义的接口。
- 所有外部系统访问都收敛到 Adapter。
- 第一期不接真实短信、OAuth、加密、向量库、消息队列。
- 后续替换 Adapter 时，业务层、编排层、SDK 无需改动。

#### 6.2.1 pami 对接点规划（生产替换目标）

| Adapter | 对接目标 | 关键接口 | 鉴权 |
| --- | --- | --- | --- |
| `PamiLLMAdapter` | pami Assistant / Model | `POST /service/api/openapi/v1/agent/conversation`、`POST /service/api/openapi/v1/agent/chat` | OpenAPI APIKey（应用 1:1） |
| `PamiKnowledgeAdapter` | pami Knowledge | `POST /user/api/v1/knowledge/doc/import`、`POST /user/api/v1/knowledge/doc/url/analysis` | JWT 服务账号 |
| `PamiRagAdapter` | pami RAG | `POST /service/api/openapi/v1/rag/chat` | OpenAPI APIKey |
| `PamiWorkflowAdapter` | pami AgentScope | 工作流保存、调试、运行与发布 API | pami 管理端 / 工作流 API |
| `PamiAuthAdapter` | pami IAM / Permission | `/user/api/v1/user`、`/user/api/v1/role`、`/user/api/v1/resource/*` | JWT 服务账号 |
| `MySQLRepository` | pami MySQL | `zhiyin_service` schema | 数据库账号 |
| `KafkaEventAdapter` | pami Kafka | 行为日志、影响面传播、主动事件 Topic | 复用 pami |
| `ElasticsearchAdapter` | pami ES | 全文检索 | 复用 pami |
| `MinioObjectStoreAdapter` | pami MinIO | 对象存储 | 复用 pami |
| `PgVectorAdapter` | 职引新增 pgvector | 语义检索 | 数据库账号 |

### 6.3 详细要求

| 编号 | 要求 | 验收标准 |
| --- | --- | --- |
| `R-INF-001` | 鉴权提供 DefaultPassAuth | 第一期演示可跳过真实登录 |
| `R-INF-002` | 安全提供 NoopSecurity | 不接敏感数据时可正常运行 |
| `R-INF-003` | 模型提供 LocalOrMockLLM | 无模型服务也能跑通流程 |
| `R-INF-004` | 知识库提供 LocalKnowledgeRepo | 诊断和决策有本地事实来源 |
| `R-INF-005` | 对象存储提供 LocalFileStore | 报告、导出可本地保存 |
| `R-INF-006` | 事件总线提供 InMemoryEventBus | 影响面传播本地可触发 |
| `R-INF-007` | 调度提供 LocalScheduler | 停滞检测可本地运行 |
| `R-INF-008` | 数据库只承载权威业务数据 | 权威事实不写进本地文件 |
| `R-INF-009` | 生产级 Adapter 只定义接口不提前实现 | 团队不被高并发/安全阻塞 |
| `R-INF-010` | 适配器通过 zhiyin-boot 装配 | 模块不自行 new 具体实现 |

### 6.4 解析

基础设施层的第一期重点是“可替换”。目标基础设施为 pami 平台，职引通过 Adapter 封装其 OpenAPI 与 JWT 接口；第一期使用 DefaultPassAuth、LocalOrMockLLM、LocalKnowledgeRepo 等本地实现，后续替换为 PamiAuthAdapter、PamiLLMAdapter、PamiKnowledgeAdapter。这样团队可以并行开发业务逻辑，同时基础设施团队按接口逐步接入真实 pami、MySQL、pgvector 和 MinIO。

## 九、高内聚低耦合验收要求

| # | 验收项 | 通过标准 |
| --- | --- | --- |
| 1 | 依赖方向 | 代码依赖图不存在反向依赖或跨层直连 |
| 2 | 接口隔离 | 各层只暴露最小必要接口 |
| 3 | 模块内聚 | 一个业务模块的修改不引起其他业务模块重新编译 |
| 4 | 事件解耦 | 跨模块行为通过事件触发，不直接调用私有方法 |
| 5 | 动态资源入库 | 文案、规则、提示词、页面结构均可在不发布代码的情况下修改 |
| 6 | 可替换性 | 替换基础设施 Adapter 时，业务层和编排层无需修改 |
| 7 | 可测试性 | 每层可使用 Mock/Noop 独立测试 |
