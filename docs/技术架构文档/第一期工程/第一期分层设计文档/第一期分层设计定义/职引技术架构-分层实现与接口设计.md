## 一、总体架构与设计目标

### 1.1 总体架构

```text
前端 / BFF（zhiyin-api）
   ↓
业务逻辑层（zhiyin-business）
   ↓
编排层（zhiyin-orchestration）
   ↓
Data Access SDK（zhiyin-data-sdk）
   ↓
基础设施层（zhiyin-infrastructure）
```

> 上图是**层次顺序**。`Data Access SDK → 基础设施层` 表示 SDK 只定义契约、不实现；
> 真正的代码依赖是 **基础设施层 → Data Access SDK**（infra 用 MySQL / Local / pami
> 适配器实现 SDK 抽象，属依赖倒置），因此 §九 验收项 1 检查的是 infra 不得 import 上层。

依赖方向固定为：

```text
zhiyin-api → zhiyin-business → zhiyin-orchestration → zhiyin-data-sdk → zhiyin-infrastructure
```

### 1.2 高内聚低耦合原则

| 原则 | 落地方式 |
| --- | --- |
| 单一职责 | 每层只处理自己的语义；业务层管业务，编排层管通用编排，SDK 管数据访问，基础设施层管原子能力 |
| 依赖倒置 | 上层依赖接口，不依赖具体实现；接口定义在 contract 或 SDK/编排层 |
| 单向依赖 | 只允许自上而下调用，禁止反向依赖与跨层直连 |
| 显式契约 | 跨层调用必须有接口签名、DTO、事件契约和产出契约 |
| 配置与代码分离 | 文案、任务、规则、提示词、页面结构、通知模板等动态资源全部入库 |
| 领域事件解耦 | 跨业务模块通信通过事件总线，不互相调用私有 Service |
| 数据访问收敛 | 所有存储、检索、对象、向量访问都通过 Data Access SDK |

### 1.3 契约归属与 BFF 取数口径（实现约定）

依赖方向要有可检查的判据，因此明确三条：

| 约定 | 说明 |
| --- | --- |
| 数据形状是跨层共享契约 | `Profile / ProfileField / AssetVersion / TaskSession / Report / DirectionPlan / ActionPlan` 等**读模型与枚举**集中定义在共享内核 `zhiyin_kernel`（`zhiyin-src/template/zhiyin-kernel/zhiyin_kernel/`），是全系统唯一的"数据形状"定义处。这是「每层只暴露自己的 DTO」的唯一例外，原因见下 |
| 例外理由 | Repository 的入参与返回值就是这些模型（§2.4）。若把它们上移到业务层，SDK 契约就要反向依赖业务层，反而破坏单向依赖；因此选择"契约下沉、实现收敛" |
| BFF 不得直连数据访问契约 | `zhiyin-api` 只允许依赖 `zhiyin-business` 与共享内核 `zhiyin_kernel`。api 需要领域取值（环节、资产类型、任务状态等）时**直接读内核形状**（`zhiyin_business.published` 发布面已删除，见《目标架构设计》§2.2）；但**不得** import `zhiyin_data_sdk`（数据访问契约） |

> 这三条把 §九 验收项 1「代码依赖图不存在反向依赖或跨层直连」变成可执行断言：
> `zhiyin-src/template/tests/test_architecture.py` 用 AST 解析全部源码逐层校验，
> 越层即测试失败。维护契约时请先跑该测试。

## 二、各层实现逻辑与接口设计

### 2.1 前端 / BFF 层

#### 职责

- 接收前端请求，做参数校验、登录态透传、DTO 转换。
- 从动态资源库读取页面结构、菜单、任务入口、文案和功能开关。
- 调用业务层接口，组织视图数据。
- 不写业务规则，不直接访问数据库、模型、知识库。

#### 核心接口

| 接口 | 说明 |
| --- | --- |
| `GET /zhiyin/api/app/bootstrap` | 启动时返回菜单、路由、任务入口、文案、功能开关 |
| `POST /zhiyin/api/task/enter` | 用户选择首页任务 |
| `POST /zhiyin/api/conversation/message` | 发送对话消息 |
| `GET /zhiyin/api/workspace/overview` | 获取智能工作台总览 |
| `GET /zhiyin/api/asset/{assetType}/{assetId}` | 获取报告、方案、计划资产 |
| `POST /zhiyin/api/action/task/{taskId}/done` | 勾选行动任务 |
| `GET /zhiyin/api/review/messages` | 获取陪伴教练消息 |
| `POST /zhiyin/api/auth/login-demo` | 第一期演示登录 |

#### 实现逻辑

```text
前端请求
  → BFF 校验参数
  → 读取 app_bootstrap / 功能开关 / 文案配置
  → 调用 zhiyin-business 对应 Application Service
  → 组装 View DTO
  → 返回前端
```

### 2.2 业务逻辑层（zhiyin-business）

#### 职责

- 实现职引业务语义：三轴、五环节、黑板、资产影响面、工作台聚合。
- 编排器在本层实现，负责意图识别、环节判定、主理/协理选择、交接和显式告知。
- 不直接调用模型、知识库、数据库、对象存储、消息通道。

#### 核心模块

| 模块 | 职责 |
| --- | --- |
| Orchestrator | 判定环节、选择主理、处理交接、显式告知 |
| LoopCoordinator | 五环节状态机、可拆可续 |
| ProfileService | 画像活状态与缺口 |
| BehaviorService | 行为日志 |
| ConversationMemoryService | 会话记忆、摘要与跨会话续接 |
| AssetService | 报告、方案、计划、版本与影响面 |
| WorkspaceService | 工作台聚合 |
| FunctionService | 日历、成就、导出、导师建议 |

#### 核心接口

```text
Orchestrator
  RouteTask(userId, taskCode) -> TaskSession
  HandleMessage(sessionId, message) -> MessageResult
  Handoff(sessionId, fromStage, toStage, reason)
  SelectLead(axisA, axisB, intent) -> LeadDecision
  BuildDisclosure(changeType, context) -> Disclosure

LoopCoordinator
  Start(taskSession, stage)
  Advance(sessionId, fromStage, toStage)
  Resume(sessionId)
  GetState(sessionId)

ProfileService
  GetLiveProfile(userId)
  UpdateField(userId, fieldKey, value, confidence, source)
  GetGaps(userId)

BehaviorService
  Log(userId, eventType, payload)
  Query(userId, eventType?, timeRange?)

ConversationMemoryService
  GetByTask(userId, taskSessionId)
  UpsertSummary(userId, taskSessionId, leadAgent, summary)

AssetService
  CreateReport(userId, profileVersion)
  CreatePlans(userId, reportId)
  SelectPlan(userId, planId)
  CreateActionPlan(userId, planId)
  RegenerateAffectedAssets(userId, profileKeys)
  GetAsset(assetType, assetId)

WorkspaceService
  GetOverview(userId)
  GetStageView(userId, stage)

FunctionService
  GetCalendar(userId)
  GetAchievements(userId)
  ExportAsset(assetType, assetId, format)
  AddMentorAdvice(userId, mentorId, advice)
```

#### 实现逻辑

```text
Orchestrator
  → 读取黑板（画像 / 行为 / 会话记忆）
  → 判定轴 B 环节
  → 按轴 A 阶段 × 轴 B 环节 × 意图选择主理
  → 调用编排层 AgentEngine.invoke
  → 校验产出契约
  → 写行为日志与资产
  → 生成行为引导
```

### 2.3 编排层（zhiyin-orchestration）

#### 职责

- 提供通用编排原语：Agent、Workflow、EventBus、Schedule、State、Notify。
- 不定义“画像”“差距”“五环节”“建档分析师”等职引业务概念。
- 不写职引提示词、理论卡、产出 schema。

#### 核心接口

```text
AgentEngine
  invoke(agentId, context, contract) -> StructuredOutput

WorkflowEngine
  run(workflowId, input) -> WorkflowResult

EventBus
  publish(eventType, payload) -> EventId
  subscribe(eventType, handler) -> SubscriptionId

Scheduler
  register(spec, action) -> ScheduleId
  cancel(scheduleId)

StateStore
  read(namespace, key) -> StateValue
  write(namespace, key, value, expectedVersion?) -> StateValue

Notifier
  push(sessionId, channel, payload) -> NotifyResult
```

#### 实现逻辑

```text
业务层调用 AgentEngine.invoke
  → 从 agent_registry 读取 agent_id 对应能力包
  → 注入上下文与产出契约
  → 调用基础设施层模型能力
  → 返回结构化产出

业务层发布领域事件
  → EventBus.publish
  → 订阅者执行影响面传播 / 主动事件 / 通知
```

### 2.4 Data Access SDK（zhiyin-data-sdk）

#### 职责

- 封装数据访问、事务、缓存、检索、对象存储、向量检索、事件发布。
- 自动注入租户上下文、统一错误与降级。
- 业务层只依赖 SDK 接口，不感知底层 MySQL、Redis、Kafka、ES、pgvector、MinIO。

#### 核心接口

```text
TransactionManager
  executeTx(work) -> Result

ProfileRepository
  getField(userId, fieldKey)
  saveField(profileField)
  listFields(userId)
  listGaps(userId)

BehaviorRepository
  append(behaviorEvent)
  query(userId, filter)

ConversationMemoryRepository
  getByTask(userId, taskSessionId)
  upsertSummary(userId, taskSessionId, leadAgent, summary)
  listByUser(userId)

AssetRepository
  saveVersion(assetVersion)
  listVersions(userId, assetType, assetId)

AgentRepository
  get(agentId)
  listEnabled()

TheoryRepository
  get(theoryCode)
  listByStage(stage)

KnowledgeGateway
  search(query, namespace, filter)

ObjectStoreGateway
  put(bucket, key, data)
  get(bucket, key)
  delete(bucket, key)

EventBusGateway
  publish(eventType, payload)
  consume(eventType, handler)

SearchGateway
  keywordSearch(query, filter)
  vectorSearch(queryEmbedding, filter)
  hybridSearch(query, queryEmbedding, filter)

CacheGateway
  get(key)
  set(key, value, ttl?)
  delete(key)
```

#### 实现逻辑

```text
Repository 接口由基础设施层实现
  → zhiyin-data-sdk 只定义契约
  → zhiyin-infrastructure 提供 MySQL/Local/Mock 适配器
  → zhiyin-boot 完成装配
```

### 2.5 基础设施层（zhiyin-infrastructure）

#### 职责

- 提供 pami 平台原子能力适配，以及第一期的默认通过/Local/Mock 实现。
- 不感知业务语义，不依赖上层模块。

#### 主要适配器

| 适配器 | 实现 |
| --- | --- |
| `PamiAuthAdapter` | 后续接 pami IAM；第一期 `DefaultPassAuth` |
| `PamiLLMAdapter` | 后续接 pami Assistant/Model；第一期 `LocalOrMockLLM` |
| `PamiKnowledgeAdapter` | 后续接 pami knowledge-service；第一期 `LocalKnowledgeRepo` |
| `PamiWorkflowAdapter` | 后续接 pami AgentScope；第一期 `WorkflowEngine` 骨架 |
| `MySQLProfileRepository` | 画像、行为、会话记忆、资产数据 |
| `RedisCacheAdapter` | 后续接缓存；第一期可不启用 |
| `KafkaEventAdapter` | 后续接 Kafka；第一期 `InMemoryEventBus` |
| `PgVectorAdapter` | 后续接 pgvector；第一期 `LocalKeywordSearch` |
| `MinioObjectStoreAdapter` | 后续接 MinIO；第一期 `LocalFileStore` |

#### 实现逻辑

```text
基础设施层实现 Data Access SDK 或编排层定义的接口
  → 通过配置装配到 zhiyin-boot
  → 第一期优先使用本地/默认通过实现
  → 后续切换为 pami / Kafka / pgvector / MinIO 时只替换 adapter
```

## 三、动态资源入库原则

所有可配置、可运营、可修改的内容都应进入数据库，禁止散落在代码、JSON 硬编码或前端静态文件中。

### 3.1 必须入库的内容

| 类别 | 示例 |
| --- | --- |
| 前端动态内容 | 页面、区块、组件、菜单、路由、任务入口、文案、横幅、FAQ、信任背书 |
| 后端动态配置 | 智能体、理论卡、产出契约、提示词模板、工作流模板、决策规则、交接规则、事件规则、调度规则、通知模板 |
| 业务动态资源 | 任务、理论卡、知识源、职业库、JD、模型版本、向量命名空间 |
| 系统配置 | 功能开关、枚举字典、多语言文案、租户配置、对象桶、鉴权提供方、限流策略 |

### 3.2 统一配置模式

所有动态资源表建议具备以下通用字段，但不要求在本文展开：

- `id`
- `code`
- `name`
- `status`
- `version`
- `sort_order`
- `effective_at`
- `expire_at`
- `created_at`
- `updated_at`

## 五、动态资源的配套治理

### 5.1 前端动态内容

- 页面/区块/组件通过 `app_page`、`app_page_section`、`app_component` 组装。
- 文案不写死在 JSX/HTML，统一从 `app_copy` 读取。
- 任务入口由 `app_task_entry` + `app_task_option` 驱动，新增任务不改前端代码。
- 导航、路由、横幅、信任背书、FAQ 全部支持配置上下线与排序。

### 5.2 后端动态配置

- 智能体、理论卡、产出契约、提示词模板、工作流模板均入库。
- 意图判定、交接、事件路由、主动调度、通知模板均通过规则表配置。
- 知识源、嵌入模型、向量命名空间、对象桶、鉴权提供方、限流策略均通过配置表管理。
- 第一期可以只读这些表或使用默认数据，但表结构应提前保留。

### 5.3 缓存与版本

- 高频读配置可缓存，但必须带版本号，变更后失效。
- 规则类配置建议支持发布版本，回滚时切回上一版本。
- 页面文案与前端资源应有生效时间、失效时间和排序字段。

## 六、其他类似内容

### 6.1 跨层 DTO 与事件契约

- 每层只暴露自己的 DTO，不直接透传数据库实体。
- 事件类型集中在 `zhiyin-orchestration` 的事件契约中定义。
- 关键事件建议：`profile_field_updated`、`gap_claim`、`decision_select`、`task_done`、`task_stall`、`asset_version_changed`。

### 6.2 错误与降级

- 业务层抛业务异常，不抛底层驱动异常。
- Data Access SDK 统一包装数据库、检索、对象存储错误。
- 第一期外部能力失败时走默认通过或本地兜底，不中断核心调用链。

### 6.3 日志与追踪

- 每层输出结构化日志，包含 `traceId`、`userId`、`sessionId`、`stage`、`agentId`。
- 编排器每次交接、影响面传播、主动事件都记录原因与结果。

### 6.4 配置变更影响面

- 提示词、理论卡、产出契约、交接规则变更需记录版本。
- 涉及智能体产出结构变化时，必须同时更新 `output_contract` 和对应测试用例。

---

## 一句话总结

总架构按「前端/BFF → 业务逻辑层 → 编排层 → Data Access SDK → 基础设施层」单向分层实现；各层职责单一，通过接口与事件解耦。所有前端动态内容和后端动态配置统一入库，首期规划动态资源表 38 张，核心业务表另按总体架构落地。
