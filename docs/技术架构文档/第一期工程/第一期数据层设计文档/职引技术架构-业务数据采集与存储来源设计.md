## 一、三条基本原则

| 原则 | 说明 |
| --- | --- |
| 公共知识不进画像 | 专业介绍、职业介绍、岗位 JD 等**跨用户共享**的公共知识只入公共知识库，**绝不写入 `profile_field`** |
| 个人数据不进公共库 | 用户简历、测评结果、目标职业等**只属于某个用户**的数据只入个人画像/资产，不回流公共库 |
| 公共知识只作引用 | 公共知识在报告/方案中只作为 `evidence` / `sources` 引用，不直接变成用户结论 |

一句话判定：**数据描述的是"世界"还是"这个人"？世界的入公共库，这个人的入画像。**

## 三、重点来源拆解

### 3.1 学职平台（SR-1）· 专业与职业主来源

平台栏目与采集对象：

| 栏目 | 路径 | 采集内容 | 存储归属 |
| --- | --- | --- | --- |
| 专业洞察 / 专业百科 | `/speciality/index.action`、`/speciality/detail.action?specId=...` | 专业基本信息、培养目标、开设课程、专业满意度、从业情况、专业点分布、考研方向、从业方向 | 公共知识库（专业库） |
| 职业探索 / 职业百科 | `/occupation/index.action` | 职业介绍、任务职责、知识技能与资格要求、工作环境、发展前景、毕业生能力模型 | 公共知识库（职业库） |
| 职业人物 / 职业案例 | `/occucase/index.action` | 真实从业案例、任职能力、常用工具、薪酬与环境 | 公共知识库（案例，可选） |
| 职业微视频 / 就业指导课 | `/video/`、`/jyzdk/` | 视频元数据、标题、简介 | 公共知识库（内容索引） |
| 职业测评 | `/survey/index.action` | 测评题目与维度 | **不采集**，由用户在平台完成，结果授权后进画像 |

采集要点：

- 专业以「专业代码 / 专业名称」为唯一键，职业以「职业编码 / 职业名称」为唯一键，便于去重与更新。
- 每个专业/职业必须保留 `source_url`（详情页地址）与 `fetched_at`，供报告引用与追溯。
- 专业与职业之间建立映射（专业 → 对应从业方向 → 职业），是 ② 诊断匹配的关键数据。

### 3.2 BOSS 直聘（SR-5）· 岗位来源（实际爬取）

#### 3.2.1 采集入口

| 页面 | 地址 | 采集内容 |
| --- | --- | --- |
| 职位搜索列表页 | `/web/geek/job?query={关键词}&city={城市编码}&page={页码}` | 岗位卡片：`jobId`、岗位名、薪资、城市、经验、学历、技能标签、公司行业/规模 |
| 职位详情页 | `/job_detail/{jobId}.html` | 岗位职责、任职要求、福利、发布时间 |
| 搜索筛选项 | 搜索页筛选组件 | 城市编码、行业、薪资区间、经验/学历筛选项 |

#### 3.2.2 采集方式

- 页面为动态渲染 + 参数签名，**不使用纯 HTTP 抓取**，采用无头浏览器（Playwright / Selenium + Headless Chrome）渲染后解析 DOM。
- 抓取前先取列表页拿到 `jobId` 清单，再按需进入详情页；列表页负责全量发现，详情页负责内容补全。
- 抓取清单按「城市 × 岗位关键词」配置，关键词映射到职业库节点，避免全站无目的抓取。

#### 3.2.3 反爬应对

| 反爬手段 | 应对措施 |
| --- | --- |
| 登录态校验 | 维护登录态 Cookie 池，定期校验有效性并轮换 |
| 动态渲染 / 接口签名 | 无头浏览器渲染后解析 DOM，不逆向签名接口 |
| 频率限制 | 单账号低频、串行抓取、随机间隔 3~10 秒 |
| IP 限制 | 代理 IP 池轮换，失败指数退避重试 |
| 验证码 / 风控 | 触发即暂停该账号并降频，**不强行绕过**；连续触发则整体停采 |
| 字体 / 数字混淆 | 薪资等字段做解析校验，异常值直接丢弃 |

#### 3.2.4 字段映射与落地

| 字段 | 落地位置 | 说明 |
| --- | --- | --- |
| `jobId` | 公共库（唯一键） | 平台岗位 ID |
| 岗位名称 | 公共库 | 映射到职业库职业编码 |
| 岗位职责 / 任职要求 | 公共库（结构化 JD） | 抽取为「能力要求结构」 |
| 技能标签 | 公共库 | 用于 ②③ 的能力差距计算 |
| 城市 / 经验 / 学历 | 公共库 | 岗位条件维度 |
| 薪资区间 | 公共库（统计用） | 只做区间统计，不落个人画像 |
| 公司行业 / 规模 | 公共库（脱敏） | 只保留行业与规模，不含公司名 |
| 公司名 / 联系方式 | **不入库** | 商业敏感，脱敏丢弃 |
| 列表页 / 详情页原始 HTML | 缓存 | 采集中间产物，只进缓存，过期即丢 |

#### 3.2.5 去重与更新

- 唯一键 `jobId`；同岗位重新抓取时比对内容哈希，有变化才更新版本。
- 岗位下架后按 `jobId` 标记失效，不物理删除，供后续统计回溯。

#### 3.2.6 合规与边界

- 仅用于内部研究/演示，不对外分发平台原始内容，不采集任何求职者个人信息。
- 采集模块独立部署、独立限流，可一键停采与按 `jobId` 批量下架。

## 四、存储决策规则

### 4.1 三种落地形态

| 形态 | 判据 | 存储位置 | 生命周期 |
| --- | --- | --- | --- |
| **A 公共知识库** | 跨用户共享、长期有效、需被引用 | MySQL 知识表 + 本地 JSON（后续 pgvector/ES） | 长期，带版本 |
| **B 缓存 / 快照** | 时效短、量大、可丢、可重建 | 本地内存缓存 / 本地对象目录 | 短期，可随时清空 |
| **C 个人画像 / 资产** | 只属于某个用户本人 | MySQL `profile_field` / 业务资产表 | 长期，带版本与影响面 |

### 4.2 判定规则

```text
采集到一条数据
  ├─ 它描述的是「用户本人」吗？（简历、专业、测评结果、目标职业、经历）
  │     ├─ 是 → C 个人画像（必须带 source + confidence + evidence）
  │     └─ 否 → 继续判断
  ├─ 它能长期复用、会被报告引用吗？（专业库、职业库、政策、岗位要求结构）
  │     ├─ 是 → A 公共知识库（带 source_url + fetched_at + version）
  │     └─ 否 → B 缓存/快照（实时岗位列表、原始页面、搜索热词）
```

红线：

1. 公共知识**永不**写入 `profile_field`。
2. 爬取的原始 HTML/JSON **只进缓存**，不进任何库。
3. 未经用户确认的抽取结果 **不得**直接入画像（需在采集环节向用户确认）。

## 五、各来源处理流程

### 5.1 通用处理流程

```text
① 采集（Fetch）
     → 定时任务 / 手动触发 / 用户上传
② 解析（Parse）
     → HTML/JSON → 原始字段
③ 清洗与归一化（Normalize）
     → 去广告、统一枚举、标准化名称与编码
④ 去重与更新（Dedup / Upsert）
     → 唯一键比对 → 新增或更新版本
⑤ 审核（Review）
     → 规则校验 + 人工抽检（第一期简化为规则校验）
⑥ 分流存储（Store）
     → A 公共知识库 / B 缓存 / C 个人画像
⑦ 索引与引用（Index）
     → 供 ②③ 检索引用（第一期本地关键词，后续向量化）
```

### 5.2 分词来源的处理流程

| 来源 | 采集方式 | ③ 归一化 | ④ 唯一键 | ⑥ 落地 | 是否入画像 |
| --- | --- | --- | --- | --- | --- |
| SR-1 专业百科 | 定时低频抓取 | 专业名称/代码/门类/学科标准化 | 专业代码 | **A 公共库** | ❌ 否（用户自己的专业才入画像） |
| SR-1 职业百科 | 定时低频抓取 | 职业名称/编码/能力要求标准化 | 职业编码 | **A 公共库** | ❌ 否 |
| SR-1 职业案例/视频 | 定时低频抓取 | 标题、标签、时长 | 内容 ID | **A 公共库**（内容索引） | ❌ 否 |
| SR-1 职业测评 | 不采集 | — | — | 用户完成测评后结果 → **C 画像** | ✅ 是（兴趣/性格/价值观） |
| SR-2 阳光志愿 | 定时低频抓取 | 专业/院校标准化 | 专业代码/院校代码 | **A 公共库** | ❌ 否 |
| SR-3 24365 岗位 | 定时抓取 | 岗位名映射职业编码 | 岗位指纹（名称+城市+要求哈希） | 精选后 **A 公共库** | ❌ 否 |
| SR-4 公共招聘网 | 定时抓取 | 同上 | 同上 | 精选后 **A 公共库** | ❌ 否 |
| SR-5 BOSS 直聘 | 无头浏览器实际爬取 | 岗位名映射职业编码、公司信息脱敏 | `jobId` | 岗位结构 → **A 公共库**；原始 HTML → **B 缓存** | ❌ 否 |
| SR-7 政策/统计 | 手动/低频抓取 | 标题、发布机构、时间 | 官方文号 | **A 公共库** | ❌ 否 |
| SR-8 职业资格 | 手动/低频抓取 | 资格名称、等级 | 资格编码 | **A 公共库** | ❌ 否 |
| 用户简历上传 | 用户上传 | 抽取学业/技能/经历 | `(user_id, field_key)` | 原件 → 对象存储；抽取字段 → **C 画像** | ✅ 是 |
| 用户在线测评 | 平台内完成 | 维度得分标准化 | `(user_id, 测评ID)` | 结果 → **C 画像** | ✅ 是 |
| 用户对话提及 | 对话抽取 | 字段抽取 | `(user_id, field_key)` | **C 画像**（低置信，需确认） | ✅ 是 |
| 实时岗位列表 | 抓取快照 | — | — | **B 缓存**（过期即丢） | ❌ 否 |
| 原始页面 | 抓取 | — | URL | **B 缓存** | ❌ 否 |

### 5.3 面向画像的入口条件

只有满足以下全部条件的数据才允许进入 `profile_field`：

| 条件 | 说明 |
| --- | --- |
| 主体是用户本人 | 数据描述用户自身（专业、经历、兴趣、目标），不是外部世界 |
| 有明确来源 | `source ∈ {简历, 对话, 测评, 行为推断, 导师建议}` |
| 有置信度 | 用户显式输入 1.0；简历解析 0.6~0.9；对话抽取 0.6~0.9；行为推断 0.3~0.7 |
| 有证据 | 记录原话/简历片段/测评报告 ID 作为 `evidence` |
| 已确认（推荐） | 抽取类数据在采集环节向用户确认后再落库 |

## 七、采集规范与合规

| 编号 | 规范 | 说明 |
| --- | --- | --- |
| `R-CRAWL-001` | 尊重 robots 与用户协议 | 禁止抓取明确禁止抓取、需登录或超出协议范围的页面 |
| `R-CRAWL-002` | 限频 | 单站点低频、串行、带随机间隔，避免影响对方服务 |
| `R-CRAWL-003` | 标识身份 | 请求头带可识别 UA 与联系方式（第一期本地调试除外） |
| `R-CRAWL-004` | 只取公开信息 | 不采集个人隐私、不采集需授权才能访问的内容 |
| `R-CRAWL-005` | 不存原帖 | 岗位类数据只保留结构化要求，不复制平台原始内容 |
| `R-CRAWL-006` | 保留来源 | 每条入库数据必须带 `source_url` + `fetched_at`，支持溯源与下架 |
| `R-CRAWL-007` | 可下架 | 支持按来源/唯一键批量删除，响应对方下架要求 |
| `R-CRAWL-008` | 风险站点专项管控 | SR-5 BOSS 直聘等强反爬站点必须独立模块、独立限流，维护登录态池、代理池与一键停采/下架能力 |
| `R-CRAWL-009` | 风控即停 | 触发验证码或风控时立即暂停该账号并降频，连续触发则整体停采，不强行绕过 |

第一期落地方式：**采集链路按来源独立实现**——学职平台等静态站点用定时抓取，BOSS 直聘用无头浏览器采集；两者都走「采集 → 归一化 → 分流存储 → 引用」统一流程，结构化结果入公共库，原始响应只进缓存。

## 八、落库位置与表约定

| 本设计的对象 | 落库位置 | 说明 |
| --- | --- | --- |
| 公共知识（专业/职业/岗位/政策） | MySQL 知识表 + 本地 JSON | 来源与分类由 `knowledge_source`、`knowledge_category` 配置维护 |
| 检索与向量命名空间 | `occupation`、`jd`、`theory` 等 | 第一期用本地关键词检索，后续接 pgvector/ES |
| 个人画像字段 | `profile_field`、`profile_gap` | 见第一期技术架构文档 §6.2 核心业务表 |
| 采集与分流处理 | 同步写入 / 异步处理 | 采集侧写公共库，用户侧写画像 |
| 采集来源配置与治理 | `knowledge_source` + 变更流程 | 新增来源需登记并明确存储归属 |

## 一句话总结

业务数据分两类：**描述世界的进公共知识库**（学职平台的专业/职业百科为主来源，阳光志愿、24365、公共招聘网、政策统计为补充，BOSS 直聘通过无头浏览器实际爬取岗位列表与详情并结构化入库）；**描述本人的进个人画像**（简历、测评、目标职业、对话抽取，且必须带 source、confidence、evidence 并经确认）。所有采集统一走「采集 → 解析 → 归一化 → 去重 → 审核 → 分流（公共库 / 缓存 / 画像）→ 索引引用」流程：长期可复用的入公共库、时效量大可丢的只进缓存、涉及用户本人的才入画像，公共知识绝不写进画像，爬取原始内容一律不入库。
