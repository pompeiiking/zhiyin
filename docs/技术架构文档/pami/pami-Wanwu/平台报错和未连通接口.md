# Wanwu 平台问题与未接通接口汇总

> 整理日期：2026-09-13  
> 状态口径：以官方原始源码和官方镜像为准。本地验证过的修改仅作为修复思路，不代表官方平台状态已经改变。  
> 范围：只记录已经实际触发并确认的 Wanwu 平台代码、接口、路由和前端处理问题；不收录依赖推断或尚未执行的接口，不记录 Docker 构建、网络拉取、本地模拟服务、测试脚本、测试数据或命令问题。

> 当前工作区状态：本表同时区分“官方基线问题”和“当前工作区已修复项”。已在当前工作区修复的项以 [接口.md](接口.md) §6 的回归结果为准，不重复作为当前阻断项。

## 1. 问题所在的整体流程

```text
外部程序或前端
  → 8081 / Nginx
  → BFF 路由与 JWT/API Key 鉴权
  → 模型、知识库、RAG、智能体、工作流等业务配置
  → RAG 检索或 Agent 路由判断
  → BFF 内部模型回调
  → Action / MCP / 工作流执行
  → SSE 或 JSON 返回
  → 前端或外部程序处理正文、完成标记和错误码
```

## 2. 平台问题总表

| 编号 | 流程位置 | 平台现象/错误 | 平台根因 | 影响 | 修复思路 |
| --- | --- | --- | --- | --- | --- |
| P01 | BFF 返回智能体详情 | 实测 `GET /user/api/v1/assistant` 返回 HTTP 200 但正文为空；服务端出现 `unexpected end of JSON input` | 实测对象的 `externalConfig` 是空字符串，BFF 转换成 `json.RawMessage` 后无法序列化 | 前端显示“Error/无信息”，外部程序无法取得配置 | BFF 将空字符串规范化为合法 JSON `null`；成功判定同时检查 HTTP、业务码和非空正文 |
| P02 | Action 服务启动 | Gunicorn worker 报 `KeyError: 'ACTION'`，1992 没有可用 worker | Action 代码读取 `[ACTION]`，官方配置文件实际只有 `[AUTH]` | 智能体未命中 RAG 后无法进入 Action | 统一配置节名称；健康检查应等待 worker 稳定并请求真实健康接口 |
| P03 | Agent 调用 Action | 实测出现 `HTTPConnectionPool(host='172.17.0.1', port=1992) ... Connection refused` | Action 地址被硬编码为特定 Docker 网关；两个进程实际位于同一容器 | 智能体试运行和应用广场已出现无回复 | 默认使用 `127.0.0.1:1992`，支持 `ACTION_SERVER_URL` 配置，不依赖固定网段 |
| P04 | Action 调用 Wanwu 模型 | `Invalid URL 'xxx/xxx/token': No scheme supplied` | 内部模型回调仍走遗留外部鉴权，默认地址是占位值 | Wanwu 中配置的模型不能被 Action 正常调用 | 内部回调使用内部凭据或明确的占位 key；直连外部模型时才走供应商鉴权 |
| P05 | Action HTTP/SSE 响应 | HTTP 500：`action_infer did not return a valid response` | 路由预读生成器；无输出时返回 `None`，有输出时丢失第一块 | 调用方收到 500 或缺少首个片段 | 始终返回流式 `Response`，不要预读生成器；异常也输出结构化终止事件 |
| P06 | Action 错误处理 | `'generator' object has no attribute 'text'` | 空响应分支把生成器当作 HTTP Response 读取 `.text` | 原始模型错误被二次异常覆盖 | 定义统一返回类型；错误分支使用显式异常对象，不读取生成器 `.text` |
| P07 | 配置工具但无需调用 | 模型判断可以直接回答，应用广场却返回空正文 | ReAct 返回“自行回答”后，Action HTTP 层清空 `action_output` | 实测挂载工具的智能体无法回答普通问题 | 为“模型自行回答”建立成功分支，使用当前模型生成正文 |
| P08 | 前端消费智能体 SSE | 后端返回 `code:1, finish:1` 后页面仍保持加载或空白 | 前端智能体分支只处理 `code === 0` 和 `code === 7` | 用户误以为模型仍在运行，错误原因不可见 | 所有 `finish:1` 都结束加载；统一显示非 0 业务码和错误信息 |
| P09 | 资源成员授权写入 | `PUT /user/api/v1/resource/permissions` 返回 HTTP 403、code 110003、`auth错误: EOF` | `Record` 中间件读取请求体后未恢复，handler 再次绑定时读到 EOF | 外部程序无法稳定设置授权成员；查询路径部分可用 | 恢复 `ctx.Request.Body`，或统一使用可复用缓存的绑定方法 |
| P10 | 子组织状态管理 | `PUT /user/api/v1/org/status` 返回 code 13、`nil pointer dereference` | 子组织启停服务链存在未判空对象 | 外部程序不能安全启用或停用组织 | 补齐组织及关联对象判空；无效 ID 返回明确业务码 |
| P11 | 内部知识库名称查询 | `GET /user/api/v1/api/category/info` 返回无权限或资源不存在 | `OrgId` 缺少 GET query 绑定标签 | 按名称查询知识库失败 | 为 `OrgId` 增加 query 绑定，并验证 categoryName、userId、orgId |
| P12 | Python 节点调试 | `POST /workflow/api/node/run_python` 返回 `input param type is NoneType, not dict` | 单节点请求契约与工作流服务实际输入不一致 | Python 单节点接口不能交付 | 明确 `nodeSchema` 和 `input` 的真实结构并补契约测试 |
| P13 | 工作流静态 Token | `/bffservice/v2/app/list` 返回 404 | 当前路由未提供，但前端流程仍依赖它 | 静态 Token 选择流程不可用 | 注册对应路由，或让前端改用现有应用列表接口 |
| P14 | 用户详情 | `GET /user/api/v1/user/info?userId=<ID>` 仍返回当前 JWT 用户 | 接口忽略 `userId` | 不能作为管理员按 ID 查询详情 | 明确为“当前用户”接口，另增管理员详情接口 |
| P15 | 工作流发布 | 实测同一工作流重复发布时报同英文名插件存在 | 发布操作不幂等 | 重复发布请求失败 | 发布前查状态，服务端增加幂等约束 |

P01 与 P02—P08 在当前工作区已完成临时修复（证据见 [接口.md](接口.md) §6），但官方基线仍存在上表所列问题；P09—P15 当前仍为未解决项。

## 3. 当前存在问题、不能按目标用途交付的接口

### 3.2 路由缺失或路径漂移

| 接口/路径 | 当前问题 | 可用替代或修复思路 |
| --- | --- | --- |

## 4. 交付结论

官方基线状态下，成员授权写入、子组织启停、内部知识库按名称查询、Python 单节点调试、工作流应用列表与重复发布，以及智能体 Action/SSE 异常链路已经暴露明确问题，不应作为稳定能力向外部服务承诺。其中智能体详情与 Action/SSE 异常链路已在当前工作区临时修复，但官方基线仍不稳定；其余问题仍未修复。

本文件只汇总平台问题和修复思路。完整请求字段与接口调用证据见 [字段级 API 契约](接口.md)。
