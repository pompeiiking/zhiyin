## 一、设计目标

架构要满足的不是"好看"，而是下面五件可验证的事。每条都对应评估中暴露的具体缺口。

| # | 目标 | 可验证标准 | 当前缺口 |
| --- | --- | --- | --- |
| G1 | **可运行** | 五环节端到端 main path 能在本地跑通，不依赖任何外部中间件 | HTTP 业务端点全 503，Facade 未装配 |
| G2 | **可并行** | 3–5 人按模块并行，接口冻结后互不阻塞 | 8 个服务只有 1 个有实现，其余无落位约定 |
| G3 | **可演进** | 换 MySQL / Kafka / pgvector / SSE 只改装配，业务代码零改动 | SDK 缺 vector / embed / cache / db 四类契约；MySQL 分支 `begin()` 未实现 |
| G4 | **防跑偏** | 依赖方向、契约归属、动态资源边界均有机械守卫 | 已达成（AST 守卫 + `--check`），但契约归属无守卫 |
| G5 | **成本可控** | 不引入与规模不匹配的结构复杂度 | 基本达成（单分发单元），但契约归属命名失真 |

**总体判断**：现行四层 + BFF + 装配层的骨架是对的，**不需要推翻**。需要做的是三处加固 —— 契约归属显式化、IO 契约统一、门禁分级 —— 外加内部目录规范化。下文所有建议都遵守这个边界。

### 2.1 依赖矩阵（修订版，AST 守卫按此更新）

| 包 | 允许依赖 | 与现行差异 |
| --- | --- | --- |
| `zhiyin_kernel` | 仅自身 | **新增** |
| `zhiyin_data_sdk` | `kernel` | 原为"无"；领域模型移出后仅剩契约 |
| `zhiyin_orchestration` | `kernel`、`data_sdk` | 补 `kernel` |
| `zhiyin_infrastructure` | `kernel`、`data_sdk` | 补 `kernel` |
| `zhiyin_business` | `kernel`、`data_sdk`、`orchestration` | 补 `kernel` |
| `zhiyin_api` | `kernel`、`business` | api **直连 kernel** 取枚举与读模型；访问 business 只面对 `ports/` 与 Facade |
| `zhiyin_boot` | 全部 | 不变 |

### 2.2 已收敛：api 直连 kernel，取消"对外发布面"

`zhiyin-api → zhiyin_kernel` 是**有意且已定案**的：kernel 按定义就是跨层共享的取值与数据形状。
原先为了"api 不直连 kernel"而保留的 `zhiyin_business.published`，本质是把同一批内核符号
再导出一次，等于留下两条获取路径（新人不知道取枚举该走哪条）。

**定案（已落地）**：`published.py` 删除。api 取领域取值直接 `from zhiyin_kernel.enums import ...`；
访问业务能力只面对 `business/ports/` 抽象与 Facade。契约类别因此从五类收敛为四类（见 §三）。

## 三、契约归属矩阵（本建议的核心）

评估发现的最大结构性问题是：**契约没有归属，而且有一处命名失真**。`zhiyin_data_sdk/contracts/__init__.py` 自己写着"本包是全系统唯一的数据形状定义处" —— 它描述的是共享内核，却命名在数据访问包下。这个失真已经造成过一次真实缺陷（api 越层 import `data_sdk.contracts.enums`，无人发现）。

据此明确五类契约的唯一归属，**每类只允许一个家**：

| 契约类别 | 内容 | 归属 | 规则 |
| --- | --- | --- | --- |
| **共享内核** | 跨层枚举、身份、黑板数据形状、资产数据形状、动态资源形状 | `zhiyin_kernel` | 零依赖、无实现；所有层可读，任何层不得在此写业务逻辑 |
| **数据访问契约** | Repository / Gateway / Transaction 抽象 | `zhiyin_data_sdk` | 只定义抽象；实现一律在 infrastructure |
| **语义编排契约** | EventBus / Scheduler / Notifier / StateStore / AgentEngine / WorkflowEngine | `zhiyin_orchestration` | 通用、无业务语义；传输能力一律下沉到 SDK Gateway |
| **业务产出契约** | `CollectOutput` / `DiagnoseOutput` / `DecideOutput` / `ActOutput` / `ReviewOutput` | `zhiyin_business.contracts` | 五环节产出的唯一事实来源；编排层只拿它的 JSON Schema |
| ~~对外发布面~~ | ~~api 可见的读模型与枚举入口~~ | **已取消** | 内核归位后它只是同义再导出；api 直连 `zhiyin_kernel`，业务能力只经 `ports/` 与 Facade |

**硬规则（建议用 AST 测试守卫）**：
1. 同一能力不得在两处定义。若出现在两处，必须以"语义契约 + 传输契约"为唯一合法形态，且字段集必须由一处的适配器单向映射。
2. `zhiyin_kernel` 内不得出现任何 `import` 其他 `zhiyin_*` 包。
3. `zhiyin_data_sdk` 内不得出现领域行为（只允许数据形状引用与纯契约）。

## 五、六项关键机制

### 5.1 共享内核显式化（对应 G4、G5）

**做法**：把 `contracts/` 整体提升为顶层包 `zhiyin_kernel`，文件名保持不变，仅改 import 路径。

**成本**：一次性机械改名（约 40 个文件的 import 行）+ AST 守卫矩阵更新。当前 5k 行是改名的黄金窗口，越晚越贵。

**收益**：
- "领域模型归谁"不再有歧义，新人不会再把 `Profile` 当成数据访问契约；
- `published.py` 随之删除（定案见 §2.2）：不再保留"发布面"这条同义获取路径；
- 未来若要拆分发单元，kernel 天然是那个"必须共享的最小内核"。

**备选（保守）**：代码不动，仅在文档与模块 docstring 中显式声明"`data_sdk.contracts` 是共享内核，不属于数据访问契约"。成本为零，但命名失真长期存在，且 `published.py` 需保留现状。**已放弃。**

### 5.2 IO 契约统一为 async（对应 G3）

**做法**：Repository 的全部方法改为 `async def`。内存实现只需加关键字，不改变逻辑。

**理由**：当前 Repository 全同步、编排层全异步（`AgentEngine.invoke` / `EventBus.publish`）。内存实现掩盖了"同步调用阻塞事件循环"的问题，接 MySQL / 网络 IO 时必然暴露，届时需要改动每一个调用点。

**配套约定**：
- 同一个应用内只有一个事件循环，由 boot 的 lifespan 持有；
- 第三方同步 SDK 一律在 `infrastructure` 的 Gateway 实现内部用 `asyncio.to_thread` 包装，**业务层不得出现线程池代码**；
- 需要并发聚合的读路径（工作台）用 `asyncio.gather`，错误按"部分失败降级"处理，不整体失败。

### 5.3 Port 契约测试（对应 G3、G4）

**这是当前最值得补的一块工程实践**。现状：内存 Repository 与未来的 MySQL Repository 语义靠人工对齐（版本单调递增、行为日志只追加、影响面按依赖字段匹配、返回深拷贝快照），必然漂移。

**做法**：

```text
tests/contracts/
├── test_repository_contract.py   # 对所有 Repository 实现跑同一套断言
├── test_gateway_contract.py      # 对 EventBus / Scheduler / Notify / Vector 等
└── conftest.py                   # 以 fixture 参数化注入不同实现
```

**要求**：任何新实现（MySQL / Kafka / Redis / pgvector）合入前，必须通过同一套契约测试。这条把"换实现只改装配"从口号变成门禁。

### 5.4 异步 Worker 与统一启动方式（对应 G1、G3）

Worker 目前没有归属。建议按"谁拥有规则"分家：

| Worker | 规则性质 | 归属 | 启动 |
| --- | --- | --- | --- |
| 影响面传播 | 业务规则（哪些画像字段影响哪些资产） | `business/workers/impact.py` | `python -m zhiyin_boot worker impact` |
| 主动事件 / 停滞检测 | 业务规则（阈值、冷却、打扰上限） | `business/workers/active_event.py` | `python -m zhiyin_boot worker active-event` |
| 向量同步 / 嵌入补偿 | 纯数据管道，无业务语义 | `infrastructure/workers/vector_sync.py` | `python -m zhiyin_boot worker vector-sync` |

三种 Worker **复用同一个 container**，MVP 阶段可同进程（lifespan 内启动），成长期用同一入口独立部署 —— 部署形态变了，代码不变。

**已定案：基类下放到内核，驱动留在装配层。** 业务层与基础设施层都有 Worker，而
`zhiyin_infrastructure` 被依赖矩阵禁止 import `zhiyin_business`，两边不可能共用业务侧基类。
因此契约落在双方唯一的公共依赖上：

```
zhiyin_kernel/worker.py      Worker（只有 name + run_once，零行为）
zhiyin_boot/workers.py       run_forever / run_until_cancelled（驱动，只有装配层需要）
```

这样"换启动方式"（同进程 lifespan / 独立进程 / 未来的 CronJob）只改驱动，两边 Worker
实现与契约都不动；内核也不会因为持有 asyncio 循环而变成杂物间
（由 `tests/test_architecture.py::test_kernel_holds_only_shapes_and_contracts` 守卫）。

### 5.5 读写路径分离（CQRS-lite，对应 G3）

黑板与工作台的读取是"多源聚合 + 只读快照"，写入是"事务 + 事件"，两种负载特征不同。建议在**接口形状**上先分开，实现第二期再分化：

| 路径 | 入口 | 特征 | 二期优化点 |
| --- | --- | --- | --- |
| 写侧 | `Orchestrator.handle_message` / 各 Service 的 `save_*` / `update_*` | 事务、发事件、强一致 | MySQL + Kafka |
| 读侧 | `WorkspaceService` / `ReportService` / `BootstrapService` | 只读、可缓存、允许轻微陈旧 | Redis 缓存 / ES / pgvector |

**约定**：读侧服务不写任何状态、不发事件；不得在写侧方法里做重聚合。第一期同进程同库，但接口分开后，第二期加读模型不需要改调用方。

### 5.6 装配分级门禁（对应 G1、G2、G4）

现行 `--check` 只有二值（`degraded` / `ok`）与单一 `--strict`，导致"第一期永远无法达标"（评估中 9 项验收 5 项不通过即源于此）。建议改为**按里程碑分级**：

```bash
python -m zhiyin_boot --check --phase=1     # 框架可验证：契约冻结 + 装配可观测
python -m zhiyin_boot --check --phase=2     # 主干端到端：services 全 wired（内存实现）
python -m zhiyin_boot --check --phase=3     # 真实存储：MySQL / 向量 / 缓存替代内存
python -m zhiyin_boot --check --phase=4     # 生产化：安全 / 限流 / 真实推送
python -m zhiyin_boot --check --strict      # 全绿（发布门禁）
```

门禁定义写入 `data/registry/assembly_gates.json`（**动态资源，不进代码**）。装配报告同时输出：

- 能力矩阵：能力 → 契约 → 实现 → 状态；
- 缺口归属：读 `data/registry/ownership.json`，替代现在硬编码在 `container.py` 里的负责人字符串。

**收益**：CI 可以按里程碑精确卡门禁；`healthy: false` 不再是一个没有行动含义的红灯。

### 5.7 功能落位决策树（防止未来再次跑偏）

新增任何代码前，按顺序问自己，**第一个命中即为归属**：

1. 是跨层共享的枚举或数据形状？→ `zhiyin_kernel`
2. 是访问外部能力（DB / 缓存 / 模型 / 向量 / 对象 / 消息 / 鉴权）？→ `data_sdk` 定契约 + `infrastructure` 出实现
3. 是调用 LLM / 校验产出契约 / 通用流程编排（与职引无关）？→ `zhiyin_orchestration`
4. 是职引的业务规则或领域行为？→ `zhiyin_business`（规则进 `policies/`，服务进 `services/`，异步执行进 `workers/`）
5. 是 HTTP 适配、DTO 转换、SSE 通道？→ `zhiyin_api`
6. 是把上面接起来 / 决定用哪个实现？→ `zhiyin_boot`（唯一装配处）

**禁止**：在 kernel 写业务逻辑；在 data_sdk 写领域行为；在 business 直接 import `infrastructure`；在 api 写业务判断；把文案 / 规则 / 开关 / 负责人写进 Python（一律走 `data/registry/`）。

## 七、演进路线与门禁

| 里程碑 | 目标 | 退出条件（`--check --phase=N` 全绿） |
| --- | --- | --- |
| **M1 框架可验证**（已基本达成） | 分层冻结、依赖可守卫、装配可观测 | `--phase=1` 全绿；AST 守卫 + 契约测试通过 |
| **M2 主干端到端** | 五环节在内存实现上跑通，前端可联调 | `--phase=2` 全绿；`tests/e2e/` 主路径通过；验收项 1/2/3/4/5/6 达成 |
| **M3 真实存储** | MySQL + Redis + pgvector 替换内存 | `--phase=3` 全绿；契约测试对 MySQL 实现同样通过 |
| **M4 生产化** | 安全 / 限流 / 真实推送 / 可观测 | `--phase=4` 全绿 |

**关键排期建议**：M2 是当前唯一瓶颈。评估显示 5 项验收不通过**同源于一个根因**（Orchestrator + 黑板四件套 + Facade 未装配），补齐这一组即同时解锁。把资源集中到 M2，而不是分散推进 M3/M4 的骨架。

## 八、需要拍板的三项决策

| # | 决策 | 我的建议 | 影响面 |
| --- | --- | --- | --- |
| 1 | 共享内核：新建 `zhiyin_kernel`（方案 A）还是仅文档声明（方案 B） | **方案 A** | 约 40 个文件的 import 改名；不做则命名失真长期存在，且 `published.py` 需持续膨胀 |
| 2 | Repository 是否现在统一为 async | **是** | 现在改成本最低；推迟到接 MySQL 时需改动每个调用点 |
| 3 | M2 的 8 个服务实现顺序 | **黑板四件套 → Facade → Orchestrator → Workspace/Function** | 黑板四件套是 Orchestrator 的前置；Facade 先到位可让前端并行开工 |

**另有 4 项业务规则必须在写 Orchestrator 之前定稿**（技术架构文档 §十五 待确认事项中直接阻塞该项的条目）：

1. 轴 A 阶段判定信号；
2. 意图识别 → 环节判定的兜底规则；
3. 画像置信度算法与缺口表达（采集结束条件）；
4. 主动干预参数：停滞阈值 / 冷却期 / 打扰上限。

这四项不定稿，Orchestrator 只能靠猜实现，返工概率高。

## 一句话总结

架构不用推翻：四层 + BFF + 装配层是对的，`--check` 与 AST 守卫是本期最好的两个决策。真正需要补的是**契约归属**——把 `data_sdk/contracts` 提升为显式的共享内核 `zhiyin_kernel`，让"领域模型归谁"不再有歧义；**IO 契约**——Repository 统一 async，并用 Port 契约测试锁住"换实现只改装配"；**门禁**——把 `--check` 按里程碑分级，让 `healthy` 重新具备行动含义。三处加固做完后，把资源集中到 M2（黑板四件套 → Facade → Orchestrator），这是唯一能同时解锁五项验收的动作。
