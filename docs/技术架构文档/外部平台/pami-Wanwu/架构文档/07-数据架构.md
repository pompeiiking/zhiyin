# Wanwu 数据架构

## 1. 数据组件总览

默认 Docker Compose 部署一个 MySQL、Redis、MinIO、Kafka 和 Elasticsearch 实例，由不同服务使用独立业务库或逻辑空间。配置代码保留其他关系数据库驱动入口，但当前 Compose 的实际基线是 MySQL。

```ascii
                         +-------------------+
                         | 领域 Go 服务       |
                         +--+----+----+----+--+
                            |    |    |    |
          +-----------------+    |    |    +------------------+
          v                      v    v                       v
+----------------+     +-------------+  +-------------+  +----------------+
| MySQL          |     | Redis       |  | MinIO       |  | Elasticsearch  |
| 业务权威数据    |     | 临时/协调数据|  | 二进制对象   |  | 检索索引        |
+----------------+     +-------------+  +-------------+  +----------------+
          ^                                           ^
          |                  +-------------+          |
          +------------------| Kafka       |----------+
                             | 知识处理事件 |   RAG Engine
                             +-------------+
```

## 2. 数据职责

| 组件 | 主要数据 | 权威性 | 使用者 |
|---|---|---|---|
| MySQL | 用户、组织、权限、模型、MCP、知识、RAG、智能体、会话、应用、工作流元数据 | 业务事实主要来源 | 全部领域服务、AgentScope |
| Redis | Token/会话辅助、缓存、锁或运行协调 | 非长期业务事实 | IAM、Model、MCP、RAG、Assistant、App、AgentScope |
| MinIO | 上传文件、知识文档、会话/工具相关对象 | 二进制内容来源 | BFF、Knowledge、Assistant、RAG、Agent |
| Kafka | 文档解析/索引等处理事件 | 传输通道，不是最终事实 | Knowledge、RAG Engine |
| Elasticsearch | 知识检索索引、Assistant 会话检索数据 | 可重建的检索视图 | RAG Engine、Assistant |

## 3. 领域数据所有权

| 数据域 | 所有者 | 备注 |
|---|---|---|
| 用户、组织、角色、权限 | IAM service | BFF 只聚合和校验 |
| 模型与供应商配置 | Model service | 密钥不得通过普通详情接口明文返回 |
| MCP 定义 | MCP service | 外部 MCP 业务状态不属于平台 |
| 知识库、文档和任务 | Knowledge service | 对象在 MinIO、索引在 ES |
| RAG 应用 | RAG service | 引用模型与知识库 |
| 智能体、Action、会话 | Assistant service | 外部会话映射字段为未提交扩展 |
| 应用发布与空间 | App service | 聚合 RAG/Agent/Workflow 应用 |
| 工作流定义与运行 | AgentScope | 实现主要位于外部镜像 |
| 成员授权策略【未提交】 | IAM 库中的 `resource_access_policies` | BFF 初始化并读写 |

## 4. 未提交跨库读取例外

资源成员授权要求 BFF 判断 Model、Agent、Workflow、Knowledge、MCP 中资源的创建者及父资源，因此 `pkg/resource-access`直接建立到多个业务库的只读访问，并把授权策略写入 IAM 库【未提交】。

```ascii
BFF Resource Access【未提交】
   |-- read owner/source --> model_service / assistant_service / knowledge_service / mcp_service / agentscope
   `-- read/write policy -> iam_service.resource_access_policies
```

这打破“只经领域服务访问领域数据”的常规边界。需要最小权限数据库账号、明确 schema 兼容策略，并将领域表变更纳入 BFF 回归测试。

## 5. 生命周期与一致性

| 流程 | 多组件写入 | 一致性策略 |
|---|---|---|
| 文档上传 | MinIO + MySQL + Kafka | 分阶段状态；失败可重试 |
| 文档索引 | ES + MySQL 状态 | ES 可重建；状态记录成功/失败 |
| 知识删除 | MySQL + MinIO + ES | 异步分步清理，需幂等 |
| 智能体会话 | MySQL + ES | MySQL 保存关系，ES 服务检索 |
| 资源授权【未提交】 | IAM 策略表 + 多库归属读取 | 单策略事务 + 每次重新验证成员身份 |
| 发布应用 | 领域资源 + App 元数据 | 使用资源 ID 关联，避免复制配置 |

## 6. 持久化与卷

Compose 为 MySQL、Redis、MinIO、Kafka、ES 数据和 ES 证书声明命名卷；各服务日志和部分静态/临时文件映射到项目目录。命名卷删除会导致数据丢失，`docker compose down -v`不应作为普通停机命令。

## 7. 备份与恢复顺序

仓库未提供一套经验证的全平台一致性备份编排【静态推断】。建议恢复顺序为：配置与密钥 → MySQL → MinIO → Kafka（如需保留未消费事件）→ Elasticsearch 重建/恢复 → Redis 按需重建 → 服务与引擎。备份点必须记录版本和 schema，避免只恢复数据库而丢失对象。

## 8. 数据安全

- 数据库、Redis、MinIO、Kafka 和 ES 凭据由环境变量注入，文档不保存实际值。
- 默认 Compose 暴露多个中间件端口到宿主机，生产环境应由防火墙或端口绑定限制外部访问。
- ES 启用 TLS 和认证；Kafka 配置 SASL_PLAINTEXT，依赖受控网络防止链路窃听。
- MinIO 下载代理与签名/对象权限必须协同，不能将内部存储凭据下发浏览器。
- 日志、备份和导出文件与主库同样可能含敏感内容，应纳入访问控制和保留策略。

## 9. 容量关注点

主要增长项是 MinIO 文档/附件、ES 索引、MySQL 会话与审计数据、Kafka 日志和各服务日志。容量预警应分别覆盖卷空间、ES heap/segment、MySQL 连接/慢查询、Kafka lag 与对象增长率。
