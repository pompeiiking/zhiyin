# Wanwu 部署与运行架构

## 1. 默认部署拓扑

默认交付使用 Docker Compose 和单一外部网络 `wanwu-net`。这是单主机拓扑，不是高可用集群。

```ascii
Host / Docker Engine
|
|-- :8081 nginx + Vue【混合】
|       `--> :6668 BFF【混合】
|              |--> :8888 IAM
|              |--> :8989 Model【混合】
|              |--> :9898 MCP【混合】
|              |--> :8889 Knowledge【混合】
|              |--> :9640 RAG service
|              |--> :8890 Assistant【混合】
|              |--> :9988 App
|              |--> :6672 AgentScope【混合】
|              `--> Agent auxiliary endpoints【混合】
|
|-- AI engines
|     |-- agentscope-wanwu :6672
|     |-- rag-wanwu :8613/:8681/:10891/:15000
|     `-- agent-wanwu :7258/:1990-1992/:15001-15003
|
`-- Middleware
      |-- MySQL :3306      |-- Redis :6379
      |-- MinIO :9000/9001 |-- Kafka :9092
      `-- Elasticsearch :9200
```

端口是 Compose 基线映射；生产环境是否对外可达还取决于主机监听、防火墙和云安全组。

## 2. 启动依赖

```ascii
MySQL ---> mysql-worker ---> initialize schemas
  |  \--> IAM / Model / MCP / Knowledge / RAG / Assistant / App / AgentScope
Redis ----------------------------------------------------------/
MinIO ---> BFF / Knowledge / RAG Engine / Agent
Kafka ---> Knowledge / RAG Engine
ES -----> RAG Engine / Assistant

Healthy dependencies -> business services -> AI engines -> nginx
```

Compose 的 `depends_on.condition: service_healthy`只控制启动门槛，不提供运行期自动故障转移。

## 3. 镜像与源码边界

| 镜像 | 内容 |
|---|---|
| Backend | 八个 Go 服务二进制及配置 |
| Frontend | Nginx、Vue 构建产物和代理配置 |
| AgentScope | 工作流 Python 服务【外部依赖】 |
| RAG | 文档处理和检索引擎【外部依赖】 |
| Agent | Python Agent 环境；仓库目录运行时挂载 |
| Middleware | MySQL、Redis、MinIO、Kafka、Elasticsearch |

`Dockerfile.backend`和`Dockerfile.frontend`提供基础构建；AgentScope、RAG 的完整源码不在本仓库，升级必须按接口和配置兼容性验证。

## 4. 配置与卷

- `.env`和架构变量选择镜像、网络、项目目录、地址与凭据；实际值不进入本文档。
- `configs/microservice/<service>/configs/config.yaml`定义服务端口、内部地址和领域配置。
- `configs/middleware/`包含 MySQL 初始化、Kafka 日志、ES 插件及 Nginx 代理配置。
- 命名卷保存 MySQL、Redis、MinIO、Kafka、ES 数据和证书。
- `${WANWU_PROJECT_DIR}`下保存服务日志、BFF 临时文件、Knowledge 静态文件及引擎日志。

## 5. Compose 覆盖层

| 覆盖文件 | 用途 | 状态 |
|---|---|---|
| `docker-compose-develop.yaml` | 开发模式覆盖 | 已提交 |
| `docker-compose.local.yaml`【未提交】 | 本机端口及 Kafka/BFF 回调调整 | 工作区覆盖 |
| `docker-compose.wsl.yaml`【未提交】 | Docker Desktop/WSL 主机路径绑定 | 工作区覆盖 |
| `docker-compose.sharing.yaml`【未提交】 | 组织共享后端与 AgentScope 镜像 | 工作区覆盖 |
| `docker-compose.member-access.yaml`【未提交】 | 成员授权 BFF、AgentScope、前端镜像和构建目录 | 工作区覆盖 |

覆盖顺序会改变最终镜像、端口和卷；运行记录必须保存完整的 Compose 文件列表，不能只记录基础文件。

## 6. 未提交部署形态

```ascii
base compose
   + local + wsl
   + member-access【未提交】
        |-- backend:member-access
        |-- agentscope:member-access
        `-- frontend:member-access + bind project/member-access-web

legacy alternative: base + sharing【未提交】
```

成员授权覆盖替代了早期组织共享语义；两者不应同时当作正式行为叠加。回退覆盖文件不会自动删除 IAM 中已创建的授权策略表。

## 7. 健康检查与启动验证

中间件使用各自探测命令，Go 服务以本地端口探测为主，AgentScope 使用 Python socket，Nginx 使用端口探测。端口可连只证明进程监听，不证明依赖调用、数据库迁移或模型服务有效。

建议启动验收顺序：容器 healthy → BFF 基础接口 → 登录 → 模型列表 → 知识上传/状态 → RAG/Agent SSE → 工作流调试 → OpenAPI → 未提交成员授权专项路径。

## 8. 发布与回滚

- 固定镜像版本或摘要，保存环境变量模板、Compose 覆盖列表和数据库 schema 版本。
- 先备份 MySQL 和 MinIO，再执行涉及 AutoMigrate 或领域表变化的升级。
- Go Proto、BFF、前端和 AgentScope 补丁存在耦合的功能必须作为同一发布单元验证。
- 回滚前确认新版本写入的数据能被旧版本忽略或兼容，尤其是 `external_config`、`external_session`和授权策略表【未提交】。

## 9. 单机风险

主机、Docker daemon、磁盘、网络和 Compose 网络均为共同故障域。需要更高可用时，应优先外置有状态组件、建立备份恢复验证，再评估多实例服务发现和编排平台；当前配置不能直接等价迁移为高可用架构。
