## 2. 各层职责

| 层 | 核心职责 | 主要实现 |
|---|---|---|
| 用户与接入 | 建模、配置、调试、发布和消费 AI 应用 | `web/src/`、OpenAPI、外部页面【未提交】 |
| 统一接入 | 静态资源、反向代理、认证、聚合和流式输出 | `configs/middleware/nginx/`、`internal/bff-service/` |
| 业务微服务 | 按领域管理身份、模型、工具、知识、应用和会话 | `cmd/*-service/`、`internal/*-service/` |
| AI 引擎 | 实际执行工作流、知识处理和 Agent 推理 | AgentScope 镜像、RAG 镜像、`agent/agent_open_source/` |
| 数据中间件 | 持久化、缓存/协调、对象、事件和索引 | Compose 中 MySQL、Redis、MinIO、Kafka、ES |
| 外部生态 | 提供模型、搜索、工具和企业系统能力 | OpenAI 兼容 API、MCP、HTTP/Callback |

业务微服务的精确进程映射为：IAM → `iam-service`，Model → `model-service`，MCP → `mcp-service`，Knowledge → `knowledge-service`，RAG → `rag-service`，Assistant → `assistant-service`，App → `app-service`；统一入口为 `bff-service`。该命名同时用于 `cmd/`入口、内部服务地址和 Compose 容器。

## 3. 核心架构原则

1. Nginx 是默认 Web 入口，BFF 是业务 API 的统一入口；内部 Go 服务主要通过 gRPC 暴露能力。
2. 服务按业务域切分，共享通信与基础设施包，但各自保有领域模型和配置。
3. AI 执行引擎与管理面分离：Go 服务管理元数据，Python/独立镜像承担推理、工作流和知识处理。
4. MySQL 保存业务事实；Redis、Kafka 和 Elasticsearch 承担衍生或运行期职责；MinIO 保存对象内容。
5. 长响应通过 SSE 或流式 HTTP 传递，普通管理操作使用同步 HTTP/gRPC。
6. 组织、用户和资源归属贯穿请求；成员级资源授权是当前工作区新增横切能力【未提交】。
7. 外部智能体可复用平台会话入口或以 iframe 呈现，但外部系统自身安全边界不由 Wanwu 接管【未提交】。

## 4. 层级依赖关系

```ascii
Web / OpenAPI
      |
      v
Nginx -----> AgentScope workflow API
      |
      v
BFF ----gRPC----> IAM / Model / MCP / Knowledge / RAG / Assistant / App
 |  \----HTTP----> AgentScope / Agent 辅助服务
 |                 |
 |                 +----> 模型 / MCP / 外部智能体【未提交】
 +----SSE/WS------> Browser

Go 服务 / AI 引擎 ----> MySQL / Redis / MinIO / Kafka / Elasticsearch
```

## 5. 关键风险

- Compose 为单节点形态，中间件和服务均存在主机级共同故障域。
- AgentScope 与 RAG 的主要实现由镜像交付，仓库只能通过配置和接口观察其内部边界。
- `【未提交】`能力尚未进入版本历史；其中成员授权写接口存在已知请求体读取问题，不能写成已稳定能力。
- Nginx 暴露 MinIO 下载路径，必须依赖服务端生成的受控对象路径和访问策略。
