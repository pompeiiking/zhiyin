# Wanwu 身份、权限与安全架构

## 1. 安全域

Wanwu 的访问控制由入口路由、JWT 用户身份、组织上下文、菜单/接口权限、资源归属和发布/API Key 规则共同组成。前端权限只控制展示，不替代后端鉴权。

```ascii
Request
  |
  v
Nginx route boundary
  |
  v
BFF middleware
  +-- JWT validity / token refresh
  +-- user status and organization context
  +-- route permission
  +-- request record / audit context
  `-- resource access【未提交】
          +-- creator? ----------> manage + use
          +-- authorized member? -> use only
          `-- otherwise ----------> deny
  |
  v
Domain service / AgentScope / external dependency
```

## 2. 登录与请求身份

1. 用户通过 BFF 登录接口访问 IAM。
2. IAM 校验账号并签发平台 Token；Redis参与令牌/会话辅助状态。
3. Web Axios 在请求中发送 Bearer Token，同时携带用户和组织头。
4. BFF 中间件校验身份并注入可信上下文；客户端头不得单独作为身份事实。
5. 响应可通过 `new-token`头刷新前端 Token；401 触发本地凭据清理和重新登录。

## 3. 权限层次

| 层次 | 解决的问题 | 实现位置 |
|---|---|---|
| 路由边界 | 哪类 URL 可从外部访问 | Nginx、BFF router |
| 身份 | 请求是谁 | IAM、JWT 中间件 |
| 组织 | 请求属于哪个租户上下文 | IAM、`x-org-id`校验 |
| 菜单/接口权限 | 能否进入某管理模块或调用管理接口 | 角色权限、BFF middleware |
| 资源归属 | 能否管理自己的模型/知识/Agent 等 | 各领域表和服务规则 |
| 成员使用权【未提交】 | 能否使用他人明确授权的资源 | `pkg/resource-access`与资源中间件 |
| 发布/API Key | 能否通过开放入口运行应用 | App/Assistant/AgentScope/OpenAPI 规则 |

既有用户、组织和资源归属共同形成资源范围；当前工作区在这一基线之上加入指定成员使用权，因此整体资源范围机制属于`【混合】`状态。

## 4. 资源成员授权【未提交】

适用资源：`model`、`agent`、`workflow`、`knowledge`、`mcp`。创建者可查看/更新成员列表；被授权成员只有使用权，不能编辑、删除、发布或再次授权。

```ascii
org_id + resource_type + resource_id
                |
                v
       resolve resource owner
                |
      +---------+----------+
      | creator            | member
      v                    v
 manage + use       read/use/run saved config
      |                    |
      +---------+----------+
                |
        IAM membership recheck
                |
                v
 resource_access_policies (revision prevents overwrite)
```

子资源通过父资源追溯权限，例如知识文档继承知识库，Action/会话继承智能体。工作流执行时服务端强制使用已保存图，避免成员提交替换图。

### 已知运行状态

2026-09-12 的专项验证表明，`permissions`、`members`、`access`、`visible`四个 GET 路径在本轮测试中有成功记录，但各有一条 HTTP 403 失败样本，属于部分通过；PUT 更新授权因 Record 中间件读取请求体后未恢复，handler 再绑定时得到 EOF【未提交】【运行验证】。因此当前部署不能宣称授权闭环稳定。

## 5. 外部智能体安全【未提交】

- API 模式仅允许 HTTP/HTTPS，拒绝 URL 用户名/密码、查询和片段等危险配置；正常校验 TLS，禁用重定向。
- API Key 存储于 Assistant 配置，详情只返回掩码；更新日志应避开请求体。
- 外部响应限制大小并按配置路径提取文本；远端内容视为不可信输入。
- iframe 模式不注入平台身份，使用 sandbox、referrer policy 和 Permissions Policy 限制能力；SSO 与外部页面权限不在平台边界内。

## 6. 网络与接口安全

- Nginx 是用户入口；内部 gRPC、数据库及引擎端口应限制在 Docker 网络或受控主机网络。
- 当前 Nginx 配置阻止三个对外代理前缀下的 callback 路径直达内部回调【混合】。
- ES 使用 TLS/认证；Kafka 为 SASL_PLAINTEXT，必须依靠网络隔离。
- Compose 映射 MySQL、Redis、MinIO、Kafka、ES 和引擎端口到宿主机，生产环境需额外限制监听地址和防火墙。

## 7. 密钥与审计

密钥从环境变量或受限配置注入，不能进入源码、前端、日志或文档。请求记录中间件必须对登录、模型密钥、外部 Agent 配置和上传内容进行脱敏。高风险操作至少记录用户、组织、资源、动作、结果和请求标识。

## 8. 威胁与控制

| 威胁 | 当前/要求的控制 |
|---|---|
| 伪造用户/组织头 | JWT 与组织成员关系复核 |
| 越权访问资源 | 创建者检查、成员策略、子资源追溯【未提交】 |
| API Key 绕过身份 | Key 所属身份与目标资源再次校验 |
| SSRF 调用内网 | 外部 URL 校验；仍需生产出站网络策略【未提交】 |
| Prompt/工具注入 | 工具输出不可信、限制工具权限和响应大小 |
| iframe 窃取平台身份 | 不注入 Token、隔离源、sandbox【未提交】 |
| 日志泄密 | 请求体脱敏、受限日志目录和保留周期 |
| 跨库授权故障 | 最小权限账号、失败拒绝、schema 兼容测试【未提交】 |
