## 一、文档定位

本文档由《职引技术架构》和《职引数据层架构》合并而成，用于统一描述职引系统的整体分层、职责边界、数据访问与存储规划、向量检索能力、部署形态及落地顺序。

本版按 PRD v2.0 优化：业务主线从「一次性报告流水线」改为「三轴模型 + 五环微循环 + 动态编排 + 黑板影响面传播」。技术实现重点围绕以下能力：

- **可拆可续**：用户可从任意环节进入，前序资产自动继承，不重复问、不整篇重生成。
- **动态组队**：智能体作为能力池，由业务编排器按轴 A × 轴 B × 意图选择主理、协理与信息侦查员。
- **黑板一致性**：画像活状态、行为日志、会话记忆、资产版本影响面共享读写，更新后增量重算。
- **主动干预**：陪伴教练仅由真实行为信号触发，带最小可执行动作。
- **显式告知**：换主理、换理论依据、结论变化都可解释。

### 1.2 与《职引-PRD-v2.0》的对齐边界

本文档与 [职引-PRD-v2.0.md](../PRD/职引-PRD-v2.0.md) 共同使用以下唯一口径，避免产品语义与技术实现错耦合：

| 主题 | PRD 负责（产品语义） | 技术架构负责（技术实现） |
| --- | --- | --- |
| 三轴模型 | 定义轴 A、轴 B、轴 C 的含义与业务规则 | 定义阶段推断、环节状态机、编排器调用链 |
| 五环节 | 定义 ①采集→②诊断→③决策→④行动→⑤复盘 的命名、四元组与防跑偏规则 | 定义 Loop Service、任务会话、环节切换与持久化 |
| 智能体 | 定义五个智能体的理论包、可做/不可做、被调用场合 | 定义 agent_registry、output_contract、Agent.invoke |
| 黑板 | 定义画像活状态、行为日志、会话记忆、资产影响面的业务含义 | 定义 MySQL/Redis/Kafka 落点、一致性与读写顺序 |
| 影响面传播 | 定义哪些行为触发增量重算、版本 diff 的用户可见语义 | 定义 Worker、资产版本表、只重算受影响片段 |
| 页面 | 定义首页、三栏对话页、智能工作台的信息架构与交互 | 定义 BFF、SSE/WS、Notify 与前端接口 |
| 指标埋点 | 定义北极星、行为事件与产品指标 | 定义行为日志事件 schema、Kafka 路由与存储 |

防错耦合原则：

1. PRD 不规定服务名、存储选型、数据库表；技术架构不规定用户可见文案、环节理论链、行为引导口径。
2. 双方使用同一组术语：五环节、三轴、智能体名称、黑板四件套必须完全一致。
3. 任何一侧变更术语或边界，必须同步更新另一侧的「对齐边界」表。

合并后的核心结论：

- 职引采用「四层业务架构 + 前端/BFF 接入层」：基础设施层、数据接入层（Data Access SDK）、编排层、业务逻辑层；前端/BFF 是接入层，不承载业务规则。
- Data Access SDK 在工程实现中是独立包，在逻辑上承担横跨基础设施层与业务层之间的数据访问与存储规划。
- pami（联通元景葩米 Lite / Wanwu）是自家平台模块，继续作为基础设施底座；该层的组件扩展与部署在 pami 模块内进行，职引侧只经冻结接口调用。
- 新增 PostgreSQL + pgvector 作为职引专属向量库，承载语义检索读模型。
- MySQL 仍是业务权威库和唯一事实源，pgvector 仅保存向量、原文片段和检索元数据。
- 业务层只能通过编排层原语与 Data Access SDK 访问底层能力，禁止跨层直连。

## 二、总体架构

```text
┌─────────────────────────────────────────────────────────────┐
│  前端 / BFF（zhiyin-api，接入层）                            │
│  首页、核心对话页、智能工作台、功能块接口                     │
├─────────────────────────────────────────────────────────────┤
│  第三层：业务逻辑层（职引业务域）                            │
│  Profile / Behavior / Asset / Loop / Orchestrator           │
│  Workspace / Function                                       │
│  只写业务规则、领域语义、业务编排策略                         │
│  通过 Repository / Data Access SDK 访问数据                  │
├─────────────────────────────────────────────────────────────┤
│  第二层：编排层（通用能力，可被多个业务复用）                  │
│  Agent / Workflow / EventBus / Schedule / State / Notify     │
│  只写通用编排规则，不感知职引业务语义                         │
├─────────────────────────────────────────────────────────────┤
│  数据接入层：Data Access SDK                                 │
│  连接 / 鉴权 / 多租户 / 审计 / 读写分离 / 幂等 / 锁 / 向量检索 │
├─────────────────────────────────────────────────────────────┤
│  第一层：基础设施层（pami 平台 + 职引新增向量库）               │
│  接入 / 安全 / 模型 / 工具 / 知识 / RAG / 会话 / 存储 / 消息   │
│  MySQL / Redis / Kafka / ES / MinIO / PostgreSQL + pgvector │
└─────────────────────────────────────────────────────────────┘
```

### 2.1 分层原则

| 层 | 定位 | 可以依赖 | 禁止依赖 |
|---|---|---|---|
| 基础设施层 | 原子能力提供方 | 无 | 编排层、业务层 |
| 数据接入层 | 数据访问、隔离、审计、检索封装 | 基础设施层 | 业务语义 |
| 编排层 | 通用编排原语 | 基础设施层、数据接入层 | 业务层 |
| 业务逻辑层 | 职引业务语义与业务规则 | 编排层、数据接入层 | 直接访问基础设施 |
| 前端 / BFF 接入层 | 请求接入、参数校验、DTO 与视图装配 | 业务逻辑层 | 基础设施、数据接入、编排层 |

调用方向只能自上而下：

```text
前端 / BFF → 业务逻辑层 → 编排层 / Data Access SDK → 基础设施层
```

禁止反向调用，禁止业务层直接连接 Kafka、Redis、Assistant、MySQL、pgvector 等基础设施。

## 三、第一层：基础设施层

基础设施层由 pami 平台能力与职引新增 PostgreSQL + pgvector 组成。该层只提供原子能力，不感知任何职引业务。

### 3.1 基础设施底座（复用）：pami 平台（联通元景葩米 Lite / Wanwu）

基础设施层实际复用 pami 平台，不对其核心微服务做侵入式改造。职引通过 pami 暴露的 OpenAPI 与管理端 v1 API 对接。

| 能力域 | 实际服务 / 模块 | 关键接口 | 复用方式 |
|---|---|---|---|
| 网关 / OpenAPI | `bff-service` | `POST /service/api/openapi/v1/agent/conversation`、`POST /service/api/openapi/v1/agent/chat`、`POST /service/api/openapi/v1/rag/chat` | OpenAPI APIKey |
| 身份权限 | `iam-service` | `/user/api/v1/user`、`/user/api/v1/role`、`/user/api/v1/org`、`/user/api/v1/resource/*` | JWT 服务账号 |
| 模型纳管 | `model` | `ImportModel`、`ListModels`、`ChangeModelStatus` | JWT / 管理 API |
| 知识库 | `knowledge-service` | `POST /user/api/v1/knowledge/doc/import`、`POST /user/api/v1/knowledge/doc/url/analysis` | JWT 服务账号 |
| 检索增强 | `rag-service` | `POST /service/api/openapi/v1/rag/chat` | OpenAPI APIKey |
| 智能体 | `assistant` | `/user/api/v1/assistant`、`/user/api/v1/assistant/stream`、`/user/api/v1/assistant/workflow`、`/user/api/v1/assistant/action` | JWT 管理 / OpenAPI 运行 |
| 可视化工作流 | `agentscope`（Python，端口 6672） | 工作流触发 / 配置 API | pami 管理端配置 |
| Agent 执行 | `agent` / `agent_open_source`（Qwen-Agent + LangChain） | function call / ReAct | 按需加自定义工具 |
| 应用发布 | `app-service` | OpenAPI / iframe | 配置级复用 |
| 中间件 | MySQL / Redis / Kafka / Elasticsearch / MinIO | 标准协议 | 复用现有实例 |

**鉴权体系（必须与实现一致）**：

- OpenAPI APIKey：与已发布应用 1:1 绑定。五个业务智能体应用各拿一个专属 Key。
- JWT 服务账号：用于知识库导入、权限同步、模型管理等内部 v1 API。

职引业务层不能直接调用这些接口，必须通过 Data Access SDK / 基础设施适配器封装。

稳定契约：

- OpenAPI 统一前缀：`/service/api/openapi/v1`
- 管理端 v1 API：`/user/api/v1`
- 内部服务通信：gRPC
- AI 执行：Assistant / AgentScope / Agent

pami 基础设施层作为底座与职引解耦：职引侧只经受冻结接口调用、不改其内部实现；pami 模块自身的变更在模块内评审并同步文档。

> 字段级真实契约见 [pami/pami-Wanwu/接口.md](pami/pami-Wanwu/接口.md)；已确认的平台缺陷、未连通接口和替代方案见 [pami/pami-Wanwu/平台报错和未连通接口.md](pami/pami-Wanwu/平台报错和未连通接口.md)。涉及 pami 能力时必须以此为准，不把未通过或未执行接口当作稳定能力承诺。

### 3.2 存储资源全景

| 存储 | 角色 | 承载数据 | 来源 |
|---|---|---|---|
| MySQL | 业务权威库 | `zhiyin_service` 业务数据、用户域、领域知识、外部事实 | 复用 pami |
| Redis | 热状态与缓存 | 会话热数据、限流、延迟队列、连接注册 | 复用 pami |
| Kafka | 事件流 | 行为日志、影响面传播、主动事件、向量同步事件 | 复用 pami |
| Elasticsearch | 全文检索 | 对话、职业库、JD、政策、报告 | 复用 pami |
| MinIO | 对象存储 | 简历、作品、报告全文、导出文件 | 复用 pami |
| PostgreSQL + pgvector | 向量库 | 理论卡、职业库、JD、报告片段、会话摘要、简历向量 | 职引新增 |

职责边界：

- MySQL 存权威事实，是唯一事实源。
- PostgreSQL + pgvector 存向量、分块原文和检索元数据，是 MySQL 的读模型副本。
- 向量检索命中后，必须回 MySQL 补全权威详情。
- ES 负责关键词和全文检索，pgvector 负责语义检索，两者可做混合检索。

## 四、第二层：编排层

编排层把基础设施原子能力组合成可被业务调用的通用编排原语。该层不包含任何职引业务语义。

### 4.1 编排能力组成

```text
┌─────────────────────────────────────────────────────────────┐
│  编排层                                                      │
│                                                              │
│  ┌──────────────────┐  ┌──────────────────┐                 │
│  │ Agent 编排引擎    │  │ Workflow 编排引擎 │                 │
│  │ 主理/协理选择     │  │ 多步骤流程        │                 │
│  │ 能力池注册        │  │ 条件分支          │                 │
│  │ 交接状态机        │  │ 并行/串行         │                 │
│  │ 产出契约校验      │  │ 失败重试/降级     │                 │
│  └──────────────────┘  └──────────────────┘                 │
│                                                              │
│  ┌──────────────────┐  ┌──────────────────┐                 │
│  │ EventBus 编排引擎  │  │ Schedule 编排引擎 │                 │
│  │ 事件发布/订阅     │  │ 定时触发          │                 │
```

### 4.2 编排层对外契约

| 原语 | 输入 | 输出 | 底层依赖 |
|---|---|---|---|
| `Agent.invoke` | `agent_id`、上下文、产出契约 | 结构化产出 | Assistant、AgentScope、Model |
| `Workflow.run` | `workflow_id`、入参 | 步骤产出 | AgentScope、Python Agent |
| `EventBus.publish` | `event_type`、payload | 事件 ID | Kafka |
| `EventBus.subscribe` | `event_type`、handler | 订阅 ID | Kafka |
| `Schedule.register` | 触发条件、动作、冷却策略 | 任务 ID | Redis ZSET、Kafka |
| `State.read/write` | 命名空间、key、版本 | 状态值 | MySQL、Redis |
| `Notify.push` | session、channel、payload | 推送结果 | SSE、WS、通知通道 |

### 4.3 编排层禁止事项

- 不定义“画像”“差距”“五环节”等业务概念。
- 不知道“建档分析师”“职业顾问”“路径规划师”等职引角色。
- 不写职引特有提示词、理论卡、产出 schema。
- 不感知轴 A、轴 B、轴 C。

编排层必须保持通用，可被 pami 平台上其他垂直应用复用。

### 5.2 业务层调用示例

以“用户认领差距”为例：

```text
Loop Service 收到 gap_claim 请求
  │
  ├─ 1. 调 Behavior Service 写行为日志
  │      → EventBus.publish("gap_claim", {...})
  │
  ├─ 2. 调 Profile Service 更新画像
  │      → State.write("profile", field, value, confidence)
  │
  ├─ 3. 触发影响面传播
  │      → EventBus.publish("profile_field_updated", {...})
  │      → Asset Service 订阅后增量重算
  │
  ├─ 4. 判断是否进入决策环节
  │      → 编排决策表：轴 A × 轴 B × 意图 → 职业顾问
  │      → Agent.invoke("zhiyin_advisor", 上下文, 方案集契约)
  │
  └─ 5. 返回前端
         → Notify.push(session_id, 最短结论 + 行为引导)
```

### 5.3 业务层禁止事项

- 不实现消息队列、定时器、状态存储。
- 不直接实现 LLM 调用、RAG 检索、工具调用。
- 不实现 SSE / WS 通道。
- 不实现 JWT / 鉴权。
- 不直接拼 SQL 操作底层存储。

### 5.4 业务编排器（Orchestrator）

业务编排器是轴 C 的业务实现，位于业务逻辑层。它调用通用编排层原语，但所有职引业务语义留在本层，不与通用编排层混淆。

职责对应 PRD `FR-ORCH`：

| 职责 | 技术实现 |
| --- | --- |
| 意图识别与环节判定 | 输入 + 会话记忆 + 规则/模型分类 |
| 主理/协理/信息侦查员选择 | `AgentRegistry` + 决策表 |
| 交接契约与触发 | `OutputContract` + 交接状态机 |
| 黑板一致性维护 | `Profile/Asset Service` + 影响面事件 |
| 主动事件调度 | `Schedule` + 行为日志事件 |
| 显式告知文案生成 | 交接/理论/结论变化时生成解释文本 |

决策输入与产出：

```text
当前输入 + 会话记忆
        │
        ├─ 意图识别 → 候选环节
        ├─ 轴 A 推断（画像 + 行为日志 + 时间窗口）→ 服务深度
        ├─ 轴 B 判定 → 当前环节
        └─ 轴 C 点兵 → 主理 / 协理 / 信息侦查员
                          │
                          v
                  输出：agent_ids + 产出契约 + 交接说明
```

### 5.5 黑板实现

黑板不是独立存储，而是画像活状态、行为日志、会话记忆、资产版本影响面的统一访问模型。权威事实在 MySQL，热状态在 Redis，事件流在 Kafka。

| 黑板项 | 权威存储 | 热状态 | 关键事件 |
| --- | --- | --- | --- |
| 个人画像活状态 | MySQL | Redis | `profile_field_updated` |
| 行为日志 | MySQL | Redis 最近事件 | `zhiyin.behavior.<type>` |
| 会话记忆 | MySQL | Redis 摘要 | `memory_updated` |
| 资产版本影响面 | MySQL | Redis 当前版本 | `asset_version_changed` |

一致性原则：

1. 先写 MySQL 权威数据，再发 Kafka 事件；
2. 资产版本变更必须记录依赖画像字段；
3. 影响面传播只重算受影响片段，禁止整篇重新生成；
4. 所有跨会话续接都从黑板读取，不依赖前端临时状态。

### 5.6 单轮回复管线

对应 PRD `FR-ORCH-006/007`。每次用户输入都走同一管线，不允许空转寒暄、不允许无下一步总结：

```text
用户输入
  → Loop Service
      → Orchestrator 读黑板（画像 + 行为日志 + 会话记忆）
      → 环节判定
      → 选主理 / 协理 / 信息侦查员
      → 理论链产出（Agent.invoke + OutputContract 校验）
      → 行为引导收尾（追问 / 选项 / 小任务 / 提醒）
      → 写行为日志与资产
      → Notify.push 返回前端
```

### 5.7 主动事件与影响面传播

```text
行为日志写入
  → Kafka zhiyin.behavior.*
      ├─ 影响面传播 Worker：
      │     profile_field_updated / gap_claim / decision_select
      │     → Asset Service 增量重算
      │     → 资产版本 +1
      │     → 报告片段重新向量化
      │
      └─ 主动事件 Worker：
            task_stall / node_due / semester_window / profile_stale
            → Schedule/Review 触发
            → 陪伴教练生成最小可执行动作
            → Notify 推送（受打扰度上限与冷却期约束）
```

主动事件只由真实信号触发，不因“系统想说话”而打扰用户。

## 六、数据层架构

数据层在逻辑上是横跨基础设施与业务之间的数据访问与存储规划，在工程实现上以 `zhiyin-data-sdk` 独立包承载。它不是业务物理层，但通过 Data Access SDK 将业务层、编排层和基础设施层连接起来，并统一处理连接、权限、租户隔离、审计、读写分离、事务、幂等、锁、检索和降级。

### 6.1 Data Access SDK 定位

Data Access SDK 对上提供稳定数据接口，对下适配 MySQL、Redis、Kafka、ES、MinIO、PostgreSQL + pgvector。

| 能力 | 说明 |
|---|---|
| `db.query / db.tx` | MySQL 查询与事务 |
| `cache.get/set` | Redis 缓存 |
| `EventBusGateway.publish/consume` | Kafka 事件发布与消费适配 |
| `search.query` | ES 全文检索 |
| `object.put/get` | MinIO 对象存储 |
| `vector.search/upsert/delete` | pgvector 向量检索与写入 |
| `embed.text/batch` | 嵌入模型调用与版本路由 |

SDK 必须负责：

- 统一连接池、超时、重试与熔断。
- 自动注入 `org_id` 过滤。
- 自动记录检索日志和审计日志。
- 统一嵌入模型版本路由。
- 对向量检索、全文检索、混合检索提供降级策略。

SDK 禁止事项：

- 禁止业务层直接拼 SQL 操作向量表。
- 禁止跨命名空间向量查询。
- 禁止无 `org_id` 过滤的租户私有数据检索。

### 6.2 PostgreSQL + pgvector 服务定位

| 项 | 规划 |
|---|---|
| 定位 | 职引专属向量库，不承载业务权威数据 |
| 部署 | 独立实例，与 pami MySQL 解耦 |
| 版本 | PostgreSQL 16+，pgvector 0.7+ |
| 数据库 | `zhiyin_vector` |
| 应用账号 | `zhiyin_vector_app` |
| 高可用 | MVP 可单节点，V1.1 建议主从 + 流复制 |
| 备份 | 每日全量 + WAL 归档 |

实例规格建议：

| 阶段 | 规格 | 说明 |
|---|---|---|
| MVP | 4C8G，SSD 200G | 向量少于 500 万，单节点 |

### 6.4 pgvector 表结构模板

```sql
CREATE TABLE theory (
    id            BIGSERIAL PRIMARY KEY,
    source_id     BIGINT NOT NULL,
    source_type   VARCHAR(64) NOT NULL,
    org_id        BIGINT,
    chunk_index   INT NOT NULL DEFAULT 0,
    content       TEXT NOT NULL,
    metadata      JSONB NOT NULL DEFAULT '{}',
    embedding     vector(1024) NOT NULL,
    model_version VARCHAR(64) NOT NULL,
    created_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX idx_theory_embedding ON theory
USING hnsw (embedding vector_cosine_ops)
WITH (m = 16, ef_construction = 64);

CREATE INDEX idx_theory_source ON theory (source_type, source_id);
CREATE INDEX idx_theory_org ON theory (org_id);
CREATE INDEX idx_theory_metadata ON theory USING gin (metadata);
```

索引策略：

| 索引类型 | 适用场景 | 参数建议 |
|---|---|---|
| HNSW | 在线检索，高召回 | `m=16, ef_construction=64` |
| IVFFlat | 批量构建，内存敏感 | `lists=1000`，按数据量调整 |
| 无索引 | 数据量少于 10 万 | 精确检索，避免索引开销 |

MVP 建议统一使用 HNSW。

## 七、数据同步机制

PostgreSQL 的向量数据来自 MySQL 权威表。同步链路如下：

```text
MySQL 权威表变更
  │
  ├─ 业务层写入 MySQL
  │
  ├─ 发 Kafka 事件：zhiyin.vector.sync
  │     { namespace, source_id, action: upsert/delete }
  │
  v
Vector Sync Worker
  │
  ├─ 1. 从 MySQL 拉取权威原文
  ├─ 2. 分块 chunk
  ├─ 3. 调 Embedding 模型
  ├─ 4. 写入 pgvector
  ├─ 5. 更新 sync_state
  └─ 6. 失败写入 embed_task 等待重试
```

同步策略：

| 数据 | 同步方式 | 频率 |
|---|---|---|
| 理论卡 | 手动触发 + 版本变更事件 | 极低频 |
| 职业库 | 定时批量 + 变更事件 | 低频 |
| JD | 实时事件 + 定时批量 | 高频 |
| 报告片段 | 资产版本 +1 时触发 | 中频 |
| 会话摘要 | 会话结束事件 | 实时 |
| 简历 | 上传解析后触发 | 低频 |

幂等保证：

- 用 `content_hash` 对相同内容去重。
- 用 `(namespace, source_id, content_hash)` 防止重复嵌入。
- 删除事件按 `namespace + source_id` 定位并删除对应向量。
- 同步失败进入 `embed_task`，由 Worker 重试或人工补偿。

## 八、检索路径设计

### 8.1 纯向量检索

```text
业务层：vector.search(namespace, query_embedding, top_k, filter)
  │
  ├─ SDK 注入 org_id 过滤
  ├─ pgvector HNSW 检索
  ├─ 返回 top_k 结果，包含 source_id
  └─ 业务层回 MySQL 补全权威详情
```

适用场景：

- 理论卡语义召回
- 会话摘要记忆召回
- 简历与岗位语义匹配

### 8.2 混合检索

```text
业务层：vector.hybrid_search(namespace, query_text, query_embedding, top_k, filter)
  │
  ├─ 并行检索
  │   ├─ ES BM25 全文检索 → top_k1
  │   └─ pgvector 向量检索 → top_k2
  │
  ├─ 融合排序：RRF 或加权排序
  ├─ 返回 top_k 结果
  └─ 业务层回 MySQL 补全权威详情
```

推荐用于职业库、JD、报告片段等既需要关键词命中又需要语义召回的场景。

### 8.3 检索降级

| 故障 | 降级策略 |
|---|---|
| pgvector 不可用 | 降级到 ES 全文检索 |
| Embedding 模型不可用 | 降级到 ES 全文检索，并缓存待嵌入任务 |
| ES 不可用 | 仅使用 pgvector 向量检索 |
| ES 与 pgvector 均不可用 | 返回空结果，并提示稍后重试 |

```text
│       │     → 报告片段重新向量化 → pgvector                          │
│       │                                                              │
│       └─→ 主动事件 Worker                                            │
│             task_stall / node_due / semester_window / profile_stale  │
│             → Schedule / Review 触发                                 │
│             → 陪伴教练生成最小可执行动作                              │
│             → Notify 推送（受打扰度与冷却期约束）                    │
└─────────────────────────────────────────────────────────────────────┘
```

## 十、命名空间与隔离规范

| 存储 | 隔离方式 | 命名规范 |
|---|---|---|
| MySQL | 独立 schema | `zhiyin_service` |
| Redis | 独立 DB / key 前缀 | `zhiyin:` |
| Kafka | Topic 前缀 | `zhiyin.` |
| Elasticsearch | 索引前缀 | `zhiyin_` |
| MinIO | 独立 bucket | `zhiyin-*` |
| PostgreSQL | 独立 database | `zhiyin_vector` |

多租户隔离规则：

- 公共数据 `org_id` 为 NULL。
- 租户私有数据 `org_id` 必填。
- SDK 必须自动注入 `org_id` 过滤。
- 报告、记忆、简历等用户或租户私有数据禁止无租户过滤检索。
- 是否启用 PostgreSQL Row Level Security 作为强化隔离，需要在落地阶段确认。

## 十一、部署形态

### 11.1 MVP 部署

```text
┌────────────────────────────────────────────┐
│  应用节点                                    │
│  zhiyin-service（业务层）                    │
│  含：Loop / Orchestrator / Profile / Behavior │
│      Conversation Memory / Asset             │
│      Workspace / Function                    │
│  impact-worker（影响面传播，MVP 可同进程）    │
│  active-event-worker（主动事件，MVP 可同进程）│
│  vector-sync-worker（同步 Worker）           │
└──────────────┬─────────────────────────────┘
               │
┌──────────────v─────────────────────────────┐
│  中间件节点（复用 pami + 新增 PG）           │
│  MySQL / Redis / Kafka / ES / MinIO         │
│  PostgreSQL + pgvector（新增）              │
└────────────────────────────────────────────┘
```

MVP 建议：

- `zhiyin-service` 是部署单元，采用模块化单体；内部按 `zhiyin-api / zhiyin-business / zhiyin-orchestration / zhiyin-data-sdk / zhiyin-infrastructure / zhiyin-boot` 拆包。
- Vector Sync Worker 可与应用同节点部署。
- 影响面传播 Worker、主动事件 Worker 在 MVP 可并入 `zhiyin-service`，成长期再拆出。
- PostgreSQL + pgvector 可单节点启动，但需保留主从扩展空间。
- 优先打通五环节闭环、动态编排、黑板、影响面传播、主动事件、向量检索、报告资产重算。

### 11.2 成长期部署

```text
PostgreSQL 主从：
  ├─ 主库：写向量
  └─ 从库：读向量，检索优先走从库

Vector Sync Worker：
  ├─ 独立部署
  ├─ 可水平扩展
  └─ 通过 Kafka 分区与任务表保证并发安全
```

### 11.3 规模化部署

当向量规模超过 2000 万、检索延迟不可控或 pgvector 运维成本过高时，评估迁移至 Milvus 等专用向量数据库。迁移前提是 Data Access SDK 已经封装向量接口，业务层不感知底层替换。

## 十四、关键设计决策

1. 基础设施层由 pami（Wanwu）提供原子能力。pami 是**自有平台模块**：组件扩展与部署（含职引所需的 PostgreSQL / pgvector 等）都在 pami 模块内进行；职引侧只经冻结接口调用，不改 pami 内部实现，模块变更同步到 pami 模块文档。
2. 编排层必须通用，不出现职引业务语义。
3. 业务逻辑层只写职引业务语义、领域模型和业务策略。
4. 四层单向依赖：业务 → 编排 / SDK → 基础设施；前端/BFF 只依赖业务逻辑层。
5. 编排层六组原语是业务调用通用能力的核心契约。
6. MySQL 是唯一事实源，pgvector 是向量读模型副本。
7. PostgreSQL + pgvector 作为职引专属向量库，独立 database、独立账号。
8. 统一嵌入模型和向量维度，模型版本化管理，换模型需重建索引。
9. MySQL 到 pgvector 通过 Kafka 事件驱动同步，支持幂等和断点续传。
10. 职业库、JD、报告片段优先采用 ES + pgvector 混合检索。
11. 业务层不直连基础设施，不直接操作向量表。
12. MVP 单节点起步，成长期主从，规模化再评估 Milvus。
13. 微循环是业务状态机主干，支持从任意环节进入、前序资产自动继承、跨会话续接。
14. 智能体作为能力池注册在业务层，由业务编排器选择主理/协理/信息侦查员；通用编排层不感知业务角色。
15. 黑板由画像活状态、行为日志、会话记忆、资产版本影响面组成，权威事实在 MySQL。
16. 影响面传播只重算依赖字段的受影响片段，不整篇重新生成；每次更新资产版本 +1。
17. 主动事件只由真实行为信号触发，受打扰度上限与冷却期约束。

## 一句话总结

职引技术架构以 pami（联通元景葩米 Lite / Wanwu）为基础设施底座，在其上新增通用编排层和职引业务逻辑层；数据访问由 Data Access SDK 统一封装，MySQL 作为唯一事实源，PostgreSQL + pgvector 作为职引专属向量读模型，经 Kafka 事件驱动同步，并与 Elasticsearch 形成混合检索能力，最终支撑画像、行为、会话记忆、资产、五环节、工作台和功能块的业务闭环。

业务侧以「三轴模型 + 五环微循环 + 动态编排 + 黑板影响面传播」为核心：业务编排器在轴 A 上推断用户阶段、在轴 B 上判定当前环节、在轴 C 上选择主理/协理/信息侦查员；画像活状态、行为日志、会话记忆和资产版本组成共享黑板，行为事件驱动增量重算、主动干预与跨会话续接。
